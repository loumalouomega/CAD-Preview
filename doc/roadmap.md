# Roadmap

Candidate features for future CAD-Preview releases, prioritized by value versus effort given what the extension already ships: an OCCT kernel, a Gmsh kernel, and a meshio++ kernel live in the extension host, a full picking/selection pipeline in the webview, a sidecar persistence model, and an MCP server mirroring the pipeline headless. Many high-value features are cheap precisely because that infrastructure exists.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has a per-feature section with the verified implementation details for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a lower tier or in Non-goals, not at the top because it sounds exciting. A tier's heading and admission criterion stay in the file even when it's momentarily empty (see Tier 1 below) — the taxonomy is stable even when nothing currently occupies it.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 5" always means the file's current 5th item, not a fossil of one that shipped.
- **Items marked *needs live-WASM verification* are listed on the strength of the binding manifest alone.** Green in `node_modules/opencascade.js/dist/Supported APIs.md` is **necessary but not sufficient** — both the STEP-unit and the IGES-writer findings started green and only resolved (one negative, one positive) under a real probe. No such item may be *estimated* until it has been probed against the live build; each one names its probe below.
- Most items close a **known, documented limitation** of something that already ships, or are a natural next step identified while building it. A rare one is **defect-shaped** — describing behavior that loses data, corrupts state, or is a security hole rather than merely lacking a feature. Those belong in Tier 1 regardless of effort size, queued here rather than filed separately because the fix and the feature are usually the same work.

Several items below were identified by comparing against [SketchForge-3D](https://github.com/Formsmith746/SketchForge-3D), a browser-based direct-manipulation CAD editor over the same OCCT kernel. Its *capability* gaps transferred well; most of its *interaction* model deliberately did not — see Non-goals.

## Queued

### Tier 1 — Correctness and robustness of what already ships

*Admission: closes a way the current code can silently produce wrong output, lose user data, or strand a session. No new user-facing vocabulary.*

*(None currently queued — every defect-shaped item found so far (kernel fault recovery, the edge-enumerator drift hazard, sidecar external-change reconciliation, preprocess-archive hardening) has closed; see `CLAUDE.md`'s per-feature sections. A future defect-shaped finding always goes here first, regardless of size.)*

### Tier 2 — Fidelity and performance of the display pipeline

*Admission: makes what's already on screen more accurate or faster, without adding a new interaction model.*

1. **XCAF read — assembly structure and colors** (**M–L**, *partially probed against the live WASM — names are confirmed kernel-blocked, scope narrowed accordingly, still not built*). `readShape` uses `STEPControl_Reader_1` → `TransferRoots()` → `OneShape()`, which collapses product structure into a single compound and never reads names; the Components tree labels are synthesized positionally as `Solid ${idx + 1}` (`src/meshExtract.ts`). **A real probing session (not just the binding manifest) found a mixed result, not a clean go:**
   - **Document creation and STEP→XCAF import both work, confirmed live.** `TDocStd_Application` has no numbered constructor overload — only the bare, unsuffixed `new oc.TDocStd_Application()` — mirroring the "single-overload class" pattern already documented elsewhere in this codebase. `app.NewDocument(extendedStringFormat, handleOut)` (a `TCollection_ExtendedString_2` + an empty `Handle_TDocStd_Document_1()`) correctly mutates the passed-in empty handle in place — the SAME "pre-construct an empty out-handle, it gets filled" convention `BRepAlgoAPI`-adjacent calls elsewhere in this codebase never needed, genuinely new but genuinely working. `STEPCAFControl_Reader_1` → `.ReadFile()` → `.SetColorMode/SetNameMode(true)` → `.Transfer_1(docHandle)` (NOT `.Transfer` bare, NOT `.Transfer_1(doc)` unwrapped — it wants the `Handle`, confirmed by trial) all work and return `true`.
   - **Assembly hierarchy traversal fully works, confirmed live on a real multi-part assembly (`as1_pe.stp`).** `XCAFDoc_DocumentTool.ShapesLabel(doc.Main())` (a static, distinct from `.ShapeTool()`) gives the label to walk; `TDF_ChildIterator_2(label, false)` correctly enumerates children (7 top-level labels on `as1_pe.stp`, a known assembly fixture). `XCAFDoc_ShapeTool.IsFree`/`IsAssembly`/`IsSimpleShape`/`GetShape_2` are all **static** methods (not instance methods on the shape-tool object, a real gotcha caught mid-probe) and all work correctly against a label. This alone — real assembly/component hierarchy instead of a flat solid list — is a genuine, achievable win on its own.
   - **Product/component NAMES are comprehensively blocked in this WASM build — confirmed exhaustively, not a guess.** `label.FindAttribute_1(TDataStd_Name.GetID(), emptyHandle_TDF_Attribute)` correctly finds the name attribute (embind's RTTI resolves the returned handle's `.get()` to the real `TDataStd_Name` subtype with no explicit downcast needed — `.Get()` is directly callable and returns a `TCollection_ExtendedString` with a correct `.Length()`). But extracting that string's actual characters is dead every way tried: `.ToExtString()`/`.ToUTF8CString()` both throw `"unbound types: PKDs"`/`"Pc"` (raw pointer return types never bound), `.Value(i)` throws `"unbound types: Ds"` (`Standard_ExtCharacter` unbound), and all 14 numbered `TCollection_AsciiString` constructors reject a `TCollection_ExtendedString` argument outright (wrong arg count/type on every one). **A raw-text scan of the STEP file's own `PRODUCT('name', ...)` entities (mirroring `stepUnits.ts`'s already-established pattern for unit detection) is a possible workaround** but was NOT explored this session — it needs its own feasibility check for correlating a scanned STEP entity id back to the XCAF label it produced, which is a separate, non-trivial bridge.
   - **Per-label colors are NOT yet confirmed working.** `XCAFDoc_ColorTool` exposes exactly one `GetColor` overload (`GetColor_3`, unlike `ShapeTool`'s several) and its real argument shape wasn't found — every combination tried (label+color, label+type-enum+color, shape+type+color, in various orders) threw a `TDF_Label`/`Quantity_Color` type mismatch, suggesting the actual C++ overload signature differs from all standard `GetColor(label, type, color)`/`GetColor(shape, type, color)` forms assumed. Needs a fresh, more systematic overload probe (or a source-level check of THIS exact opencascade.js version's embind declarations) before it can be scoped.
   - **Revised scope, reflecting the above:** this item is no longer "product names, colors, assembly structure" — **names are dropped** (kernel-blocked, not a scoping choice) unless a future attempt validates the STEP-text-scan workaround; colors remain genuinely open pending more probing; assembly structure is the one confirmed-viable piece. `STEPCAFControl_Reader`, `TDocStd_Document`, `TDocStd_Application`, `XCAFDoc_ShapeTool`, `XCAFDoc_ColorTool`, `XCAFDoc_DocumentTool`, and `TDF_ChildIterator` are all green and still completely unused (`grep XCAFDoc src/` → zero hits) — the binding manifest was never the blocker; the concrete API surface above is. This is squarely a *preview/inspect* feature, which is why it ranks above its write-side sibling (item 7 below).

2. **Persisted, topology-anchored annotations** (**M**). Measurements and markup are both explicitly session-only, and markup strokes are screen-space pixels with **no 3D anchoring at all** — they stop meaning anything the instant you orbit, and their only escape is being composited into a screenshot. A review note that survives closing the file is the whole point of a review note. SketchForge's `RulerAttachment` carries a `topologyKey` so a measurement stays attached across edits and detaches honestly when the topology it referenced no longer exists — the same graceful-degradation contract this codebase already applies to unresolved entity ids. A fifth sidecar following `partsSidecar.ts`'s tolerant-parse shape (the persisted view state closed above is the fourth, `<model>.view.json`) — and, per the closed sidecar external-change reconciliation work (see CLAUDE.md), it should be wired into the same file-watcher reconciliation `.edits.json`/`.parts.json`/`.mesh.json`/`.view.json` already get, for the same reason those four do; the entity-rebinding machinery (`src/entityRebind.ts`) already solves the hard half of keeping references alive across topology-changing ops.

3. **Archive integrity: checksums, `minimumReaderVersion`, migration** (**M**). The feature half of the closed preprocess-archive-hardening item (see CLAUDE.md). `parseManifest` reads `version` and, when it is missing or non-numeric, *invents* the current one; nothing ever compares it, so a hypothetical v2 archive loads silently as v1. There are no per-entry checksums (only zip's own CRC32, which is error-detection, not integrity) and no migration path. Two smaller defects belong here too: `load_preprocess` calls `requireRoute(outputPath)`, which only asserts the extension is *supported*, then writes the source bytes verbatim — restoring a STEP archive to `restored.stl` succeeds silently; and the `.geo` file is packed by the writer but deliberately discarded by both readers (regenerated from `.mesh.json`), so it is pure dead weight. SketchForge's `.skf` format is the model to copy: SHA-256 per asset, dedup by hash, `minimumReaderVersion`, an explicit v0→v1 migration, and a documented adversarial-input rejection list with hard limits.

### Tier 3 — Structural work (kernel isolation and interop)

*Admission: multi-week; changes an architectural boundary or adds a kernel capability. Each needs live-WASM verification before it can be **scoped** — being listed here is not an estimate.*

4. **OCCT in a forked child process** (**L**). The enabler for two things that cannot be done well otherwise: real cancellation (kill the child) and true fault isolation — the closed kernel-fault-recovery work (see CLAUDE.md) can recover a *rejected promise* or reset a corrupted singleton after a detected abort, but nothing in-process can un-corrupt an *aborted heap* the instant it happens, only after the fact. `src/gmshService.ts` already documents the entire Emscripten-pthread-under-Node minefield, and `dist/mcp-server.js` already proves a vscode-free standalone bundle of this pipeline is buildable — so the two hardest unknowns are already answered. Also removes the "host is frozen for the duration" property that makes item 5 hard.

5. **Progress reporting and cancellation** (**M**). `handleBRep` posts exactly two static status strings, both *before* any work begins (`src/provider.ts`), then `loadBRep` runs four synchronous, uninterruptible WASM calls on the extension-host event loop — so the host physically cannot post a mid-flight update even if the code wanted to. `CancellationToken` has zero hits in `src/`, and `vscode.window.withProgress` is never used. This must either depend on item 4, or be honestly scoped as *stage-boundary* progress with *stage-boundary* cancellation. **State which in the implementation** — a progress bar that claims to be cancellable and isn't is worse than none. The base-shape-caching prerequisite this item also needed (roadmap item, closed — `loadBRepCached`, see CLAUDE.md) is already satisfied, so building this now measures real per-edit cost, not redundant re-parsing.

6. **Mesh → B-rep promotion, diagnostic-first** (**L**, *needs live-WASM verification, high risk*). `src/exportTargets.ts` states the current limitation as policy: *"there is no path to promote a triangle soup into a B-rep."* That is a property of this codebase, not of the kernel — `ShapeFix_Shape`, `ShapeFix_Solid`, `ShapeFix_Shell`, `ShapeFix_Wireframe`, `ShapeUpgrade_UnifySameDomain`, `StlAPI_Reader` and `RWStl` are all green in the shipped WASM and have **zero** uses in `src/`. The only `BRepBuilderAPI_Sewing` call today takes user-picked faces at a hardcoded `1e-6` tolerance and treats `NbFreeEdges() > 0` as a hard reject with no repair. Closing this would let STL/OBJ/PLY sources use fillet/chamfer, `measure_exact`, mass properties, and B-rep export — everything currently gated behind `BREP_ONLY_OPS`. **Ship phase 1 as a read-only heal-quality report** — free edges, non-manifold edges, degenerate faces, the sewing tolerance actually required, and area/volume delta before vs. after — surfaced through an MCP tool and the panel with a three-valued verdict in the existing `verdictConventions` style. Promote a solid only on a passing report, and tag the result as healed-from-mesh so the `BREP_ONLY_OPS` unlock is visibly provisional. **Phase 2 must not ship first:** a shell that closed only because the tolerance ladder reached `1e-2` would feed `get_mass_properties` a confidently-wrong volume and `measure_exact` a confidently-wrong distance — the same misleading-false-result failure mode glTF support was rejected for, with a much larger blast radius. *Probe first:* `StlAPI_Reader` under the documented MEMFS short-path limit (the IGES false-negative came from an 11+ character path); `ShapeFix_*` constructor arity and whether `Perform` wants the unconstructible `Message_ProgressRange`; and whether `BRepBuilderAPI_Sewing.SetTolerance` can be reused across rungs of a tolerance ladder or needs a fresh instance each time.

7. **XCAF write — assembly structure and per-part colors** (**M**, *needs live-WASM verification*). `writeShape` uses `STEPControl_Writer_1`, which has no color channel and takes a single `TopoDS_Shape` — so exported STEP carries geometry and (since the unit-conversion work) a correct unit label, and nothing else. Parts already have names and colors; today the only format that carries color out is glTF, and only accidentally, via three.js's `GLTFExporter` materials. **Names an explicit regression risk:** `src/stepUnitPatch.ts` must still locate every `GLOBAL_UNIT_ASSIGNED_CONTEXT` in `STEPCAFControl_Writer` output, whose entity layout differs from `STEPControl_Writer_1`'s — verify against the live writer before assuming the closed unit-conversion feature survives. **Requires item 1**: the `TDocStd_Application`/`XCAFDoc_DocumentTool`/`TDF_ChildIterator` plumbing is shared, and building the writer first means building it twice.

### Tier 4 — Interaction and interop conveniences

*Admission: closes a UI gap for a capability the pipeline already has, or adds a format on top of existing ops. Explicitly ranked below every Tier 1–3 item; nothing in this tier is a prerequisite for anything.*

8. **Standard-parts browse and insert panel** (**S**). `search_standard_parts` and `download_standard_part` exist only as MCP tools, and the download path just writes a STEP file to disk for the user to open separately. There is no webview search box, no results list, no insert. This codebase's own convention is that headless and interactive capabilities stay in sync, and this is the clearest place they don't.

9. **Align, distribute, and pattern UI** (**M**). There is no align op at all — `mate` is the closest thing and it is a two-face coincident constraint, not a min/center/max axis alignment against an anchor. Lead with align, which is genuinely absent. Patterns are a smaller gap than they look: linear/circular/mirror arrays already work headless through `run_parametric_script`'s `repeat` construct, so that half is a missing UI, not a missing capability.

10. **Transform gizmo** (**M**). Every transform is typed into text fields today. Two existing decisions must be respected rather than reverted: `onSelectPointerUp` ignores pointer movement over 4 px as camera motion *deliberately* (`src/webview/viewer.ts`), and the numeric fields are `type="text"` *on purpose* so parametric variable expressions parse (`src/webview/editsPanel.ts`). **Scope the drag as a preview that populates the existing translate/rotate/scale form, with Apply still the only thing that pushes an op** — reusing `src/webview/explodePreview.ts`'s cached-base pattern, including the never-compound-onto-the-previous-frame trap it already has a regression test for. A gizmo that mutates the model directly would become a second write path, bypassing `EditsModel`'s push/undo/redo/remove contract and the "webview owns the op stack, host stays dumb" invariant. Decide and document one more thing: what happens when a drag overwrites a field the user had typed an expression into.

11. **Grid and entity snapping** (**M**). There is no geometric snapping of any kind — the grid is a bare `THREE.GridHelper` with a visibility toggle and nothing quantizes to it, and picking returns an entity id, never a point. **Requires item 10**: nothing in the current UI consumes a snapped *coordinate*, so shipping this first produces a grid that quantizes nothing.

12. **SVG import → profile ops** (**M**). No 2D vector format is supported in either direction. Importing an outline from Inkscape or Illustrator and extruding it lands entirely on existing ops (`addPolyline` + `extrude`) with no new kernel surface — a pure-TypeScript path parser, testable without the WASM. SketchForge's `svgImport.ts` is a working precedent for the tessellation-of-béziers half.

### Tier 5 — Evaluated, not actionable

13. **glTF support for `compare_models`** (**M–L**, evaluated and deliberately scoped out, not merely postponed). STL/OBJ/PLY are all now supported via dedicated host-side parsers (`stlParser.ts`/`objParser.ts`/ `plyParser.ts`, all backed by `meshComponents.ts`) — OBJ (plain, already- indexed text) and PLY (a well-specified ASCII/binary format, linearly decodable via one shared header parser) both turned out tractable to hand-roll correctly and validate thoroughly with real fixtures. glTF is a different order of complexity: accessor decoding across 5 component types with an optional `normalized` flag, sparse-accessor overlays, interleaved `bufferView` byte-stride handling, and full scene-graph TRS/matrix composition down to each mesh primitive — with no realistic way to validate a hand-rolled implementation against real-world exporter variety the way the other two formats' fixtures could be validated. Shipping a plausible-looking-but-subtly-wrong parser would risk exactly the "misleading false match" failure mode Compare Models' own design was built to avoid — see CLAUDE.md's "Model comparison" section for the full reasoning.

14. **SVG silhouette export** (**M**, blocked pending a probe). The obvious implementation is dead: every `HLRBRep_*` class is **red** in this build (see Non-goals). The one surviving door is `HLRAppli_ReflectLines`, which is green and produces an outline as a `TopoDS_Shape` — enough for a silhouette, not for a real drawing with hidden lines. Unscopable until someone probes its constructor and output usability; listed so the distinction between "silhouette" and "drawing" stays on record.

## Non-goals / known constraints

- **Writing the CAD source file** — never. The read-only invariant (sidecar persistence, export-only baking) is architectural, not a missing feature.
- **OCCT in the webview** — the kernel stays in the extension host; the webview runs only Three.js (architecture invariant).
- **G-code preview** — considered (text-to-cad ships a strong implementation: layer scrubbing, feature-type coloring, adaptive decimation) and rejected: 3D-printing-oriented, outside this extension's CAD/FEM domain.
- **URDF/SDF robotics rendering** — considered (joint articulation, FK, MoveIt2 integration in text-to-cad) and rejected for the same reason.
- **Interactive sketching with geometric constraints** — considered and rejected, not deferred. It is the single clearest "this is a modeling application now" feature, and CAD-Preview is a preview/inspect/prepare tool. More concretely: the numeric profile and curve forms are **not** a degraded mouse — they accept parametric variable expressions (`L*2`, `R*cos(i*360/N)`) that a click-to-place tool cannot express, so replacing them with drawing would trade away a distinguishing capability for a familiar one. Worth noting that SketchForge, a dedicated sketch application, still has no constraint solver either — building this would mean shipping the weak two-thirds of the feature.
- **Reference-image tracing underlay** — rejected. Its value is almost entirely to sketching, which is a non-goal above; and it would punch a hole in a real design property: every texture in the webview is a procedurally-drawn `CanvasTexture` (`geometryBuilder.ts`'s `dotTexture()`, `labelOverlay.ts`, the generated-SVG icon pipeline), a deliberately asset-free design driven by the webview's CSP. Injecting a user-supplied data-URL image trades that away for a workflow the tool doesn't have.
- **2D vector technical drawings via hidden-line removal** — **kernel-blocked, not deprioritized.** Every `HLRBRep_*` class is red in this OCCT WASM build: `HLRBRep_Algo`, `HLRBRep_PolyAlgo`, `HLRBRep_HLRToShape`, `HLRBRep_PolyHLRToShape`. `HLRAlgo_Projector` is green but is a low-level internal only reachable through them. Same class of finding as `Message_ProgressRange_1` and `Interface_Static.CVal` — recorded here so it isn't re-proposed. The narrow survivor, `HLRAppli_ReflectLines`, is queued as Tier 5 item 14.
- **3D text, engraving, and embossing** — **kernel-blocked.** `Font_BRepFont` and `Font_BRepTextBuilder` are both red in this build, so there is no path from a glyph to a `TopoDS_Shape`.
- **Parametric part generators (gears, threads, springs)** — rejected. Standard parts are something this tool should *source*, not *author*: `search_standard_parts`/`download_standard_part` already fetch real, verified geometry from step.parts as ordinary STEP files the existing pipeline opens. Authoring involute gear profiles is modeling-application scope. The genuine gap here is the missing browse/insert UI, queued as Tier 4 item 8.

## Dependencies

A few items must land in order, and getting it wrong means rework or silent corruption:

- **4 → 5**, for cancellation that genuinely cancels.
- **1 → 7.** The XCAF document plumbing is shared; building the writer first means building it twice.
- **10 → 11.** Snapping has no consumer until something consumes a snapped coordinate.
