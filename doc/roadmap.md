# Roadmap

Candidate features for future CAD-Preview releases, prioritized by value versus effort given what the extension already ships: an OCCT kernel, a Gmsh kernel, and a meshio++ kernel live in the extension host, a full picking/selection pipeline in the webview, a sidecar persistence model, and an MCP server mirroring the pipeline headless. Many high-value features are cheap precisely because that infrastructure exists.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has a per-feature section with the verified implementation details for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **Unlike an earlier version of this convention, an empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 1" always means the file's current 5th item, not a fossil of one that shipped.
- **Items marked *needs live-WASM verification* are listed on the strength of the binding manifest alone.** Green in `node_modules/opencascade.js/dist/Supported APIs.md` is **necessary but not sufficient** — both the STEP-unit and the IGES-writer findings started green and only resolved (one negative, one positive) under a real probe. No such item may be *estimated* until it has been probed against the live build; each one names its probe below.

Several items below were identified by comparing against [SketchForge-3D](https://github.com/Formsmith746/SketchForge-3D), a browser-based direct-manipulation CAD editor over the same OCCT kernel. Its *capability* gaps transferred well; most of its *interaction* model deliberately did not — see Non-goals.

**An item that corresponds to a GitHub issue names it inline** (e.g. *issue #36*). The issue is the request and the discussion thread; this file is the scoping — what already exists, what the real blocker is, and what the phasing should be. Where the two disagree, this file is the one that was checked against the code.

## Queued

### Tier 1 — New model-layer concepts

*Admission: adds a genuinely new concept to the document model — a new persisted entity, a new class of derived information, or a new kernel capability behind a new op kind — rather than closing a gap in an existing one. Most items here are phased so that the cheap, independently-useful phase can ship alone, and several have a phase that needs a live-WASM probe before it can be estimated.*

1. **Substantial new feature ops mined from FluidCAD** (**L**, phased; not estimable per-op until probed. Five cuts have **shipped**: `.thin()` — see `CLAUDE.md`'s "Thin-walled sweep-family features" section — the open-profile operand it left behind, see "Open-profile (wire) operand", the **extrude up-to-face terminator** (planar, join-only `upToFace`, same prism builder at a derived length), **`rib()`** (open spine + thin wall + up-to-face + fuse + junction blend, one atomic op), and **`wrap()`** (true surface *development* of a flat sketch onto a cylinder or cone, then sew-two-offsets thickening, with emboss/engrave/standalone variants — see `CLAUDE.md`'s "Wrap sketch onto cylinder/cone" section). What `rib()` still needed beyond those three turned out to be two things neither supplied: fusing (not appending) with debris-tolerant operand splitting, and automatic junction-edge discovery for the blend. The genuinely large capabilities, listed so the opportunity is on record with an honest size attached rather than mistaken for the cheap set above. Each is ~400–1200 lines of real geometry work in the source project, **not** a wrapper: **`wrap()`** (true surface *development* of a flat sketch onto a cylinder or cone — length-preserving, not projection — then thickening along the surface normal, with emboss/engrave/standalone variants; the most original capability in that codebase — development verified, thickening **unblocked by the green sew-two-offsets probe below**: two one-sided offsets + `ThruSections` skirt close to an exact-volume solid — **now shipped, see `CLAUDE.md`**); **`rib()`** (build a rib from an *open* spine sketch, extruded until it meets surrounding solids, with end-blending into adjacent walls); **loft `.guides()` plus `.startCondition`/`.endCondition`** (guide rails the surface must ride, and normal/tangent takeoff with a signed magnitude — a real quality jump over plain `ThruSections`, which is what this codebase currently uses); **extrude/cut up-to-a-face terminators** (`extrude(face)`, or first/last intersecting face found by filter — the "up to next" every mainstream CAD has); and **`.pick(regions)` + `.drill()`** for choosing which enclosed regions of a multi-region sketch a feature consumes.

    **The open-profile operand has now shipped, which changes what `rib()` still needs.** All four ops take `profileEdges`/`profileEdgeSets` — a set of `edge-N` ids assembled into one wire — beside the original `face-N` form, so an `addPolyline` with `closed: false` is finally consumable, and an open profile builds a walled body directly. That removes the op-model half of `rib()`. What `rib()` still needs is the geometry the operand was never going to supply: extruding the wall **until it meets** the surrounding solids (an up-to-face terminator, shared with the `extrude(face)` item above) and blending its ends into the adjacent walls. Note also that the roadmap's own kernel note here was imprecise and is corrected in `CLAUDE.md`: `isOpenResult = true` gives a ONE-SIDED offset, not a band; the closed band comes from `isOpenResult = false`.

    **Where CAD-Preview is already ahead, recorded so this item is read as a gap list and not a scoreboard**: FluidCAD has **no** assemblies, mates, or joints (its `part()` is a fusion-isolation namespace with a name, nothing more), no box/cone/torus primitives, no variable-radius or face fillet, no pattern-along-path, no interference detection, no model comparison, no mesh health or mesh→B-rep promotion, no format breadth beyond STEP/STL/BRep, and essentially no validation or manufacturability analysis. Several of those are shipped capabilities here. The transfer is one-directional for this item only. The cheap thin-wrapper set this item was split from (shell join styles, circumscribed polygons, distance-angle chamfer, `draft`, construction geometry, edge slots, midplane/midaxis references) has shipped in full — see `CLAUDE.md`'s "Cheap thin-wrapper ops mined from FluidCAD" section.

    **Sequencing**: nothing here blocks anything else in this file, and each op is independently shippable. With `.thin()`, the open-profile operand, the up-to-face terminator, `rib()`, `.pick(regions)` + `.drill()`, and `wrap()` all closed, the one remaining capability is loft guides/conditions (**probed-red**, scoped below).

    **Loft conditions probe record (smoothing shipped; the rest deliberately unexposed).** Probed live: `ThruSections` binds `SetSmoothing`/`SetParType`/`SetContinuity`/`SetCriteriumWeight`/`SetMaxDegree` (all accept their args, enums `GeomAbs_Shape`/`Approx_ParametrizationType` read off directly), but only `SetSmoothing(true)` moves geometry (-0.711% volume on a 4-section progressively-twisted fixture; zero effect on 2-section or alternating-orthogonal lofts, where there is no twist to smooth). `SetContinuity` (C1/C2/G1/G2) and the rest are byte-identical with and without on every fixture tried, including shape-changing sections — accepted-but-effectless, so only `smoothing?: boolean` is exposed (omitted/false = today's behavior, replay-identical). True guide rails have no `ThruSections` target (`AddGuide` does not exist there) and would need a `MakePipeShell` rewrite — still queued.

    **Loft guides/conditions probe record (red, do not re-probe without a new idea).** Probed live in three rounds: `BRepOffsetAPI_MakePipeShell` takes exactly 1 ctor arg (the spine wire, no suffixed variants); `Add_1(wire, WithContact, WithCorrection)` + `Build` + `IsDone` + `MakeSolid` verified end-to-end (two circles → closed 3-face solid), and `SetMode_1` accepts the full `GeomFill_Trihedron` enum — so a basic pipe-shell sweep *works*, but buys nothing over `ThruSections` and is not a rewrite target. **No guide-rail wiring is reachable**: `SetMode_4(wire)` returns `false` even for the spine itself (dead), `SetMode_5(wire, double, double)` accepts but is a binormal/tolerance setter, and the decisive rail-coincidence test (sections r=10/6, rail bowed to x=25 mid-span, `BRepExtrema_DistShapeShape` against the bulge point) reads 16.890 with the rail wired vs. 16.916 without — noise, not following. The lower-level assembly (`BRepFill_PipeShell` + `BRepFill_Sweep` + `GeomFill_LocationGuide`) would need 3+ hand-wired handle layers (`Handle_BRepFill_SectionLaw`, `Handle_GeomFill_TrihedronWithGuide`, …), each another unbound-type risk. Start/end conditions die with guides: `BRepFill_FaceAndOrder_2`/`EdgeFaceAndOrder_2` exist as signatures but have no reachable sweep consumer, and `ThruSections` has no condition API. Suggested fallback if rails ever matter: resample the rail into N intermediate sections + plain `ThruSections` — a different feature, not a silent substitution.

    **`.pick(regions)` + `.drill()` probe record (green, shipped).** All analytic, no new bindings: `MakeFace_15(outer).Add(inner)` keeps hole-ness for an enumerated inner wire added as-is (20×20 with 10×10 hole rebuilds to exactly 300; reversed it adds an island, 500 — orientation is the discriminator, and `TopoDS.Orientation` is unbound so nothing may read it); each enumerated wire alone builds its enclosed disk (400/100); region prism minus region prism via `Cut_3` is exact (3000). Shipped as `pick` on the single-profile sweep-family ops plus a `drill` cut op — see `CLAUDE.md`.

    **`wrap()` probe record (blocked, do not re-probe without a new idea).** Probed live in two stages: (A) the development half **works** — pcurve wire via the helix-verified `GCE2d_MakeSegment_1` → `MakeEdge_30` → `BuildCurves3d_2` chain, then a surface-constrained face via `BRepBuilderAPI_MakeFace_21(hSurf, wire, true)` (found by reading embind's own arity errors across all 22 overloads; the analytic-surface overloads `_16`–`_20` want `gp_Pln`/`gp_Cylinder`/etc., not a handle), giving area exactly 100.0 for a 10×10 sketch on R=10; (B) the thickening half **fails** — `BRepOffsetAPI_MakeOffsetShape_1()` + 8-arg `PerformByJoin` runs clean (`IsDone=true`) but returns only the offset face (bbox proves it sits at the offset distance), never a closed solid, across all join modes and the 8-arg `_2` ctor form; even offsetting a closed box gives a wrong volume (1698 vs 1728), so the class itself is broken in this build, not just the open-sheet case. Blocked pending a sew-two-offsets construction (itself unprobed, not a composition of anything verified) — do not ship development-without-thickness, which has no consumer.

    **Sew-two-offsets follow-up probe (green — `wrap()` shipped).** Probed live in seven abort-isolated stages (throwaway esbuild-bundled scripts driving the real `getOcct`/`volumePropertiesAdaptive` entry points, not committed), all green: (0) `MakeFace_21` re-derived, developed 10×10 face area exactly 100.0; (1) `MakeOffsetShape_1()` + 8-arg `PerformByJoin(face, d, 1e-6, Skin, false, false, Arc, false)` returns a single-face SHELL per side (pull the face via explorer, csgModel-style) with analytically exact offsets — radial separation exactly 2.0, areas exactly 110.0/90.0, 4 edges; (2) boundaries correspond radially 4/4 at 1e-9 (same angle, same z, Δradius = t); (3) `ThruSections(true, false, 1e-6)` over the two `OuterWire`s returns a closed SOLID directly (1 solid / 1 shell / 6 faces: 4×20 walls + 110/90 caps), volume exactly 200.0; (4) explicit sew ladder closes at 1e-6 with 0 free edges and preserves volume 200.0 — and distinct-edge counting (`HashCode`+`IsSame`, the `enumerateEdges` technique) shows 12 shared edges already pre-sew, so the explicit sew is a confirming no-op worth keeping as a safety net; (5) generality: cone target (`Geom_ConicalSurface_1` works first try), t=1/4, off-center sketch — `vol/midArea == t` to ~1e-9 in every case. Negative control re-run: closed-box +1 offset still yields ~1698.44, so the environment matches the original finding and the old red verdict stands — sidestepped, since this construction never asks the offsetter for a solid. Two measurement gotchas recorded: `SurfaceProperties2`'s return value is NOT the area (read `props.Mass()`), and this build's `TopExp_Explorer` revisits shared edges (a primitive box reads 24 visits for 12 edges — counts are incidences, sharing needs the de-dup). What remains is op design, not probing: emboss/engrave/standalone as offset-pair choices fused into the target, then panel, `OP_PARAM_DOCS`, docs, smoke.

## Non-goals / known constraints

- **Writing the CAD source file** — never. The read-only invariant (sidecar persistence, export-only baking) is architectural, not a missing feature.
- **OCCT in the webview** — the kernel stays in the extension host; the webview runs only Three.js (architecture invariant).
- **G-code preview** — considered (text-to-cad ships a strong implementation: layer scrubbing, feature-type coloring, adaptive decimation) and rejected: 3D-printing-oriented, outside this extension's CAD/FEM domain.
- **URDF/SDF robotics rendering** — considered (joint articulation, FK, MoveIt2 integration in text-to-cad) and rejected for the same reason.
- **Interactive sketching with geometric constraints** — considered and rejected, not deferred. It is the single clearest "this is a modeling application now" feature, and CAD-Preview is a preview/inspect/prepare tool. More concretely: the numeric profile and curve forms are **not** a degraded mouse — they accept parametric variable expressions (`L*2`, `R*cos(i*360/N)`) that a click-to-place tool cannot express, so replacing them with drawing would trade away a distinguishing capability for a familiar one. Worth noting that SketchForge, a dedicated sketch application, still has no constraint solver either — building this would mean shipping the weak two-thirds of the feature.
- **Reference-image tracing underlay** — rejected. Its value is almost entirely to sketching, which is a non-goal above; and it would punch a hole in a real design property: every texture in the webview is a procedurally-drawn `CanvasTexture` (`geometryBuilder.ts`'s `dotTexture()`, `labelOverlay.ts`, the generated-SVG icon pipeline), a deliberately asset-free design driven by the webview's CSP. Injecting a user-supplied data-URL image trades that away for a workflow the tool doesn't have.
- **2D vector technical drawings via hidden-line removal** — **kernel-blocked, not deprioritized.** Every `HLRBRep_*` class is red in this OCCT WASM build: `HLRBRep_Algo`, `HLRBRep_PolyAlgo`, `HLRBRep_HLRToShape`, `HLRBRep_PolyHLRToShape`. `HLRAlgo_Projector` is green but is a low-level internal only reachable through them. Same class of finding as `Message_ProgressRange_1` and `Interface_Static.CVal` — recorded here so it isn't re-proposed.

  **The narrow survivor, `HLRAppli_ReflectLines`, has now been probed against the live WASM, and it is not the way in either.** The binding genuinely works — the unsuffixed constructor takes a `TopoDS_Shape`, and `SetAxes`/`Perform`/`GetResult` are all bound and functional (249 ms on `bull.stp`, returning a non-null compound this codebase's own `enumerateEdges` reads as 25 edges). It was rejected on the drawing itself, which is only visible by looking at it: rendered side by side against a tessellation-derived silhouette of the same view, `GetResult()` produced the outer boundary and a few fragments while missing the part's circular holes and interior cutout entirely. `GetResult()` returns reflect lines only; sharp feature edges live behind `GetCompoundOf3dEdges(type, …)`, whose `type` argument is an `HLRBRep_TypeOfResultingEdge` — from the entirely-red family above — so calling it throws. The one filter that would make the kernel path competitive is unreachable. **SVG silhouette export shipped anyway**, built on triangle adjacency instead (`silhouetteEdges.ts`), which additionally works for STL/OBJ/PLY/glTF sources that `HLRAppli_ReflectLines` could never have handled — see `CLAUDE.md`'s "SVG silhouette export" section. Hidden-line *drawings* remain out of reach through the B-rep kernel; an *outline* no longer is.

  **The kernel-agnostic path has now SHIPPED — `export_technical_drawing` (`src/hiddenLineRemoval.ts`), and this Non-goal is narrowed accordingly.** Everything above stays true of the *kernel* path: `HLRBRep_*` is still unavailable and `HLRAppli_ReflectLines` is still the wrong tool. What is no longer true is the conclusion. The visibility test runs on tessellated triangles and calls no OCCT hidden-line API at all, so hidden-line *drawings* — visible edges solid, occluded edges dashed — now exist for B-rep and mesh sources alike. Still out of scope, deliberately: dimensions and multi-view sheet layout (see the closed item's own Phase 2 note).

  **Superseded context, kept for the record:** The blocker above is specific to OCCT's own `HLRBRep_*` family; it says nothing about a hidden-line test built directly on the tessellated triangles this codebase already has for every source, B-rep or mesh. A local sibling project, HCAD, independently ships exactly that: a grid-bucketed per-edge visibility test with no B-rep HLR call anywhere in it. This doesn't change anything above — the B-rep kernel path is still dead, for the reasons already recorded — but it means hidden-line *drawings*, not just an outline, are no longer permanently out of reach either; they're queued, not ruled out.
- **3D text, engraving, and embossing** — **kernel-blocked.** `Font_BRepFont` and `Font_BRepTextBuilder` are both red in this build, so there is no path from a glyph to a `TopoDS_Shape`.
- **Parametric part generators (gears, threads, springs)** — rejected. Standard parts are something this tool should *source*, not *author*: `search_standard_parts`/`download_standard_part` already fetch real, verified geometry from step.parts as ordinary STEP files the existing pipeline opens (and, since the closed "Standard-parts browse and insert panel" item, so does the interactive sidebar). Authoring involute gear profiles is modeling-application scope.
- **Bundling `openscad-wasm`** — rejected (was path (c) of the now-closed OpenSCAD item). Technically attractive but a GPL-3.0-or-later one-way door: CGAL is GPLv3+/LGPLv3+ with no GPLv2 option and Manifold is Apache-2.0 (FSF-held GPLv2-incompatible), and it costs ~8–14 MB plus ~8 MB more for `text()`. The shipped alternative — shelling out to a user-installed binary (mere aggregation, not linking) — covers `.scad` with zero bundled megabytes and no license propagation. Revisit only if the external binary stops being a viable dependency.
