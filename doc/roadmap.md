# Roadmap

Candidate features for future CAD-Preview releases, prioritized by value versus effort given what the extension already ships: an OCCT kernel, a Gmsh kernel, and a meshio++ kernel live in the extension host, a full picking/selection pipeline in the webview, a sidecar persistence model, and an MCP server mirroring the pipeline headless. Many high-value features are cheap precisely because that infrastructure exists.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has a per-feature section with the verified implementation details for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **Unlike an earlier version of this convention, an empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 1" always means the file's current 5th item, not a fossil of one that shipped.
- **Items marked *needs live-WASM verification* are listed on the strength of the binding manifest alone.** Green in `node_modules/opencascade.js/dist/Supported APIs.md` is **necessary but not sufficient** — both the STEP-unit and the IGES-writer findings started green and only resolved (one negative, one positive) under a real probe. No such item may be *estimated* until it has been probed against the live build; each one names its probe below.

Several items below were identified by comparing against [SketchForge-3D](https://github.com/Formsmith746/SketchForge-3D), a browser-based direct-manipulation CAD editor over the same OCCT kernel. Its *capability* gaps transferred well; most of its *interaction* model deliberately did not — see Non-goals.

**An item that corresponds to a GitHub issue names it inline** (e.g. *issue #36*). The issue is the request and the discussion thread; this file is the scoping — what already exists, what the real blocker is, and what the phasing should be. Where the two disagree, this file is the one that was checked against the code.

## Queued

### Tier 1 — New model-layer concepts

*Admission: adds a genuinely new concept to the document model — a new persisted entity, a new class of derived information, or a new kernel capability behind a new op kind — rather than closing a gap in an existing one. Most items here are phased so that the cheap, independently-useful phase can ship alone, and several have a phase that needs a live-WASM probe before it can be estimated.*

1. **Selector synthesis — persist a re-executable query instead of a positional entity id** (**L** overall — the machinery below has **shipped** except op-operand persistence; Phase 1, the build-time classification buckets, has **shipped** — see `CLAUDE.md`'s "Build-time classification buckets" section — and so have the ladder's first three rungs, whole bucket → bucket plus an induced predicate → scene-wide predicate, surfaced headless as `resolve_selector`, plus constant-free-first induction with a live oracle, surfaced as `synthesize_selector`, plus Part-level persistence (`Part.selector` annotation+cache, resolved host-side on open and after every op-list change, oracle-gated writes). What remains is op-operand queries; the bucket-indices bottom rung needs no build — positional ids plus the existing rebind already are the fallback). Comparing against [FluidCAD](https://fluidcad.io), which faces the same topological-naming problem every history-based CAD faces and answers it in a way this codebase has not considered: **it never persists an entity reference at all.** A pick in its viewport is converted into a *source-code query expression* that re-derives the selection from scratch on every rebuild. There is no id to go stale, because there is no id.

    **This is a genuinely different answer from the one already shipped here, and it complements rather than replaces it.** CAD-Preview persists positional `face-N`/`edge-N`/`solid-N` ids and repairs them after the fact with `entityRebind.ts`'s best-effort geometric match (bbox-centre nearest-neighbour with an area/length tie-break) — a *recovery* mechanism that runs after topology changed and, by its own documented admission, "can't distinguish 'this face moved' from 'this face was deleted and a new coincidental one appeared nearby.'" A stored query is a *prevention* mechanism: it never needed to survive renumbering because it re-resolves against whatever the model currently is. The two compose — a query that resolves to exactly one entity is authoritative, and the existing rebinding stays as the fallback for a stored raw id, so nothing already persisted has to be migrated.

    **Phase 1 already shipped, and it changed one assumption below.** The build-time classification buckets (FluidCAD's `endFaces`/`sideFaces`/`capEdges` idea) are recorded per-op during the `applyEditsBRep` fold via a before/after face-set diff, surfaced as `BRepResult.opBuckets` → the `geometry` message's `opBuckets` → Edits-history `+N` chips (click-to-highlight), and in `load_model`/`apply_edit_ops`/`render_ops_prefix` responses. Verified live: extrude's `startCap` comes from `MakePrism`'s `Copy=false` identity reuse and its `endCap` from a farthest-along-direction split; `band`-style roles include REBUILT adjacent faces, not just brand-new ones. **The recorded bucket ids are valid against the model state at their own op's step** — which is exactly why the machinery below needs a *re-executable* query rather than the recorded ids: re-resolving a bucket against a newer model state is prefix-replay work (now cheap and mechanical, since the recording side already exists), and the query form is what avoids paying it on every access.

    **Two remaining pieces of portable machinery, in the order they'd be built:**

    - **A synthesis ladder**, tried in order and stopping at the first candidate that resolves: whole bucket → bucket plus an induced predicate → a scene-wide predicate (all three **shipped** as `resolve_selector`, rung by rung) → bucket indices (remaining). The ladder matters because the top rungs are the stable ones and the bottom rung is what today's positional ids already are, so the fallback is never worse than the status quo. The Phase 1 buckets are the raw material for every rung.
    - **Constant-free-first induction** (**shipped** as `synthesize_selector`: greedy set-cover over the induced-layer leaves with restarts, ordered qualitative → exact normal → area literals, verified live by exact re-execution plus `centreDistance ~ 0` before returning). A greedy set-cover over candidate predicates, with restarts to escape a myopic opener, that **prefers predicates carrying no baked-in numeric constant** — `edge().line().below("xz")` beats `edge().onPlane("xz", -34.641…)` even when the latter needs fewer terms, because a qualitative/datum predicate survives the dimension edits that silently break a literal. This is the single most transferable idea in the whole approach and the one that makes stored queries meaningfully better than stored coordinates.
    - **Oracle verification.** Every candidate is *executed* before being accepted, and kept only if it resolves to exactly the picked set. This is what makes a synthesized selector trustworthy rather than plausible, and it is the same discipline this codebase already applies when it re-`inspect`s a rebound id and compares geometry rather than trusting the match.

    **One correctness gate worth carrying over verbatim: bindability.** A pick whose producing op was a pattern instance or a replayed op cannot be safely named, because the name would be ambiguous across instances — FluidCAD detects this and routes those picks to a scene-wide predicate instead. CAD-Preview has exactly this shape today (`patternLinear`/`patternCircular` append `count - 1` copies; the mesh engine tags them `pattern-{K}`), so the same check applies directly, and getting it wrong would produce a selector that silently resolves to the wrong instance — the misleading-false-result failure mode this file gates other items behind a report for.

    **Scope discipline this item must state, because it is the obvious way to get this wrong:** the query language should stay a small predicate AST persisted as JSON in the existing `.edits.json` sidecar, resolved by the same tolerant gate `validateEditOp` already is — **not** a new expression language and **not** executable code. This codebase already rejected `eval()` on CSP grounds for `paramExpr.ts` and hand-wrote a recursive-descent evaluator instead; a selector AST is the same call. It also shares a predicate vocabulary the closed query filters shipped (`src/webview/selectFilters.ts`'s `FACE_FILTERS`/`LINE_FILTERS`), which it must reuse rather than inventing a second.

    **Verification**: the induction, the ladder, and the AST resolver are all pure and unit-testable headless against hand-built entity-fact fixtures (no WASM) — the oracle-verification step is what needs the live kernel, and its bar is the one `measure_exact`'s own radius path set: not "the selector resolved" but "the selector resolved to the *same* entity, confirmed by comparing `inspect`-reported geometry against the pre-edit baseline with zero delta," exactly as the closed entity-rebinding work already verifies itself in `npm run mcp:smoke`.

2. **Substantial new feature ops mined from FluidCAD** (**L**, phased; not estimable per-op until probed. Four cuts have **shipped**: `.thin()` — see `CLAUDE.md`'s "Thin-walled sweep-family features" section — the open-profile operand it left behind, see "Open-profile (wire) operand", the **extrude up-to-face terminator** (planar, join-only `upToFace`, same prism builder at a derived length), and **`rib()`** (open spine + thin wall + up-to-face + fuse + junction blend, one atomic op). What `rib()` still needed beyond those three turned out to be two things neither supplied: fusing (not appending) with debris-tolerant operand splitting, and automatic junction-edge discovery for the blend. The genuinely large capabilities, listed so the opportunity is on record with an honest size attached rather than mistaken for the cheap set above. Each is ~400–1200 lines of real geometry work in the source project, **not** a wrapper: **`wrap()`** (true surface *development* of a flat sketch onto a cylinder or cone — length-preserving, not projection — then thickening along the surface normal, with emboss/engrave/standalone variants; the most original capability in that codebase); **`rib()`** (build a rib from an *open* spine sketch, extruded until it meets surrounding solids, with end-blending into adjacent walls); **loft `.guides()` plus `.startCondition`/`.endCondition`** (guide rails the surface must ride, and normal/tangent takeoff with a signed magnitude — a real quality jump over plain `ThruSections`, which is what this codebase currently uses); **extrude/cut up-to-a-face terminators** (`extrude(face)`, or first/last intersecting face found by filter — the "up to next" every mainstream CAD has); and **`.pick(regions)` + `.drill()`** for choosing which enclosed regions of a multi-region sketch a feature consumes.

    **The open-profile operand has now shipped, which changes what `rib()` still needs.** All four ops take `profileEdges`/`profileEdgeSets` — a set of `edge-N` ids assembled into one wire — beside the original `face-N` form, so an `addPolyline` with `closed: false` is finally consumable, and an open profile builds a walled body directly. That removes the op-model half of `rib()`. What `rib()` still needs is the geometry the operand was never going to supply: extruding the wall **until it meets** the surrounding solids (an up-to-face terminator, shared with the `extrude(face)` item above) and blending its ends into the adjacent walls. Note also that the roadmap's own kernel note here was imprecise and is corrected in `CLAUDE.md`: `isOpenResult = true` gives a ONE-SIDED offset, not a band; the closed band comes from `isOpenResult = false`.

    **Where CAD-Preview is already ahead, recorded so this item is read as a gap list and not a scoreboard**: FluidCAD has **no** assemblies, mates, or joints (its `part()` is a fusion-isolation namespace with a name, nothing more), no box/cone/torus primitives, no variable-radius or face fillet, no pattern-along-path, no interference detection, no model comparison, no mesh health or mesh→B-rep promotion, no format breadth beyond STEP/STL/BRep, and essentially no validation or manufacturability analysis. Several of those are shipped capabilities here. The transfer is one-directional for this item only. The cheap thin-wrapper set this item was split from (shell join styles, circumscribed polygons, distance-angle chamfer, `draft`, construction geometry, edge slots, midplane/midaxis references) has shipped in full — see `CLAUDE.md`'s "Cheap thin-wrapper ops mined from FluidCAD" section.

    **Sequencing**: nothing here blocks anything else in this file, and each op is independently shippable. With `.thin()`, the open-profile operand, the up-to-face terminator, and `rib()` all closed, the remaining three (`wrap()`, loft guides/conditions, `.pick(regions)` + `.drill()`) are each independently shippable.

### Tier 2 — Externally gated

*Admission: the work is understood and scoped, but is blocked on a decision or an event outside this repository — a license choice, an upstream merge, or a dependency that does not yet exist. Listed so the blocker is on record and re-scoping is unnecessary when it clears; **not** estimable until it does.*

3. **Open OpenSCAD (`.scad` / `.csg`) files** (*issue #35*) (**M** for the recommended path; **L** and license-affecting for the maximal one).

   Three genuinely distinct approaches, in ascending cost. **The recommendation is (a) plus (b); (c) should not be chosen by default.**

   - **(a) Parse `.csg` only — no new dependency, no license change.** OpenSCAD's `.csg` export is *the fully evaluated model*: loops unrolled, modules inlined, variables literalised, `if` branches collapsed, every transform emitted as an explicit 4×4 `multmatrix`. **There is therefore no language to implement** — FreeCAD's own `.csg` lexer has 33 reserved words and no arithmetic, no `if`/`for`, no variables, because none survive into the format. Most nodes (`cube`, `sphere`, `cylinder`, `polyhedron`, `union`, `difference`, `intersection`, `group`, `multmatrix`) map directly onto primitives and booleans this codebase already has, with graceful degradation on the rest — the same convention every unresolvable operand in this codebase already follows.
   - **(b) Shell out to a user-installed `openscad` binary** for `.scad` → `.csg`, then (a). Still zero bundled megabytes and **no license propagation — a separate process is mere aggregation, not linking**. Degrades to a clear `supported: false` when the binary is absent, structurally identical to how `render_snapshot` already handles a missing Playwright. This is precisely FreeCAD's own architecture.
   - **(c) Bundle `openscad-wasm`.** Technically attractive: it is under the official `openscad` GitHub org, actively committed to, ships a dedicated **Node** build, needs no `SharedArrayBuffer`, and drives through an Emscripten MEMFS plus a literal `callMain(argv)` — structurally identical to how this codebase already drives Gmsh. **But it costs roughly 8–14 MB uncompressed (plus ~8 MB more if `text()` is ever to work), and it permanently upgrades the shipped `.vsix` to GPL-3.0-or-later.** CGAL is GPLv3+/LGPLv3+ with no GPLv2 option, and Manifold is Apache-2.0, which the FSF holds GPLv2-incompatible; OpenSCAD's own playground documents shipping its build as GPLv3 for exactly these reasons. **This is not a conflict for a GPL-2.0-*or-later* project** — the "or later" grant is precisely the escape hatch — **but it is a one-way door, and it would be the first bundled dependency to force it** (gmsh-wasm is GPL-2.0-or-later and OCCT is LGPL-2.1-with-exception; both are GPLv2-compatible today, and so is fTetWild's own MPL-2.0 — see `CLAUDE.md`'s "fTetWild robust volume meshing" section, which also closed the "Robust volumetric meshing from a skin mesh" item this note used to cross-reference, by a route that needed no MMG/GPLv3 decision at all).

   **One correctness decision must be settled before any option, and getting it wrong reproduces the same misleading-false-result failure mode the primitive-recognition work describes.** **OpenSCAD's `cylinder` is a faceted prism, not an analytic cylinder.** `$fn`/`$fa`/`$fs` survive into `.csg`, and the common default `$fn = 0` means *unresolved* — the consumer must reimplement OpenSCAD's own segment-count rule from `$fa`/`$fs`. Mapping a `$fn = 10` cylinder onto an exact `BRepPrimAPI_MakeCylinder` yields a solid that silently disagrees with OpenSCAD's own STL by the chord error, and `get_mass_properties`/`measure_exact` would then report confidently-wrong numbers. FreeCAD's answer is an explicit dial — a `useMaxFN` preference (default 16: below it build the real polygon, above it treat as circular) — worth copying, though note its default silently favours exactness over fidelity.

   **Other limits to record now rather than discover later:** `.csg` prints at default stream precision (~6 significant figures), a hard accuracy ceiling on anything reconstructed from it, and rigid transforms come back with float noise (`rotate([90,0,0])` → `2.22045e-16`), so exact axis alignment must be recovered with a tolerance. A `multmatrix` is **not** guaranteed rigid, since `scale`/`mirror` collapse into it. Module names are destroyed — every user module becomes an anonymous `group()`. `hull` and `minkowski` have no OCCT equivalent at all (FreeCAD round-trips them through the binary and accepts triangles). `text()` carries a font *name*, not outlines — and the official WASM build ships with "no support for fonts". `import`/`surface` reference external files, so `.csg` is evaluated but not self-contained. And the format is documented poorly, versioned inconsistently, and framed by its own man page as "mainly used for debugging and testing" — treat it as a de-facto format with no stability guarantee.

   **Ruled out, with evidence: writing a JavaScript OpenSCAD evaluator.** Every prior attempt is dead — the JSCAD translator is deprecated and *its own designated successor is also deprecated* — the one live from-scratch effort is Rust with acknowledged silent divergences from the reference implementation, and OpenSCAD's `$`-variable **dynamic** scoping alongside ordinary lexical scoping is a documented design landmine that upstream contributors themselves call one of the language's worst mistakes. Upstream also closed its own bytecode-interpreter rewrite as not planned. This is the same "shipping the weak two-thirds of the feature" reasoning that rejected a constraint solver in Non-goals.

4. **Native 6-DOF (SpaceMouse-class) input for the viewport** (**M–L**, externally gated on a native-module packaging decision). Comparing against [SindriCAD](https://github.com/MakerViking/sindricad): its Rust layer (`src-tauri/src/spacemouse.rs`) reads a 3Dconnexion SpaceMouse via raw HID (its webview has no WebHID access under WebKitGTK on Linux), ranking candidate devices by **HID usage page/usage** (Generic Desktop / Multi-axis Controller, `0x01`/`0x08`) rather than vendor-ID allowlisting — fixed this way after a vendor-only match once misidentified an ordinary Logitech mouse as a SpaceMouse and fed its motion into the 3D camera.

    **The constraint that forced SindriCAD's Rust-side workaround doesn't apply to CAD-Preview's own layer split, which changes where this would live.** A VS Code webview has no WebHID either (the same browser-sandbox gap), but CAD-Preview's **extension host** is a plain Node.js process, not a browser sandbox — the same process that already runs OCCT/Gmsh/meshio++ WASM. A native HID addon could in principle read the device there and pipe motion deltas to the webview over the existing `postMessage` channel (`Viewer.orbit`/`pan`/`dolly`, already exposed and unit-tested in `cameraControls.ts`), mirroring the OCCT-in-host/Three.js-in-webview split this codebase already has, with no Tauri-style native shell needed.

    **What actually gates this, and why it is externally gated rather than a routine dependency bump**: every WASM dependency this codebase bundles today (OCCT, Gmsh, meshio++) is architecture-independent by construction — one `.wasm` file runs on any host CPU/OS. A native HID addon is not: it needs a prebuilt binary per OS/CPU-arch combination the `.vsix` targets, a real packaging model change (platform-specific `.vsix` publishing, which this extension doesn't use today) versus the current single universal package. That's a decision to make deliberately, not a probe to run — hence Tier 2, alongside the OpenSCAD and MMG items' own license-gated packaging decisions, rather than a routine dependency bump.

    **If ever built, the one concrete technical lesson worth carrying over verbatim**: device discovery by HID usage-page/usage, not vendor ID — the exact bug SindriCAD's own comment records hitting once.

### Tier 3 — Documentation and onboarding

*Admission: closes a gap in how the extension explains itself — to a new user, a contributor, or an agent — with no kernel/webview/MCP capability change; the deliverable is `doc/**` content plus, at most, the tests and CI gates that keep it honest. Ranked last because nothing here blocks or is blocked by the feature tiers above, not because it is low-value.*

5. **Per-step generated screenshots for the tutorials** (**S–M**; Phase 1 — the five narrative pages themselves — has **shipped**, see `CLAUDE.md`'s "Narrative tutorials" section). `doc/tutorials/` now has an index plus five pages (bracket, parametric bolt-circle flange, shelled enclosure, FEA prep, model-with-an-agent), each with numbered `Step N` sections and a **Full operation list** block that this repo's own test suite compiles on every `npm test`. What they reuse is the *existing* 20 screenshots, chosen where a step already matches a captured panel; no shot yet shows a tutorial's own part at a given step.

    **What remains is the capture pipeline, per `CLAUDE.md`'s standing "screenshots are generated, never hand-captured" rule.** Investigated in detail: `scripts/screenshots/fixtures-entry.ts` produces one *global* fixture set from `bull.stp` with no per-shot parametrization (it calls `loadBRep(ROOT, bytes, "step")` with three args), and `capture.mjs`'s `SHOTS` is a hand-written `{file, setup(page), target}` list — both additive-friendly, but genuinely new work. `fixtures-entry.ts` would need to call the already-4-parameter `loadBRep(extensionPath, bytes, "step", ops)` with the cumulative `EditOp[]` prefix for each tutorial step. **The ids those ops need are no longer an unknown** — every tutorial's op list was probed against the live kernel while writing Phase 1 and is pinned in `npm run mcp:smoke`, so this phase inherits them rather than re-deriving them. `capture.mjs` then needs roughly 10 purely-additive `SHOTS` entries (flat filenames — only `doc/public/screenshots/` is ever `mkdirSync`'d), reusing `populate()`'s exact `geometry → {type:"viewState", view:null} → sleep → tree → sleep` ordering, whose `viewState` post is load-bearing for correct first-load framing.

    **Verification**: `npm run build` → `npm run docs:screenshots` → **visually inspect every new PNG**, not just the exit code (`CLAUDE.md` records a real exit-0-but-silently-broken screenshot regression from skipping exactly this) → `npm run docs:build` → `npm test`.

6. **A coverage gate for agent-facing docs** (**S–M**; Phase 1 — executing the examples — has **shipped**, see `CLAUDE.md`'s "Executable doc examples" section). A ` ```parametric ` fence is now the per-block opt-in marker, `src/docExamples.ts` extracts those blocks from `doc/**`, and `src/docExamples.test.ts` compiles each through the real `compileParametricScript`, failing on a syntax error, a renamed op kind or field, or a block that compiles to nothing. It runs in `npm test`, so it gates CI. What is still unverified is *coverage*: nothing checks that every op kind is documented **somewhere**.

    **Phase 2 — a gate with three failure modes, not one.** The authoritative symbol list already exists and needs no new registry: `describeCapabilities()`' op catalog is exactly the set that must be documented. The gate fails on **missing** (a documented-nowhere op kind), on **stale** (a doc claiming an op kind that no longer exists — *this* is the half that catches renames, and the half most such gates omit), and on **unused-allowlist** (an opt-out entry that is now documented or no longer exported, so the escape hatch garbage-collects itself rather than rotting). Keep the allowlist a committed file with a `# reason` comment per entry so every opt-out shows up in review — the same "no silent skips" discipline `validateEditOp`'s rejections and every MCP `warnings` array already follow. `src/docExamples.ts`'s tree walk is the piece to build on; it was put in `src/` rather than under `scripts/` for exactly this reason.

    **Deliberately still NOT proposing a separate `llm-docs/` tree.** FluidCAD needs one because its MCP server is a *thin proxy with no other doc channel*; CAD-Preview already ships `describe_capabilities` as a first-class tool returning the op catalog, parameter docs, entity-id scheme, export matrix, and `verdictConventions` in one call. Duplicating that into a second hand-maintained tree would create exactly the drift this item exists to prevent.

    **One adjacent gap worth closing with it**: `npm run docs:build` — the only thing that dead-link-checks `doc/**` — runs in the separate `docs.yml` workflow (push-to-master / manual), **not** in `ci.yml`. A broken intra-doc link therefore reaches `master` before anything notices. Adding one `npm run docs:build` step to `ci.yml` is a one-line change and squarely this item's business.

    **Verification**: the gate is pure Node/TypeScript, unit-testable against a temp fixture tree (a doc covering every kind, one missing a kind, one naming a kind that does not exist), plus the gate running green over the real `doc/` tree. No WASM, no webview, no F5 caveat.

## Non-goals / known constraints

- **Writing the CAD source file** — never. The read-only invariant (sidecar persistence, export-only baking) is architectural, not a missing feature.
- **OCCT in the webview** — the kernel stays in the extension host; the webview runs only Three.js (architecture invariant).
- **G-code preview** — considered (text-to-cad ships a strong implementation: layer scrubbing, feature-type coloring, adaptive decimation) and rejected: 3D-printing-oriented, outside this extension's CAD/FEM domain.
- **URDF/SDF robotics rendering** — considered (joint articulation, FK, MoveIt2 integration in text-to-cad) and rejected for the same reason.
- **Interactive sketching with geometric constraints** — considered and rejected, not deferred. It is the single clearest "this is a modeling application now" feature, and CAD-Preview is a preview/inspect/prepare tool. More concretely: the numeric profile and curve forms are **not** a degraded mouse — they accept parametric variable expressions (`L*2`, `R*cos(i*360/N)`) that a click-to-place tool cannot express, so replacing them with drawing would trade away a distinguishing capability for a familiar one. Worth noting that SketchForge, a dedicated sketch application, still has no constraint solver either — building this would mean shipping the weak two-thirds of the feature.
- **Reference-image tracing underlay** — rejected. Its value is almost entirely to sketching, which is a non-goal above; and it would punch a hole in a real design property: every texture in the webview is a procedurally-drawn `CanvasTexture` (`geometryBuilder.ts`'s `dotTexture()`, `labelOverlay.ts`, the generated-SVG icon pipeline), a deliberately asset-free design driven by the webview's CSP. Injecting a user-supplied data-URL image trades that away for a workflow the tool doesn't have.
- **2D vector technical drawings via hidden-line removal** — **kernel-blocked, not deprioritized.** Every `HLRBRep_*` class is red in this OCCT WASM build: `HLRBRep_Algo`, `HLRBRep_PolyAlgo`, `HLRBRep_HLRToShape`, `HLRBRep_PolyHLRToShape`. `HLRAlgo_Projector` is green but is a low-level internal only reachable through them. Same class of finding as `Message_ProgressRange_1` and `Interface_Static.CVal` — recorded here so it isn't re-proposed.

  **The narrow survivor, `HLRAppli_ReflectLines`, has now been probed against the live WASM, and it is not the way in either.** The binding genuinely works — the unsuffixed constructor takes a `TopoDS_Shape`, and `SetAxes`/`Perform`/`GetResult` are all bound and functional (249 ms on `bull.stp`, returning a non-null compound this codebase's own `enumerateEdges` reads as 25 edges). It was rejected on the drawing itself, which is only visible by looking at it: rendered side by side against a tessellation-derived silhouette of the same view, `GetResult()` produced the outer boundary and a few fragments while missing the part's circular holes and interior cutout entirely. `GetResult()` returns reflect lines only; sharp feature edges live behind `GetCompoundOf3dEdges(type, …)`, whose `type` argument is an `HLRBRep_TypeOfResultingEdge` — from the entirely-red family above — so calling it throws. The one filter that would make the kernel path competitive is unreachable. **SVG silhouette export shipped anyway**, built on triangle adjacency instead (`silhouetteEdges.ts`), which additionally works for STL/OBJ/PLY/glTF sources that `HLRAppli_ReflectLines` could never have handled — see `CLAUDE.md`'s "SVG silhouette export" section. Hidden-line *drawings* remain out of reach through the B-rep kernel; an *outline* no longer is.

  **The kernel-agnostic path has now SHIPPED — `export_technical_drawing` (`src/hiddenLineRemoval.ts`), and this Non-goal is narrowed accordingly.** Everything above stays true of the *kernel* path: `HLRBRep_*` is still unavailable and `HLRAppli_ReflectLines` is still the wrong tool. What is no longer true is the conclusion. The visibility test runs on tessellated triangles and calls no OCCT hidden-line API at all, so hidden-line *drawings* — visible edges solid, occluded edges dashed — now exist for B-rep and mesh sources alike. Still out of scope, deliberately: dimensions and multi-view sheet layout (see the closed item's own Phase 2 note).

  **Superseded context, kept for the record:** The blocker above is specific to OCCT's own `HLRBRep_*` family; it says nothing about a hidden-line test built directly on the tessellated triangles this codebase already has for every source, B-rep or mesh.
