# Roadmap

Candidate features for future CAD-Preview releases, prioritized by value versus effort given what the extension already ships: an OCCT kernel, a Gmsh kernel, and a meshio++ kernel live in the extension host, a full picking/selection pipeline in the webview, a sidecar persistence model, and an MCP server mirroring the pipeline headless. Many high-value features are cheap precisely because that infrastructure exists.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has a per-feature section with the verified implementation details for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **Unlike an earlier version of this convention, an empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 1" always means the file's current 5th item, not a fossil of one that shipped.
- **Items marked *needs live-WASM verification* are listed on the strength of the binding manifest alone.** Green in `node_modules/opencascade.js/dist/Supported APIs.md` is **necessary but not sufficient** — both the STEP-unit and the IGES-writer findings started green and only resolved (one negative, one positive) under a real probe. No such item may be *estimated* until it has been probed against the live build; each one names its probe below.

Several items below were identified by comparing against [SketchForge-3D](https://github.com/Formsmith746/SketchForge-3D), a browser-based direct-manipulation CAD editor over the same OCCT kernel. Its *capability* gaps transferred well; most of its *interaction* model deliberately did not — see Non-goals.

**An item that corresponds to a GitHub issue names it inline** (e.g. *issue #36*). The issue is the request and the discussion thread; this file is the scoping — what already exists, what the real blocker is, and what the phasing should be. Where the two disagree, this file is the one that was checked against the code.

## Queued

### Tier 1 — New model-layer concepts

*Admission: adds a genuinely new concept to the document model — a new persisted entity, a new class of derived information, or a new kernel capability behind a new op kind — rather than closing a gap in an existing one. Most items here are phased so that the cheap, independently-useful phase can ship alone, and several have a phase that needs a live-WASM probe before it can be estimated.*

7. **A named, persisted construction-plane entity** (*issue #36*) (**Phases 1–3 closed**; the op-reference half remains, **M**) — see `CLAUDE.md`'s "Arbitrary clip planes derived from picked geometry" and "Named, persisted construction planes".

   **Phase 3 is CLOSED: the `plane-N` entity and its sidecar exist.** `<model>.planes.json` is the sixth sidecar, following the five existing ones' tolerant-parse shape; `set_plane` writes it headlessly, `get_state` reports it, a Planes panel saves/uses/renames/deletes and offers the numeric point+normal entry Phase 1 deliberately omitted, and it rides the preprocess archive, the dirty-buffer guard, and a sixth file watcher. The design question is settled the way it was recommended — **resolved vectors, with provenance as display-only metadata** — which keeps planes entirely out of `entityRebind.ts`, verified live: a topology-changing op that demonstrably rebinds the parts sidecar leaves the planes sidecar byte-identical.

   **What remains: ops referencing a plane id instead of inline vectors.** Deliberately deferred rather than attempted, because it would be the first cross-entity reference anywhere in the op model — every op field today is a topology id or a literal — and it needs three things with no precedent: validation that cannot check existence (`validateEditOp` is purely structural, with no document context), a dangling-reference policy, and a decision about how plane ids interact with `TOPOLOGY_CHANGING_OPS`, since unlike `face-N` they are never renumbered by replay. The storage half is useful on its own and already unblocked item 9's Phase 2 (now closed — see CLAUDE.md’s "Fitting primitives to a mesh region — Phase 2").

   **This does not reopen the sketching non-goal.** A construction plane is a *placement* for the parametric profile ops that already exist — it removes retyping, and every op it feeds still takes numeric, expression-capable fields. It adds no click-to-draw geometry and no constraint solver, which is what Non-goals rejects and why that rejection stands.

   **Two smaller findings worth recording here so they aren't rediscovered:** what AutoCAD calls a UCS is a plane *plus an in-plane frame*, and this codebase already has both conventions — `inPlaneBasis(normal, up)` (deterministic, user-anchored) and `planeBasis(axis)` (arbitrary perpendicular). `sectionSolids` currently uses the arbitrary-phase one, which is fine for a trimmed boolean result but would need `inPlaneBasis` semantics for any work plane meant to carry a stable 2D coordinate frame. And **`gp_Pln` is used nowhere in this codebase** — every face is built via the `BRepBuilderAPI_MakeFace_15(wire, true)` wire overload, so the plane overload is unprobed should a true infinite-plane primitive ever be wanted.

8. **Decompose imported geometry into parametric primitives** (*issue #34*) (**L** overall; **Phases 1 and 2 closed**, Phase 3 **L**). Feature recognition — take an imported STEP whose geometry is opaque, identify that a solid *is* a box or a cylinder, and re-express it as a primitive whose side length or radius is a named variable the user can then edit.

   **The parametric half is already complete end to end** — variables, per-op `exprs`, `resolveEditOps`, and `set_variables` (which already writes ops and variables together) all exist and would need no change. Emitting `{op: "addBox", size: [20,10,5], exprs: {"size[0]": "L"}}` alongside a `ParamVariable{name: "L", …}` is already a supported shape. **What is missing is (a) deriving primitive parameters from a B-rep at all, and (b) any way for ops to replace the source geometry rather than add to it.**

   **Phase 1 is CLOSED** — `inspect` now returns `surfaceParams` alongside `surfaceType`: a cylinder's radius and axis, a cone's signed half-angle (degrees) with its apex and reference radius, a sphere's centre and radius, a torus's major/minor radii, all in world coordinates. Every accessor was probed against the live WASM and round-tripped against known geometry, including a fillet-generated face (the case that stands in for imported STEP). See `CLAUDE.md`'s "Analytic surface parameters on `inspect`" for the full trail, including that the wrong accessor throws a bare `number` with no decoder, and that `BRepAlgoAPI_Defeaturing` was probed in the same pass and works.

   **Phase 2 is CLOSED** — `recognize_primitives` reports, per solid, the face inventory by surface type, a candidate primitive when the inventory matches a signature exactly, and the fit residual (largest deviation between the solid's real tessellated boundary and the idealized primitive, plus a bbox-diagonal-relative form). Facts only; emits no ops. Two of this item's own claims turned out wrong on inspection and are corrected in `CLAUDE.md`'s "Primitive recognition report": `collectAllEntitySignatures` was NOT the right home (no solid→faces association, and it sits on the interactive rebind path), and the residual cannot come from OCCT at all (this build has no maximum-distance query) — nor would a per-face residual mean anything, since an analytic face's tessellation nodes lie on its own surface by construction.

   **Phase 3 (L) — actually emit ops and variables.** `BRepAlgoAPI_Defeaturing` — the "remove a recognized feature" primitive this phase wants — was probed during Phase 1 and **works**: `SetShape`/`AddFaceToRemove`/`Build`/`Shape` removed a fillet and restored the exact analytic box volume, and `Build()` takes no `Message_ProgressRange` (which matters, since that class is not constructible in this build). Two structural blockers remain, neither of them a matter of effort:

   - **`AddBoxOp` has no orientation at all** — it is `{center, size}`, full stop. A recognized box that is not axis-aligned cannot be expressed as one op; it needs `addBox` + a follow-on `rotate`, or a new oriented-box op. Related trap: **`center` does not mean the same thing across primitives** — box/sphere/torus take the geometric centre, while cylinder/cone/prism/wedge take the **base** centre, so a fitted cylinder's axis location must be converted rather than passed through.
   - **Nothing in the op model can replace the base shape.** `applyEditsBRep` folds ops over `readShape(sourceFile)`; all 44 op kinds either append or operate on solids already present; there is no "empty base" concept, since `routeFile()` is a pure function of file extension computed once per document-open. Two viable shapes, both new: a new `TOPOLOGY_CHANGING` op kind that suppresses base solids (which then has to interact with `entityRebind.ts`), or **the `promote_mesh_to_brep` model — analyze, and write a brand-new file** whose content is the recognized primitives. **The export model is the recommended v1**, and for exactly the reason recorded when mesh promotion made the same call: it sidesteps in-place reclassification entirely, and the written file is an ordinary document from the moment it exists.
   - Worth noting: **no code path anywhere in this repo currently produces an expression string from geometry.** `exprs` is only ever authored by a human typing in the panel, by an agent's raw JSON, or by a hand-edited sidecar — and `parametricScript.ts` deliberately does the *opposite*, baking and stripping `exprs` after compiling. The plumbing needs no change, but this would be its first programmatic producer.

9. **Selector synthesis — persist a re-executable query instead of a positional entity id** (**L** overall; **M** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io), which faces the same topological-naming problem every history-based CAD faces and answers it in a way this codebase has not considered: **it never persists an entity reference at all.** A pick in its viewport is converted into a *source-code query expression* that re-derives the selection from scratch on every rebuild. There is no id to go stale, because there is no id.

    **This is a genuinely different answer from the one already shipped here, and it complements rather than replaces it.** CAD-Preview persists positional `face-N`/`edge-N`/`solid-N` ids and repairs them after the fact with `entityRebind.ts`'s best-effort geometric match (bbox-centre nearest-neighbour with an area/length tie-break) — a *recovery* mechanism that runs after topology changed and, by its own documented admission, "can't distinguish 'this face moved' from 'this face was deleted and a new coincidental one appeared nearby.'" A stored query is a *prevention* mechanism: it never needed to survive renumbering because it re-resolves against whatever the model currently is. The two compose — a query that resolves to exactly one entity is authoritative, and the existing rebinding stays as the fallback for a stored raw id, so nothing already persisted has to be migrated.

    **Four pieces of portable machinery, in the order they'd be built:**

    - **Build-time classification buckets.** Every op already knows, at the moment it runs, which faces it produced and what role each plays — an extrude's start cap, end cap, and side walls; a fillet's generated bands. FluidCAD records these into named buckets (`endFaces`, `sideFaces`, `capEdges`, …) and an accessor resolves against the live array. **This phase is independently valuable even if nothing else here ships**, because it is a strictly better namespace than global geometric matching for exactly the ids that drift most, and it is additive to `occtOperations.ts`'s existing per-op functions.
    - **A synthesis ladder**, tried in order and stopping at the first candidate that resolves: whole bucket → bucket plus an induced predicate → a scene-wide predicate → bucket indices. The ladder matters because the top rungs are the stable ones and the bottom rung is what today's positional ids already are, so the fallback is never worse than the status quo.
    - **Constant-free-first induction.** A greedy set-cover over candidate predicates, with restarts to escape a myopic opener, that **prefers predicates carrying no baked-in numeric constant** — `edge().line().below("xz")` beats `edge().onPlane("xz", -34.641…)` even when the latter needs fewer terms, because a qualitative/datum predicate survives the dimension edits that silently break a literal. This is the single most transferable idea in the whole approach and the one that makes stored queries meaningfully better than stored coordinates.
    - **Oracle verification.** Every candidate is *executed* before being accepted, and kept only if it resolves to exactly the picked set. This is what makes a synthesized selector trustworthy rather than plausible, and it is the same discipline this codebase already applies when it re-`inspect`s a rebound id and compares geometry rather than trusting the match.

    **One correctness gate worth carrying over verbatim: bindability.** A pick whose producing op was a pattern instance or a replayed op cannot be safely named, because the name would be ambiguous across instances — FluidCAD detects this and routes those picks to a scene-wide predicate instead. CAD-Preview has exactly this shape today (`patternLinear`/`patternCircular` append `count - 1` copies; the mesh engine tags them `pattern-{K}`), so the same check applies directly, and getting it wrong would produce a selector that silently resolves to the wrong instance — the misleading-false-result failure mode this file gates other items behind a report for.

    **Scope discipline this item must state, because it is the obvious way to get this wrong:** the query language should stay a small predicate AST persisted as JSON in the existing `.edits.json` sidecar, resolved by the same tolerant gate `validateEditOp` already is — **not** a new expression language and **not** executable code. This codebase already rejected `eval()` on CSP grounds for `paramExpr.ts` and hand-wrote a recursive-descent evaluator instead; a selector AST is the same call. It also shares a predicate vocabulary the closed query filters shipped, which is why that item should ship first and this one should reuse its vocabulary rather than inventing a second.

    **Verification**: the induction, the ladder, and the AST resolver are all pure and unit-testable headless against hand-built entity-fact fixtures (no WASM) — the oracle-verification step is what needs the live kernel, and its bar is the one `measure_exact`'s own radius path set: not "the selector resolved" but "the selector resolved to the *same* entity, confirmed by comparing `inspect`-reported geometry against the pre-edit baseline with zero delta," exactly as the closed entity-rebinding work already verifies itself in `npm run mcp:smoke`.

10. **Cheap thin-wrapper ops mined from FluidCAD** (**S–M** for the set; each independently **S**). *Every one of these **needs live-WASM verification** of its overload suffix before it can be estimated*, per this file's own rule — they are listed together because each is a handful of lines over an OCCT class this build already exposes, not because they should ship as one change.

    - **Distance-angle chamfer.** `chamfer` currently takes one `distance`. FluidCAD gets the asymmetric and distance-angle variants from the *same* `BRepFilletAPI_MakeChamfer` instance this codebase already constructs, via `.Add(d1, d2, edge, face)` and `.AddDA(d, angleRad, edge, face)` beside the `.Add_2(amount, edge)` already in use. **Correction, from reading the code rather than estimating: this is NOT roughly three lines.** Both `.Add(d1, d2, edge, face)` and `.AddDA(d, angleRad, edge, face)` take a reference `TopoDS_Face` that the current call site never has — `filletEdges` resolves **edges** only (`collectEdges`), and there is no edge→adjacent-face helper anywhere in `occtOperations.ts`. Building that adjacency is the real cost of this item.
    - **`shell().join(...)` styles.** `BRepOffsetAPI_MakeThickSolid`'s join mode is already passed as `GeomAbs_JoinType.GeomAbs_Arc` in the verified 9-argument call recorded in `CLAUDE.md`; exposing intersection/tangent as an option is a parameter, not a new API.
    - **`draft(angle, faces)`** via `BRepOffsetAPI_DraftAngle`. Note explicitly that FluidCAD's implementation auto-derives the neutral plane from the bounding box's min-Z face with a hardcoded +Z direction — a real limitation to *improve on rather than copy*, since this codebase already has `facePlane` and, since item 7's Phase 2 closed, a way to derive a plane from a picked face.
    - **Construction geometry (`.guide()`).** A boolean flag on any 2D profile/curve op marking it reference-only: rendered, pickable, excluded from profile resolution. Trivial, and it pairs with the wireframe build ops already shipped.
    - **Inscribed-vs-circumscribed polygons**, **a slot built around an existing edge** rather than from length+radius, and **midplane/midaxis references** (a plane halfway between two planes, an axis halfway between two axes) — each a small addition to an existing op family.

    **Verification**: each op follows the established pattern — a probe against the live WASM to pin the overload suffix (this file's standing requirement, and `CLAUDE.md` records dozens of precedents), then round-trip coverage in `npm run mcp:smoke` asserting the produced geometry matches an analytically-known value, the bar `addCylinder`/`measure_exact` already set.

11. **Substantial new feature ops mined from FluidCAD** (**L**, phased; not estimable per-op until probed). The genuinely large capabilities, listed so the opportunity is on record with an honest size attached rather than mistaken for the cheap set above. Each is ~400–1200 lines of real geometry work in the source project, **not** a wrapper: **`wrap()`** (true surface *development* of a flat sketch onto a cylinder or cone — length-preserving, not projection — then thickening along the surface normal, with emboss/engrave/standalone variants; the most original capability in that codebase); **`rib()`** (build a rib from an *open* spine sketch, extruded until it meets surrounding solids, with end-blending into adjacent walls); **`.thin(offset)` across the whole sweep family** (thin-walled solids directly from an open or closed profile, with dual offsets); **loft `.guides()` plus `.startCondition`/`.endCondition`** (guide rails the surface must ride, and normal/tangent takeoff with a signed magnitude — a real quality jump over plain `ThruSections`, which is what this codebase currently uses); **extrude/cut up-to-a-face terminators** (`extrude(face)`, or first/last intersecting face found by filter — the "up to next" every mainstream CAD has); and **`.pick(regions)` + `.drill()`** for choosing which enclosed regions of a multi-region sketch a feature consumes.

    **Where CAD-Preview is already ahead, recorded so this item is read as a gap list and not a scoreboard**: FluidCAD has **no** assemblies, mates, or joints (its `part()` is a fusion-isolation namespace with a name, nothing more), no box/cone/torus primitives, no variable-radius or face fillet, no pattern-along-path, no interference detection, no model comparison, no mesh health or mesh→B-rep promotion, no format breadth beyond STEP/STL/BRep, and essentially no validation or manufacturability analysis. Several of those are shipped capabilities here. The transfer is one-directional for this item only.

    **Sequencing**: nothing here blocks anything else in this file, and each op is independently shippable. If any single one is picked up first, `.thin()` is the recommendation — it applies to five existing ops at once rather than adding a sixth.

### Tier 2 — Externally gated

*Admission: the work is understood and scoped, but is blocked on a decision or an event outside this repository — a license choice, an upstream merge, or a dependency that does not yet exist. Listed so the blocker is on record and re-scoping is unnecessary when it clears; **not** estimable until it does.*

12. **Open OpenSCAD (`.scad` / `.csg`) files** (*issue #35*) (**M** for the recommended path; **L** and license-affecting for the maximal one).

   Three genuinely distinct approaches, in ascending cost. **The recommendation is (a) plus (b); (c) should not be chosen by default.**

   - **(a) Parse `.csg` only — no new dependency, no license change.** OpenSCAD's `.csg` export is *the fully evaluated model*: loops unrolled, modules inlined, variables literalised, `if` branches collapsed, every transform emitted as an explicit 4×4 `multmatrix`. **There is therefore no language to implement** — FreeCAD's own `.csg` lexer has 33 reserved words and no arithmetic, no `if`/`for`, no variables, because none survive into the format. Most nodes (`cube`, `sphere`, `cylinder`, `polyhedron`, `union`, `difference`, `intersection`, `group`, `multmatrix`) map directly onto primitives and booleans this codebase already has, with graceful degradation on the rest — the same convention every unresolvable operand in this codebase already follows.
   - **(b) Shell out to a user-installed `openscad` binary** for `.scad` → `.csg`, then (a). Still zero bundled megabytes and **no license propagation — a separate process is mere aggregation, not linking**. Degrades to a clear `supported: false` when the binary is absent, structurally identical to how `render_snapshot` already handles a missing Playwright. This is precisely FreeCAD's own architecture.
   - **(c) Bundle `openscad-wasm`.** Technically attractive: it is under the official `openscad` GitHub org, actively committed to, ships a dedicated **Node** build, needs no `SharedArrayBuffer`, and drives through an Emscripten MEMFS plus a literal `callMain(argv)` — structurally identical to how this codebase already drives Gmsh. **But it costs roughly 8–14 MB uncompressed (plus ~8 MB more if `text()` is ever to work), and it permanently upgrades the shipped `.vsix` to GPL-3.0-or-later.** CGAL is GPLv3+/LGPLv3+ with no GPLv2 option, and Manifold is Apache-2.0, which the FSF holds GPLv2-incompatible; OpenSCAD's own playground documents shipping its build as GPLv3 for exactly these reasons. **This is not a conflict for a GPL-2.0-*or-later* project** — the "or later" grant is precisely the escape hatch — **but it is a one-way door, and it would be the first bundled dependency to force it** (gmsh-wasm is GPL-2.0-or-later and OCCT is LGPL-2.1-with-exception; both are GPLv2-compatible today, and so is fTetWild's own MPL-2.0 — see `CLAUDE.md`'s "fTetWild robust volume meshing" section, which also closed the "Robust volumetric meshing from a skin mesh" item this note used to cross-reference, by a route that needed no MMG/GPLv3 decision at all).

   **One correctness decision must be settled before any option, and getting it wrong reproduces the same misleading-false-result failure mode item 8 describes.** **OpenSCAD's `cylinder` is a faceted prism, not an analytic cylinder.** `$fn`/`$fa`/`$fs` survive into `.csg`, and the common default `$fn = 0` means *unresolved* — the consumer must reimplement OpenSCAD's own segment-count rule from `$fa`/`$fs`. Mapping a `$fn = 10` cylinder onto an exact `BRepPrimAPI_MakeCylinder` yields a solid that silently disagrees with OpenSCAD's own STL by the chord error, and `get_mass_properties`/`measure_exact` would then report confidently-wrong numbers. FreeCAD's answer is an explicit dial — a `useMaxFN` preference (default 16: below it build the real polygon, above it treat as circular) — worth copying, though note its default silently favours exactness over fidelity.

   **Other limits to record now rather than discover later:** `.csg` prints at default stream precision (~6 significant figures), a hard accuracy ceiling on anything reconstructed from it, and rigid transforms come back with float noise (`rotate([90,0,0])` → `2.22045e-16`), so exact axis alignment must be recovered with a tolerance. A `multmatrix` is **not** guaranteed rigid, since `scale`/`mirror` collapse into it. Module names are destroyed — every user module becomes an anonymous `group()`. `hull` and `minkowski` have no OCCT equivalent at all (FreeCAD round-trips them through the binary and accepts triangles). `text()` carries a font *name*, not outlines — and the official WASM build ships with "no support for fonts". `import`/`surface` reference external files, so `.csg` is evaluated but not self-contained. And the format is documented poorly, versioned inconsistently, and framed by its own man page as "mainly used for debugging and testing" — treat it as a de-facto format with no stability guarantee.

   **Ruled out, with evidence: writing a JavaScript OpenSCAD evaluator.** Every prior attempt is dead — the JSCAD translator is deprecated and *its own designated successor is also deprecated* — the one live from-scratch effort is Rust with acknowledged silent divergences from the reference implementation, and OpenSCAD's `$`-variable **dynamic** scoping alongside ordinary lexical scoping is a documented design landmine that upstream contributors themselves call one of the language's worst mistakes. Upstream also closed its own bytecode-interpreter rewrite as not planned. This is the same "shipping the weak two-thirds of the feature" reasoning that rejected a constraint solver in Non-goals.

13. **Native 6-DOF (SpaceMouse-class) input for the viewport** (**M–L**, externally gated on a native-module packaging decision). Comparing against [SindriCAD](https://github.com/MakerViking/sindricad): its Rust layer (`src-tauri/src/spacemouse.rs`) reads a 3Dconnexion SpaceMouse via raw HID (its webview has no WebHID access under WebKitGTK on Linux), ranking candidate devices by **HID usage page/usage** (Generic Desktop / Multi-axis Controller, `0x01`/`0x08`) rather than vendor-ID allowlisting — fixed this way after a vendor-only match once misidentified an ordinary Logitech mouse as a SpaceMouse and fed its motion into the 3D camera.

    **The constraint that forced SindriCAD's Rust-side workaround doesn't apply to CAD-Preview's own layer split, which changes where this would live.** A VS Code webview has no WebHID either (the same browser-sandbox gap), but CAD-Preview's **extension host** is a plain Node.js process, not a browser sandbox — the same process that already runs OCCT/Gmsh/meshio++ WASM. A native HID addon could in principle read the device there and pipe motion deltas to the webview over the existing `postMessage` channel (`Viewer.orbit`/`pan`/`dolly`, already exposed and unit-tested in `cameraControls.ts`), mirroring the OCCT-in-host/Three.js-in-webview split this codebase already has, with no Tauri-style native shell needed.

    **What actually gates this, and why it is externally gated rather than a routine dependency bump**: every WASM dependency this codebase bundles today (OCCT, Gmsh, meshio++) is architecture-independent by construction — one `.wasm` file runs on any host CPU/OS. A native HID addon is not: it needs a prebuilt binary per OS/CPU-arch combination the `.vsix` targets, a real packaging model change (platform-specific `.vsix` publishing, which this extension doesn't use today) versus the current single universal package. That's a decision to make deliberately, not a probe to run — hence Tier 2, alongside the OpenSCAD and MMG items' own license-gated packaging decisions, rather than a routine dependency bump.

    **If ever built, the one concrete technical lesson worth carrying over verbatim**: device discovery by HID usage-page/usage, not vendor ID — the exact bug SindriCAD's own comment records hitting once.

### Tier 3 — Documentation and onboarding

*Admission: closes a gap in how the extension explains itself — to a new user, a contributor, or an agent — with no kernel/webview/MCP capability change; the deliverable is `doc/**` content plus, at most, the tests and CI gates that keep it honest. Ranked last because nothing here blocks or is blocked by the feature tiers above, not because it is low-value.*

14. **Narrative, screenshot-illustrated tutorials — a FluidCAD-style gallery** (**M** overall; **S** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io)'s `docs/tutorials/` (13 pages, each building one real part through numbered `Step N` sections — Setup → Steps → Full code → "What you practiced" — with a screenshot after nearly every step): `doc/getting-started.md` is already a large, thorough **reference** (one section per UI panel, with tables and screenshots) but has nothing **narrative** — no single page walks a reader through building one real part end to end. `doc/mcp-server.md`'s one bolt-circle example is the closest thing to a worked example this repo has today, and it's a single JSON snippet, not a tutorial.

    **The one real structural mismatch, and how to design around it rather than fight it.** FluidCAD tutorials start from an empty code file; CAD-Preview has no such thing — `CustomReadonlyEditorProvider` only ever opens an *existing* CAD file, every creation op **appends** to whatever solids are already present, and there is no "delete body" op. The fix is not a new capability, just a naming convention: start every tutorial from `examples/STP/block.stp`, a real, tiny (3×4×5 mm) seed solid already shipped in the repo, and make the tutorial's first added primitive fully enclose the seed's bounding box — two separate, non-unioned solids in the same compound still z-buffer-occlude correctly, so the seed is genuinely invisible in every subsequent shaded render with no extra op needed (confirmed against the live WASM: the seed always stays its own separate `solid-0` group in the compound — creation ops append, they never fuse). Worth stating once, briefly, in the tutorials themselves as a real, useful CAD-Preview technique for working around the append-only model, not hidden as a trick.

    **Phase 1 (S) — the pages and cross-linking, using only existing screenshots plus text/JSON.** A new `doc/tutorials/` section (an index/gallery page + one page per tutorial, wired into `doc/.vitepress/config.mts`'s `nav`/`sidebar` alongside the existing `User Guide` group), each page following FluidCAD's proven shape adapted to this tool: H1 + intro ("covers X, Y, Z"), a **Starting point** section naming the seed file, numbered `## Step N` sections (concrete UI actions in the same "1. … 2. … 3." mini-procedure style `getting-started.md` already uses throughout), a closing **Full operation list** section (the cumulative op-JSON array — doubles as a literal `apply_edit_ops`/`run_parametric_script` payload, reinforcing that the interactive UI and MCP are two views of the same op model), and a **What you practiced** recap. Five concrete candidates, chosen to cover the feature breadth with minimal overlap: a **Bracket** (primitives + fillet + counterbore holes — the closest analog to a FluidCAD "first tutorial"); a **Parametric bolt-circle flange** (variables + circular pattern, plus a pattern-the-tool-then-subtract technique for "patterning a hole" — there is no direct op support for patterning a cut feature, only for solids, so this is worth a doc callout on its own); a **Sketch/extrude/shell enclosure** (2D profile sketch → extrude → shell, the one whole workflow family with zero narrative coverage today); **Prepare and mesh a part for FEA** (Parts + FE Mesh + Kratos MDPA export — this extension's actual raison d'être, not just a features tour); and **Model with an AI agent via MCP** (a narrated `mcp-server.md`-style conversation that builds the *same* bracket as the first tutorial, reusing its screenshots with a "built by an agent instead of by hand, identical result" framing — needs no new fixtures at all). This phase alone — reusing existing `doc/public/screenshots/*.png` wherever a step already matches a shot panel, text/JSON elsewhere — already closes the narrative gap with zero pipeline risk.

    **Phase 2 (S–M) — real per-step screenshots through the existing pipeline, not hand-drawn**, per `CLAUDE.md`'s standing "screenshots are generated, never hand-captured" rule. Investigated in detail, not just assumed: `scripts/screenshots/fixtures-entry.ts` currently produces one *global* fixture set from `bull.stp` with no per-shot parametrization, and `capture.mjs`'s `SHOTS` array is a hand-written `{file, setup(page), target}` list — both additive-friendly (no rewrite needed) but genuinely new work. `fixtures-entry.ts` needs extending to call the already-4-parameter `loadBRep(extensionPath, bytes, "step", ops)` with real, cumulative `EditOp[]` arrays per tutorial step; every op's `targets`/`edges`/`profile` ids must be resolved against the *actual* group/edge/face ids `loadBRep` returns for that step, not guessed — a throwaway probe script following this codebase's own established "brute-force probe against the live WASM" convention is the way to get them, exactly as `CLAUDE.md` records doing dozens of times elsewhere for OCCT overload discovery. `capture.mjs` then needs roughly 10 new, purely-additive `SHOTS` entries (flat filenames, matching the existing 100%-flat `doc/public/screenshots/` convention — no subfolder, since only that one directory is ever `mkdirSync`'d today), reusing `populate()`'s exact `geometry → {type:"viewState", view:null} → sleep → tree → sleep` ordering (`CLAUDE.md`'s own documented load-bearing sequence for correct camera framing on first load — skipping the `viewState` post is the exact regression it records happening once already). Playwright 1.62.1 with a matching cached Chromium (revision 1234) are already installed in this dev environment, so the pipeline is runnable here, not just in theory.

    **Verification, stated per this file's own standard**: `npm run build` (the fixture-generator additions type-check) → `npm run docs:screenshots` → **visually inspect every new PNG via the `Read` tool**, not just check the exit code (`CLAUDE.md` records a real, exit-0-but-silently-broken screenshot regression from skipping exactly this once already) → `npm run docs:build` (VitePress's dead-link checker covers the new nav/sidebar/cross-links) → `npm test` as a cheap sanity check that nothing under `src/` was touched. Phase 1 needs none of the WASM/Playwright verification above — it is markdown and nav-config only.

    **Sequencing note**: the op-JSON in each tutorial's "Full operation list" is exactly the kind of block the doc-examples coverage-gate item's executable-examples test would run, so writing these pages in the fenced language that item defines costs nothing now and makes every tutorial self-verifying later.

15. **Executable doc examples, and a coverage gate for agent-facing docs** (**M** overall; **S** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io), which maintains a parallel `llm-docs/` tree — one terse markdown file per API symbol plus a handful of concept notes — that its MCP server serves at runtime, and which is held to the real API by two CI gates. CAD-Preview's agent-facing documentation is `describe_capabilities()`' generated output plus hand-written prose in `doc/mcp-server.md`, and **nothing checks either against the code**: `OP_PARAM_DOCS` (`mcpTools.ts`) is already locked to the live op catalog by `mcpTools.test.ts`, but the prose, the parameter examples, and every JSON snippet in `doc/**` are unverified — a renamed field or a dropped op kind would leave a confidently-wrong example in place with every test still green.

    **Phase 1 (S) — execute the examples. This is the cheap half, and it is cheaper here than in the project it comes from.** FluidCAD runs every fenced example block through `new Function` against its real runtime, which works but means the docs execute arbitrary JavaScript. CAD-Preview's `run_parametric_script` format is **declarative with no code execution at all** — a `{variables?, steps}` document compiled by `parametricScript.ts`, which is already pure, already unit-tested, and already needs no WASM to compile. So a vitest case that walks `doc/**/*.md`, extracts every ```` ```parametric ```` fenced block, and asserts each one **compiles with zero rejected steps** is a small, fully-headless test with no sandboxing question to answer. Adopt FluidCAD's **fenced-language-as-opt-in marker** convention exactly: ```` ```json ```` blocks stay illustrative and are ignored, only the dedicated language tag is executed, so an author opts a block in per-block rather than having every code block in the docs become a test. Catches the three documented rot classes — a syntax error in an example, an example naming an op kind or field that no longer exists, and a block that compiles but produces nothing.

    **Phase 2 (S–M) — a coverage gate with three failure modes, not one.** The authoritative symbol list already exists and needs no new registry: `describeCapabilities()`' op catalog is exactly the set of things that must be documented. The gate fails on **missing** (a documented-nowhere op kind), on **stale** (a doc claiming an op kind that no longer exists — *this* is the one that catches renames, and it is the half most such gates omit), and on **unused-allowlist** (an opt-out entry that is now documented or no longer exported, so the escape hatch garbage-collects itself rather than rotting). Keep the allowlist a committed file with a `# reason` comment per entry, so every opt-out shows up in review — this codebase already applies the same "no silent skips" discipline to `validateEditOp`'s rejections and to every `warnings` array in the MCP surface.

    **Deliberately NOT proposing a separate `llm-docs/` tree.** FluidCAD needs one because its MCP server is a *thin proxy with no other doc channel*; CAD-Preview already ships `describe_capabilities` as a first-class tool that returns the op catalog, parameter docs, entity-id scheme, export matrix, and `verdictConventions` in one call. Duplicating that into a second hand-maintained tree would create exactly the drift this item exists to prevent. The gap is verification of what already exists, not a new surface — which is why this is Tier 3 and **S–M**, not a new-capability item.

    **Verification**: the extractor and the gate are both pure Node/TypeScript, unit-testable with a temp fixture tree (a doc with a good block, one with a bad block, one claiming a nonexistent op kind), plus the gate itself running green over the real `doc/` tree. No WASM, no webview, no F5 caveat — the first item in this file with no verification gap at all.

## Non-goals / known constraints

- **Writing the CAD source file** — never. The read-only invariant (sidecar persistence, export-only baking) is architectural, not a missing feature.
- **OCCT in the webview** — the kernel stays in the extension host; the webview runs only Three.js (architecture invariant).
- **G-code preview** — considered (text-to-cad ships a strong implementation: layer scrubbing, feature-type coloring, adaptive decimation) and rejected: 3D-printing-oriented, outside this extension's CAD/FEM domain.
- **URDF/SDF robotics rendering** — considered (joint articulation, FK, MoveIt2 integration in text-to-cad) and rejected for the same reason.
- **Interactive sketching with geometric constraints** — considered and rejected, not deferred. It is the single clearest "this is a modeling application now" feature, and CAD-Preview is a preview/inspect/prepare tool. More concretely: the numeric profile and curve forms are **not** a degraded mouse — they accept parametric variable expressions (`L*2`, `R*cos(i*360/N)`) that a click-to-place tool cannot express, so replacing them with drawing would trade away a distinguishing capability for a familiar one. Worth noting that SketchForge, a dedicated sketch application, still has no constraint solver either — building this would mean shipping the weak two-thirds of the feature.
- **Reference-image tracing underlay** — rejected. Its value is almost entirely to sketching, which is a non-goal above; and it would punch a hole in a real design property: every texture in the webview is a procedurally-drawn `CanvasTexture` (`geometryBuilder.ts`'s `dotTexture()`, `labelOverlay.ts`, the generated-SVG icon pipeline), a deliberately asset-free design driven by the webview's CSP. Injecting a user-supplied data-URL image trades that away for a workflow the tool doesn't have.
- **2D vector technical drawings via hidden-line removal** — **kernel-blocked, not deprioritized.** Every `HLRBRep_*` class is red in this OCCT WASM build: `HLRBRep_Algo`, `HLRBRep_PolyAlgo`, `HLRBRep_HLRToShape`, `HLRBRep_PolyHLRToShape`. `HLRAlgo_Projector` is green but is a low-level internal only reachable through them. Same class of finding as `Message_ProgressRange_1` and `Interface_Static.CVal` — recorded here so it isn't re-proposed.

  **The narrow survivor, `HLRAppli_ReflectLines`, has now been probed against the live WASM, and it is not the way in either.** The binding genuinely works — the unsuffixed constructor takes a `TopoDS_Shape`, and `SetAxes`/`Perform`/`GetResult` are all bound and functional (249 ms on `bull.stp`, returning a non-null compound this codebase's own `enumerateEdges` reads as 25 edges). It was rejected on the drawing itself, which is only visible by looking at it: rendered side by side against a tessellation-derived silhouette of the same view, `GetResult()` produced the outer boundary and a few fragments while missing the part's circular holes and interior cutout entirely. `GetResult()` returns reflect lines only; sharp feature edges live behind `GetCompoundOf3dEdges(type, …)`, whose `type` argument is an `HLRBRep_TypeOfResultingEdge` — from the entirely-red family above — so calling it throws. The one filter that would make the kernel path competitive is unreachable. **SVG silhouette export shipped anyway**, built on triangle adjacency instead (`silhouetteEdges.ts`), which additionally works for STL/OBJ/PLY/glTF sources that `HLRAppli_ReflectLines` could never have handled — see `CLAUDE.md`'s "SVG silhouette export" section. Hidden-line *drawings* remain out of reach through the B-rep kernel; an *outline* no longer is.

  **The kernel-agnostic path has now SHIPPED — `export_technical_drawing` (`src/hiddenLineRemoval.ts`), and this Non-goal is narrowed accordingly.** Everything above stays true of the *kernel* path: `HLRBRep_*` is still unavailable and `HLRAppli_ReflectLines` is still the wrong tool. What is no longer true is the conclusion. The visibility test runs on tessellated triangles and calls no OCCT hidden-line API at all, so hidden-line *drawings* — visible edges solid, occluded edges dashed — now exist for B-rep and mesh sources alike. Still out of scope, deliberately: dimensions and multi-view sheet layout (see the closed item's own Phase 2 note).

  **Superseded context, kept for the record:** The blocker above is specific to OCCT's own `HLRBRep_*` family; it says nothing about a hidden-line test built directly on the tessellated triangles this codebase already has for every source, B-rep or mesh. A local sibling project, HCAD, independently ships exactly that: a grid-bucketed per-edge visibility test with no B-rep HLR call anywhere in it. This doesn't change anything above — the B-rep kernel path is still dead, for the reasons already recorded — but it means hidden-line *drawings*, not just an outline, are no longer permanently out of reach either; they're queued, not ruled out.
- **3D text, engraving, and embossing** — **kernel-blocked.** `Font_BRepFont` and `Font_BRepTextBuilder` are both red in this build, so there is no path from a glyph to a `TopoDS_Shape`.
- **Parametric part generators (gears, threads, springs)** — rejected. Standard parts are something this tool should *source*, not *author*: `search_standard_parts`/`download_standard_part` already fetch real, verified geometry from step.parts as ordinary STEP files the existing pipeline opens (and, since the closed "Standard-parts browse and insert panel" item, so does the interactive sidebar). Authoring involute gear profiles is modeling-application scope.
