# Roadmap

Candidate features for future CAD-Preview releases, prioritized by value versus effort given what the extension already ships: an OCCT kernel, a Gmsh kernel, and a meshio++ kernel live in the extension host, a full picking/selection pipeline in the webview, a sidecar persistence model, and an MCP server mirroring the pipeline headless. Many high-value features are cheap precisely because that infrastructure exists.

This page is aspirational, not a commitment — items may be re-ordered, re-scoped, or dropped. Effort is a rough order of magnitude: **S** (a day or two), **M** (roughly a week), **L** (multi-week).

Everything previously shipped is tracked in `CHANGELOG.md`, and `CLAUDE.md` has a per-feature section with the verified implementation details for anything currently in the codebase — this page is for what's **not** built yet, only.

## How this file works

- **Tiers are ordered, and the order is the recommendation.** Each tier states an *admission criterion*; an item that doesn't meet it belongs in a different tier or in Non-goals, not at the top because it sounds exciting. **Unlike an earlier version of this convention, an empty tier is removed from the file entirely, not kept as a placeholder** — if a new item shows up later that needs a tier no longer listed here (e.g. a defect-shaped correctness/robustness finding, which is always top priority regardless of effort size), recreate that tier at the top rather than burying it under whatever tier happens to be listed first at the time.
- **A closed item is removed from this list entirely**, not struck through — its write-up moves to `CLAUDE.md` (a per-feature section with the verified implementation details) and its history stays in git. Numbering is renumbered to stay consecutive whenever an item closes, so a reference like "item 1" always means the file's current 5th item, not a fossil of one that shipped.
- **Items marked *needs live-WASM verification* are listed on the strength of the binding manifest alone.** Green in `node_modules/opencascade.js/dist/Supported APIs.md` is **necessary but not sufficient** — both the STEP-unit and the IGES-writer findings started green and only resolved (one negative, one positive) under a real probe. No such item may be *estimated* until it has been probed against the live build; each one names its probe below.

Several items below were identified by comparing against [SketchForge-3D](https://github.com/Formsmith746/SketchForge-3D), a browser-based direct-manipulation CAD editor over the same OCCT kernel. Its *capability* gaps transferred well; most of its *interaction* model deliberately did not — see Non-goals.

**An item that corresponds to a GitHub issue names it inline** (e.g. *issue #36*). The issue is the request and the discussion thread; this file is the scoping — what already exists, what the real blocker is, and what the phasing should be. Where the two disagree, this file is the one that was checked against the code.

## Queued

### Tier 2 — Webview-only interaction depth

*Admission: closes an interaction gap using capabilities the pipeline already has, with **no** new kernel surface — no new OCCT/Gmsh/meshio++ call, no new persisted geometry, no new MCP tool. An item here may add a host↔webview protocol message over an *existing* pipeline function (an interactive readout of something only the host can compute), but never a new kernel capability. The cost is concentrated in the webview, not in a WASM binding, so nothing here is gated on a live-WASM probe — and correspondingly, most of it carries the standing F5-only verification caveat.*

1. **Split view — multiple synchronized viewports over one document** (*issue #37*) (**S, optional** for Phase 3). A layout picker that draws the *same* scene from several cameras at once — the classic CAD quad view. **Phases 1 and 2 shipped** — Phase 1: a 1×1 ⇄ 2×2 toggle in View ▾ (per-pane cameras/orbit/projection, pane-routed picking, focused-pane concept, single renderer/canvas preserved via scissored viewports — see CLAUDE.md's "Split view" section for the verified implementation details, including the two three.js findings that shaped it: `TransformControls` has native sub-viewport pointer support in three@0.185 while `OrbitControls` has none and needs speed compensation); Phase 2: a real layout picker (`1×1`/`1×2`/`2×1`/`2×2` — the `1×2` variants add a half-width/half-height tiling, which is also when the OrbitControls speed compensation stops being exact: a half-width pane needs different pan-x vs pan-y factors than one `panSpeed` can express, per the CLAUDE.md write-up) plus `.view.json` persistence (optional `layout` + per-pane `panes` array beside the existing `view`, purely additive so older sidecars still restore sensibly). What remains:

   - **Phase 3 (S, optional)** — linked cameras across two tabs via a host relay + session registry: two webviews cannot talk to each other, and `provider.ts` currently tracks only `activeSession` (a single "which tab has focus" field, assigned on `onDidChangeViewState`), not a registry of every open session. The relay's real cost is that registry plus a decision about what "linked" means when the two documents have different extents.

   **The standing constraints Phase 1 already settled, recorded so later phases don't relitigate them:** exactly one `WebGLRenderer` and one canvas (panes are scissored viewports — `renderGizmo()`'s existing overlay technique generalized); **a fresh viewer must always default to 1×1** (the headless `renderService.ts` harness posts no layout message and must keep getting one full-canvas view); the markup overlay stays whole-canvas and screenshots capture the whole grid (the roadmap's stated readings); only camera state is per-pane — display mode, clip plane, colours, part visibility, overlays, and selection stay global; and the clip-cap's stencil isolation comes free from per-pane scissored clears (probed, not assumed — see CLAUDE.md).

   - **This is deliberately *not* "open two models side by side" — that already works today, with zero code.** `provider.ts`'s `resolveCustomEditor` has no per-provider document singleton (every document gets its own closure and its own webview page; `activeSession` is only a "which tab has focus" router for keybindings), and VS Code's own split-editor UI already puts two CAD tabs next to each other. This was investigated and recorded when Model comparison shipped — see `CLAUDE.md`'s "Model comparison" section. What does *not* exist is **more than one camera onto one scene**, which is what this item adds.
   - **The one genuinely-new cross-document variant, if it's wanted, is a separate and much smaller sub-feature: linked cameras across two tabs.** Two webviews cannot talk to each other, so it needs a host relay — and `provider.ts` currently tracks only `activeSession` (a single field, assigned on `onDidChangeViewState`), not a registry of every open session, so the relay's real cost is that registry plus a decision about what "linked" means when the two documents have different extents. Worth listing as Phase 3 below, not folding into the main item.

   **The non-negotiable constraint, already on record: exactly one `WebGLRenderer` and one canvas.** `orientationCube.ts`'s own doc comment records that a second WebGL context fails in some environments — that is an existing finding, not a fresh worry, and it is why the gizmo owns no renderer of its own. So panes must be `setViewport`/`setScissor`/`setScissorTest` regions of the single renderer. **This technique is already proven in-repo:** `Viewer.renderGizmo()` does exactly that today, including the `autoClear = false` + `clearDepth()` discipline needed to overlay a second render into a sub-rect without wiping the frame. Multi-viewport is a generalization of a loop that already runs every frame, not a new rendering strategy.

   **Where the effort actually is: `Viewer`'s single-camera and single-rect assumptions**, spread across a ~1500-line class. Each of these is a specific, known site, not a guess:

   - **Cameras.** `activeCamera` is one field (over the `camera`/`orthoCamera` pair the Persp/Ortho toggle swaps between), and `frame()`/`resetView()`/`setViewDirection()`/`orbit`/`pan`/`dolly` all read it. Per-pane means N of those pairs, plus a definition of "the focused pane" for every API that still takes no pane argument.
   - **Orbit input.** `OrbitControls` is constructed against `renderer.domElement` and cannot tell which pane the pointer is in — it would drive every pane at once. Two viable routes: N `OrbitControls` instances with `enabled` gated by hit-testing the pointer against the pane rect on `pointerdown`, or per-pane use of the **already-existing, already-unit-tested pure `cameraControls.ts`** (`orbit`/`pan`/`dolly`/`setDirection`), which the stepped view-control buttons already delegate to. The second route is more code but sidesteps N sets of damping state each calling `controls.update()` every frame.
   - **Picking.** `onSelectPointerUp` builds NDC from `renderer.domElement.getBoundingClientRect()` and raycasts with `activeCamera`; both must become pane-relative. Same for `onGizmoPointerDown`'s corner hit-test — decide whether every pane gets its own orientation cube or only the focused one.
   - **The transform gizmo.** `TransformControls` is likewise constructed against `activeCamera` + `domElement`. Its `.camera` is a genuinely reassignable accessor (verified against the installed three.js source when the gizmo shipped — see `CLAUDE.md`'s "Transform gizmo" section), so retargeting it to the focused pane is cheap; what needs a decision is a drag begun in one pane while the pointer crosses into another.
   - **Resize.** `onResize` sets one aspect on both cameras from `container.clientWidth/Height` and calls `renderer.setSize`. Per-pane aspect comes from the pane's own rect, and the orthographic `left`/`right` derive from `orthoHalfHeight * aspect`, so each pane's ortho frustum is independent.
   - **Per-frame camera-derived scaling.** The measurement label is rescaled every frame from `activeCamera` (distance under perspective, frustum height under ortho) to hold a constant on-screen size — with N cameras there is no single correct scale for one shared sprite. `pickThreshold`/`pointSpriteScale` are model-radius-derived in `frame()` and are camera-independent, so they are unaffected.

   **Highest-risk unknown, worth probing before committing to the estimate: the clip cap and the stencil buffer.** `clipCap.ts` marks the cut face by rendering boundary geometry into the **stencil** buffer, and the renderer is constructed with `stencil: true` precisely for it. Per-pane rendering under `setScissorTest(true)` needs the stencil cleared per pane, and `renderGizmo`'s existing overlay pattern clears **depth only**. This matters more than the usual unknown because the documented failure mode is *silent* — get the stencil state wrong and the model simply renders uncapped/hollow with no error anywhere. Probe: a clipped model in a 2×2 layout, checked visually in all four panes.

   **Two shared-surface decisions that are scoping choices, not bugs:**

   - **The markup overlay is one `<canvas>` absolutely positioned over the whole `#app`**, and its strokes are screen-space pixels with no pane awareness. Treating markup as whole-canvas (spanning panes) is the simpler and arguably more correct reading of a screen-space review annotation; per-pane markup would need the stroke model to carry a pane id.
   - **Screenshots capture the whole canvas.** `captureScreenshotBase64` reads `renderer.domElement`, so a split-mode screenshot is the whole grid — fine, and probably desirable, interactively. But `renderService.ts`'s headless harness drives the **same** `Viewer` through `renderViewRequest` and expects one framed view per call, so **single-pane must remain the default state** of a freshly-created viewer; the harness posts no layout message and must keep getting 1×1.

   **Persistence needs an additive `.view.json` extension, not a rewrite.** `ViewState` is exactly one camera's state (`viewDirection`/`cameraUp`/`orthographic`/`displayMode`/`clip`) at `VIEW_STATE_SIDECAR_VERSION` 1. The natural shape keeps `view` as the focused/single-pane state — so a sidecar written by a split-aware build still restores sensibly in a build without it, and vice versa — and adds an optional `layout` plus a per-pane array beside it. Per this codebase's tolerant-parse convention, purely additive optional fields need no version bump; changing what `view` *means* would. The five per-document file watchers already reconcile `.view.json` on external change, and that path has to keep working.

   **The strongest scoping recommendation, and the thing that keeps this L rather than XL: only camera state is per-pane.** There are roughly a hundred `viewer.*` references in `main.ts`, essentially all written against a single implicit "the view". The large majority are display or document state — display mode, clip plane, colours, part visibility, the FE-mesh/worst-element/colour-field overlays, selection highlight — which are genuinely global to the document and should *stay* global. Only direction/up/ortho/zoom become per-pane in v1. Making display mode or clipping per-pane multiplies the surface for little gain and should be an explicit follow-up, if ever.

   **Suggested phasing:**

   1. **Phase 1 (M)** — pane layout, N cameras, per-pane orbit/pan/zoom, per-pane resize/aspect, picking routed to the pane under the cursor, focused-pane concept. Ship 1×1 and 2×2 only; no persistence, no new UI chrome beyond a temporary toggle. **Shipped.**
   2. **Phase 2 (S–M)** — the `.view.json` extension above, plus a real layout picker in the **View ▾** menu (`1×1`/`1×2`/`2×1`/`2×2`). **Shipped.**
   3. **Phase 3 (S, optional)** — linked cameras across two tabs via the host relay + session registry described above. **Still queued.**

   **No kernel work and no MCP tool.** This is a display/interaction feature with no headless equivalent, matching the precedent already applied to Display modes, Markup, Measurement, and SVG import. The agent-facing need it resembles is already met: `render_snapshot`'s `DEFAULT_VIEWS` packet is two opposed isometrics plus TOP and FRONT — quad view is, in effect, the interactive counterpart of a view packet the codebase already chose once.

   **Verification will be mostly F5-only**, the standing caveat for every webview-only feature here. The one genuinely unit-testable piece is the pure layout math — pane rects from a container size, and the inverse mapping from a pointer position back to a pane — which should be extracted into its own DOM-free module, following the `clipping.ts` / `cameraControls.ts` precedent of keeping the math testable and leaving only the three.js application in `viewer.ts`.

2. **Op-history scrubbing — a click-to-jump timeline** (**S**). Comparing against [FluidCAD](https://fluidcad.io), a code-driven parametric CAD tool: its history/timeline panel lets a user click any past feature to roll the model back to that point, with later features greyed out and re-applicable by clicking forward again (its `breakpoint()` primitive is the same idea applied mid-script, pausing evaluation at a line). CAD-Preview's own Edits panel has no equivalent — reaching an earlier or later point in the op history today means clicking Undo/Redo one row at a time, with no way to see what's in the redo buffer or jump straight to a specific point.

   **Cheaper than it first looks, because the real primitive already exists.** `src/webview/editsModel.ts`'s `EditsModel` already holds a genuine bidirectional, multi-step undo/redo stack — `ops: EditOp[]` (applied) and `redoBuffer: EditOp[]` (undone-but-recoverable) as two separate arrays, `undo()` popping one from `ops` onto `redoBuffer` and `redo()` doing the reverse — not a single-slot pair. `main.ts`'s `syncEdits()` already posts the *entire current `ops` list* on every mutation (`editsChanged`), and both replay paths on the other end (`provider.ts` → `loadBRepCachedForDocument` for B-rep, `main.ts`'s `rebuildMeshModel()` for mesh sources) already accept an arbitrary-length `ops` array with no new message type needed. So the host/replay half of this feature is **already done**.

   **The real, narrow gap is entirely in the panel.** `editsPanel.ts`'s `render(ops, canUndo, canRedo)` rebuilds `<ol class="edits-list">` from only the *applied* `ops` — the redo buffer's pending-but-undone steps are never rendered at all, exposed only as the `canRedo` boolean, so there is no timeline to click on today. Each row already has a per-index click target to copy the pattern from (`.edit-remove`'s `✕`, wired via `onRemoveOp(i)`). The fix: `render()` also takes the redo buffer and renders its ops as additional, visually dimmed rows after the applied ones (the existing `.edit-row:hover .edit-remove` reveal pattern in `media/viewer.css` is the natural template for a second row-level affordance), and a click anywhere on a row — applied or pending-redo — calls a new `EditsModel.jumpTo(index)`.

   **`jumpTo` must splice the boundary between the two arrays directly, in one call — not loop-call `undo()`/`redo()` N times.** Looping would fire N separate `onChange`/`editsChanged`/autosave/re-tessellate round trips for one click — a real, avoidable flicker-and-redundant-replay trap, not a hypothetical one, given `main.ts` fires the full sync pipeline from every `EditsModel` mutation today. One `onChange` at the end, exactly like every other mutation this model already makes.

   **No new "preview" semantics needed, which is what keeps this Tier 2 rather than a new model concept.** Jumping to point K is exactly what repeated Undo/Redo already does — state genuinely changes, nothing is a non-committing ephemeral view — matching FluidCAD's own actual behavior too (its rollback also moves a real position in the feature list, not a separate preview buffer).

   **One stated perf caveat**: `occtService.ts`'s `loadBRepCached` only reuses its cached op-replay for a *pure append* of `previous.ops` (`appendReusable`) — jumping backward (or scrubbing back-and-forth across many lengths) always pays a full `applyEditsBRep` replay from the still-cached base shape, never an O(1) op. Fine for a click-to-jump list; worth flagging before ever building a continuous-drag scrubber on top of this.

   **A natural, smaller Phase 2, not required for v1**: wire this into `run_parametric_script`'s existing `repeat`-loop compiler as a literal breakpoint — stop compiling/applying partway through a large generated op batch for inspection. This is the closest analog to FluidCAD's actual `breakpoint()` (which pauses *script evaluation*, not a click-list), since `run_parametric_script` is the only place this codebase has anything resembling "evaluating a batch."

   **A sibling already shipped:** the closed `render_ops_prefix` MCP tool (see `CLAUDE.md`) is the headless counterpart — the same `ops.slice(0, N + 1)` replay exposed as a read-only bisection tool, inheriting exactly the append-only replay caveat stated above — so the interactive timeline below completes the pair. The closed op-outcome work (former Tier 1 item 2, see `CLAUDE.md`) already gave every history row its applied/skipped marker (`EditsPanel.render`'s optional `opOutcomes`) — a scrubbable timeline builds directly on exactly that row rendering.

   **Verification**: `EditsModel.jumpTo` is pure array logic, unit-testable with no DOM/WASM, mirroring the existing `editsModel.test.ts` coverage of `push`/`undo`/`redo`/`remove`/`clear`. The panel rendering change carries the standing "not exercised in a real Extension Development Host session" caveat every other webview-only Edits-panel change in this codebase already has.

3. **Query-based / geometric selection filters** (**S** for Phase 1; **M** for Phase 2). FluidCAD's chainable selection filters (`edge().verticalTo("top").onPlane("yz")`, `.withTangents()`, `.internalFaces()`) replace tedious multi-click entity selection with a declarative query. The interactive win is obvious (a "select all vertical edges" query next to the existing Vol/Surf/Line/Point pick-mode row); the headless win may be larger — an MCP agent today can only reference entities it already has concrete `face-N`/`edge-N` ids for from a prior `load_model`/`inspect` call, with no way to ask "give me every face whose normal is +Z" in one call.

   **What already exists to build on — reuse one of these, don't invent a third.** Per-entity geometric facts are already computed twice in this codebase: client-side, on every tagged `THREE.Mesh`/`THREE.Line` from the tessellated positions/normals already in the scene (see this file's own "Webview entity model" section in `CLAUDE.md`), and host-side, exactly, via `entityFacts.ts`'s `inspect` — bbox, centre, area/length, and for a planar face its normal and surface type.

   **The client-vs-host question this item previously deferred is now resolved, by reading the files it named.** The answer is *both*, split cleanly by predicate, and the client-side half is materially cheaper than the **M** this item originally carried:

   - **`picking.ts`'s `collectTargets(root, mode)` is already a whole-scene enumerator, not a raycast** — a plain traversal filtering on `userData.entityType`. It hands a filter every face mesh or edge line in the scene today with no new code. One asymmetry to respect: in `volume` mode it returns *face* meshes that resolve up via `userData.groupId`, so a volume-level filter must dedupe by group.
   - **`SelectionSet` needs no new API for bulk injection.** It is keyed `${entityType}:${entityId}` and is not type-homogeneous; `clear()` + a loop of `add()` + a re-render is exactly what the existing pick handler already does, and `renderSelection` is already a whole-list re-render, so a 500-face result costs the same single traverse as one pick.
   - **Normals *are* available client-side**, despite the host never sending them: `protocol.ts`'s `EncodedMesh` carries only positions and indices, but `geometryBuilder.ts` calls `computeVertexNormals()` on every face mesh at build time, and the host has already fixed reversed winding.

   **So Phase 1 (S) is client-side and covers most of the value**: normal direction and planarity, face area (exact for planar faces, slightly under for curved), bbox/extent/position tests, edge length and direction, largest/smallest-N, and — free, from the flag `geometryBuilder.ts` already sets — excluding tangent patch seams via `userData.smooth`. No kernel surface, no protocol change, no MCP tool: a clean Tier 2 fit, confirmed rather than assumed.

   **Phase 2 (M) is host-side and covers exactly what tessellation cannot answer**: analytic **surface type** ("every cylindrical face", "every fillet"), exact radius and axis, and exact areas for curved faces — a fine-faceted prism and a true cylinder are indistinguishable in triangles, so no client-side heuristic can be trusted here. The natural implementation is not a new computation but a bulk one: `entityFacts.ts`'s `collectAllEntitySignatures` already walks every solid/face/edge/point in the same deterministic order that assigns the ids, recording `{id, kind, centre, measure}` — it is missing only normals, `surfaceType`, and bbox extents to become the query index this needs, and those come from accessors `getEntityFacts` already calls one entity at a time. Add the new fields, expose it as one bulk call, and both a new protocol pair and a new MCP tool fall out of the same function.

   **A second sibling project supplies the concrete, externally-validated shape for Phase 2's query language.** [SindriCAD](https://github.com/MakerViking/sindricad)'s `query` op (`docs/PROTOCOL.md`) is a structured filter over faces/edges — `surface: plane`, `area: {min,max}`, `normal: {dir, tol}`, `radius: {min,max}`, `within: bbox`, `createdBy: featureId` — returning persistable selectors, computed host-side against its exact kernel. That maps almost one-to-one onto what the extended `collectAllEntitySignatures` above would hold (and, pending item 20 Phase 1's live-WASM probe, onto surface-type-specific radius/axis data too), so Phase 2 should adopt this shape rather than invent one. Note `createdBy: featureId` in particular: it is the predicate this codebase cannot currently express at all, and it is exactly what item 23's build-time classification buckets would make possible — which is why that item should reuse this vocabulary rather than define a second one.

   **Whichever shape it takes, it should report facts, not a verdict** — a filter returns a *list of matching ids*, consistent with `describeCapabilities()`'s `verdictConventions` and the same fact-only precedent `check_interference`/`inspect`/`measure` already established.

   **Verification**: Phase 1's predicates are pure functions over a `BufferGeometry` and are unit-testable headless against hand-built fixtures (no DOM, no WASM), which is where the tessellation-vs-exact discrepancies should be pinned down explicitly — e.g. asserting that a curved face's computed area is *under* its analytic value, so the limitation is recorded as a test rather than a comment. Phase 2 rides `npm run mcp:smoke` at the bar `inspect` already set. The panel wiring carries the standing F5-only caveat.

4. **Dense-mesh boolean guard for the webview mesh-boolean path** (**S**). Found by comparing against a local sibling project, HCAD (a Rust/Bevy parametric CAD app over the `truck` + `Manifold` kernels) — its own mesh-boolean path hit a real, documented failure mode: a dense or non-manifold mesh (a real 149k-triangle scan, in its own test case) makes its primary robust-boolean library decline, silently falling back to an O(n²) BSP path that looked exactly like a hang, until an explicit triangle-count guard was added to skip that fallback and surface an actionable message instead of grinding for minutes.

    **CAD-Preview's own webview mesh booleans have the identical, currently-unguarded shape.** `src/webview/meshEdits.ts`'s `applyMeshBoolean` hands two operand meshes straight to `three-bvh-csg`'s `Evaluator`/`Brush` with no size or complexity check first — a boolean between two dense STL scans (or a scan and anything else) could plausibly freeze the webview's main thread with zero feedback, the same failure mode the comparison project hit and had to guard against explicitly.

    **No new kernel surface, no new persisted geometry, no new MCP tool — Tier 2's own admission fits this exactly.** A pre-flight combined-triangle-count check on both operands before calling `Evaluator.evaluate`, degrading to a clear status message (in the spirit of "mesh too dense for a boolean here — try Promote to B-rep first") instead of attempting and hanging. The suggested escape hatch is already shipped — `promote_mesh_to_brep`/the Mesh Health panel — so this needs no new repair mechanism of its own, unlike the same comparison project's own voxel-remesh "Solidify" fallback (see item 27's new Phase 0 for where a genuine mesh-repair pass *is* worth adding here).

    **The threshold needs a real number from this codebase's own evaluator, not a borrowed one** — the comparison project's own cutoff was tuned against its measured O(n²) fallback cost, a different algorithm with different scaling than `three-bvh-csg`'s BVH-based evaluator; the right number here should come from timing this codebase's own `Evaluator` against a genuinely large operand pair (e.g. a decimated vs. undecimated real scan fixture), not from copying a number tuned for a different implementation.

5. **BVH-accelerated raycasting for meshes that stay "kept whole"** (**S**). Comparing against [SindriCAD](https://github.com/MakerViking/sindricad): its viewport swapped a per-frame brute-force triangle scan for `three-mesh-bvh`-accelerated raycasting (`src/viewport/raycastIndex.ts`), measuring a concrete win (2.6 ms median down to near-0 ms on a 50k-triangle textured cylinder) with one documented gotcha: `indirect: true` is load-bearing, because the app keys features on raw triangle index and a naive BVH build can otherwise reorder the index buffer under the hood.

    **CAD-Preview's per-face-mesh entity model mostly sidesteps this already, which is why this is narrowly scoped rather than a blanket "add a BVH" item.** `geometryBuilder.ts` builds one `THREE.Mesh` per B-rep face, so a volume/surface pick already raycasts against many small objects rather than one dense one. The gap is the one case that split doesn't cover: `meshFacets.ts`'s `buildMeshFacetGroup` explicitly keeps a mesh **whole** (`facetCount <= 1 || facetCount > MAX_FACETS`, `MAX_FACETS = 512`) — exactly the large, organic scans (300k+ triangles is routine for a real STL) that most need acceleration, and exactly the shape SindriCAD measured a win on. Today such a mesh is raycast in full, via `Viewer`'s plain `THREE.Raycaster.intersectObjects`, on every pointer move.

    **Scoped narrowly: apply `computeBoundsTree`/`disposeBoundsTree`/`acceleratedRaycast` only to a mesh that was kept whole**, not to every per-face mesh (where the BVH-build cost per tiny face mesh would likely exceed the raycast cost it saves) — `buildMeshFacetGroup`'s own branch condition is precisely the signal for which meshes qualify. `three-mesh-bvh` (currently `0.9.10`) is already resolved in `node_modules` as a peer dependency of the already-bundled `three-bvh-csg`, but isn't a direct dependency — promoting it to one is the honest way to add it deliberately rather than lean on a transitive resolution.

    **Carry the one documented gotcha over verbatim, since it applies here for an even sharper reason**: this codebase resolves a raycast hit back to an `entityId`/`groupId` via `userData` on the hit `Object3D`, not a raw triangle index — closer to the source project's own failure mode than a passing resemblance — so `indirect: true` (or equivalent) needs the same explicit verification before shipping.

    **Verification**: a before/after timing comparison on a genuinely large "kept whole" fixture (this codebase doesn't currently ship an STL over `MAX_FACETS` — one would need adding, or a real large scan decimated down to a representative size), plus confirming picking/highlighting is pixel-identical before and after for a representative click sequence. Standard F5-only webview verification otherwise.

6. **Mesh-source Mass Properties has no watertightness check, unlike its B-rep sibling** (**S**). Comparing against [SindriCAD](https://github.com/MakerViking/sindricad): its `massProperties` op distinguishes "unmeasured" (absent fields plus a `reason`: `no solid` / `open shell` / `empty` / `feature failed`) from a real zero, deliberately refusing to report a volume "that looks real" for geometry that isn't actually closed.

    **CAD-Preview's B-rep path already gets this for free, by construction, not by an explicit check.** `computeMassProperties`'s own doc comment (`massProperties.ts`) names the exact same trap SindriCAD does ("`BRepGProp.VolumeProperties` returns a plausible-looking but WRONG number for an open shell/face") and sidesteps it structurally: `volume` is `number | null`, computed only for the whole model or a `solid-N`, which `collectSolids`'s `TopAbs_SOLID` explorer guarantees is topologically closed.

    **The mesh-source path has no equivalent guarantee and no equivalent guard.** `src/webview/meshMassProperties.ts`'s `computeMeshMassProperties` says in its own doc comment that `volume` is "meaningful only when `meshes` forms a closed (watertight) surface... never a single open facet" — but that's a comment, not a check: the function always returns a plain `number`, and the Mass Properties panel has no way to know whether the current selection is actually closed before displaying it. A common real case — an imported STL/OBJ/PLY/glTF scan with a genuine hole, selected whole — silently shows a volume that looks exactly as authoritative as a correct one.

    **The fix reuses machinery this codebase already built for exactly this trap, in a different feature.** `meshTopology.ts`'s `analyzeMeshTopology` (pure, DOM/OCCT-free, already unit-tested against hand-built fixtures) already computes free-edge counts for `checkMeshHealth`/`meshHeal.ts` — a mesh with `freeEdgeCount > 0` is not watertight, no OCCT sewing ladder needed for this weaker-but-sufficient signal. The one real decision: `meshTopology.ts` lives at `src/` (the host bundle) today, while `computeMeshMassProperties` runs with **zero host round trip** by design (CLAUDE.md's own explicit invariant) — extending it to import a pure module from outside `src/webview/` would be the first cross-bundle reuse of its kind here. Recommend it anyway over duplicating the same edge-adjacency loop a second time: `esbuild.mjs`'s webview build is a plain `platform: "browser"` bundle rooted at `main.ts` with no path restriction, so nothing structurally excludes importing a dependency-free module from outside `webview/`.

    **Shape of the fix**: `MeshMassProperties` gains `watertight: boolean` (from `analyzeMeshTopology(...).freeEdgeCount === 0`), and the panel shows Volume/volume-centroid greyed or with an inline caveat when `watertight` is `false` — never withholding the number outright (unlike SindriCAD's `reason`-gated absence), since this is a fast client-side estimate the user can still act on, just one that needs an honest caveat. Worth a much smaller note on the B-rep side too: `addVolumeFromSurfaces`'s own `NbFreeEdges()` gate already prevents an open shell from becoming a `solid-N` via that one op, but an imported STEP/IGES/BREP file that mislabels an open shell as a `TopoDS_SOLID` on disk would still pass `collectSolids`'s type-level guarantee — low-likelihood enough to note rather than build.

    **Verification**: `analyzeMeshTopology` is already unit-tested; add a `meshMassProperties.test.ts` case reusing an existing "closed vs. missing-one-face tetrahedron" fixture to confirm `watertight: false` is reported alongside a still-returned (flagged) volume, never a suppressed one. Panel display carries the standing F5-only webview verification caveat.

7. **DXF import and export — 2D drawing interchange for CAM/laser/AutoCAD workflows** (**S–M** for Phase 1 import; **S** for Phase 2 export). Comparing against [Open CAD Studio](https://github.com/HakanSeven12/OpenCADStudio), a full desktop/web DWG/DXF drafting application: its whole reason for existing — native DWG/DXF read-write — is out of CAD-Preview's scope wholesale, the same "modeling/drafting application" territory Non-goals already rejects for interactive sketching. But the narrow, already-precedented slice of it is not: this codebase already reads one 2D vector interchange format into its parametric profile ops (SVG, `src/svgImport.ts`) and writes another one out (`src/svgSilhouette.ts`/`export_svg_silhouette`). DXF is the format that actually matters to the CAM/laser-cutting/AutoCAD-interop audience those SVG features were built for, and it's missing on both sides.

    **Scope the format the way item 26 scopes OpenSCAD: the openly-documented ASCII interchange form only, never the binary/proprietary one.** DXF (`.dxf`) is a public, version-stable, well-documented ASCII group-code format; DWG is a closed binary format Autodesk has never published, readable in the open-source world only through the ODA's non-free SDK or the GPL-3.0 LibreDWG — another one-way license-upgrade decision, like item 26(c)/28's MMG. Reading DWG at all would be its own Tier-5-style externally-gated item; DXF needs neither a new dependency nor a license decision, mirroring option (a) of item 26 almost exactly.

    **Phase 1 (S–M) — import, mirroring the already-shipped `svgImport.ts` closely.** A new `src/dxfImport.ts` (pure, vscode/DOM-free, unit-tested the same way `svgImport.ts`'s 22 cases are) parses DXF's group-code/value pair structure out of the `ENTITIES` section of model space only — paper space, layouts, and block/`INSERT` references are explicitly out of scope for v1, the same restraint item 26 applies to `hull`/`minkowski`/`text()`. `LINE`, `LWPOLYLINE`/`POLYLINE` (bulge-arc segments included — DXF polylines mix straight and arc segments within one entity, unlike SVG's separate path commands), `CIRCLE`, `ARC`, and `SPLINE` (control points + degree) map onto ops that already exist — `addLine`, `addPolyline`, `addCircleProfile`, `addArc`/`addEllipseArc`, `addSpline` — so the emission side needs no new op kind, only a new source parser. Placement follows `svgImport.ts`'s own precedent exactly: flat at z=0, no rotation/scale picker, adjustable afterward with `translate`/`rotate`/`scale`. B-rep only, the same `BREP_ONLY_OPS` gate `addPolyline`/`addSpline` already carry. No MCP tool — same "interactive-only, no headless equivalent" precedent SVG import already established.

    **Phase 2 (S) — export, extending the already-shipped SVG silhouette pipeline rather than duplicating its geometry work.** `src/silhouetteEdges.ts` already computes the visible-edge segment list `svgSilhouette.ts` serializes to SVG; a DXF writer needs only a second serializer over the same segment list, emitting a minimal `ENTITIES`-only DXF (`LINE`/`LWPOLYLINE`). **Extends the existing `export_svg_silhouette` MCP tool with an output-`format` param (`"svg" | "dxf"`, mirroring `unit`'s own optional-param convention) rather than adding a second tool** — keeps this inside Tier 2's "no new MCP tool" admission. Worth sequencing after item 22 (hidden-line drawings), not before it: a technical drawing with dashed hidden lines is a more natural DXF payload than a bare silhouette, and DXF's own `LINETYPE` mechanism is the natural home for that distinction. **Design note, not a blocker**: real DXF-consuming CAM/laser workflows expect conventional layer names — put visible and hidden runs on two distinct `LAYER` entries rather than one.

    **No live-WASM probe needed for either phase** — both directions are pure TypeScript text parsing/serialization over data (profile ops in, tessellated/silhouette edges out) this codebase already produces through other paths; no OCCT/Gmsh/meshio++ call is involved anywhere.

    **Verification**: `dxfImport.test.ts`/`dxfExport.test.ts` unit-test the parser/writer against hand-built fixtures the same way `svgImport.test.ts` does (a bulge-arc `LWPOLYLINE`, a degenerate entity, and — mirroring `svgSilhouette.test.ts`'s own strongest check — a round trip of the new writer's output back through the new reader). The webview/host wiring (a File ▾ "Import DXF…" item, a DXF choice in the silhouette-export format picker) carries the standing "not exercised in a real Extension Development Host session" caveat every other webview-only feature in this file has.

8. **Dimension-style rendering for pinned measurements — in the 3D view and in exported drawings** (**S–M**; **S** per phase). Comparing against [Open CAD Studio](https://github.com/HakanSeven12/OpenCADStudio)'s "Documentation tools" (text, dimensions, leaders, tolerances, tables): CAD-Preview already has the *data* half of a dimension — the closed "Persisted, topology-anchored annotations" feature pins a measurement's frozen `text`/`anchorPoint`/`linePoints` to a real entity, and the queued tolerance-band item below adds a nominal/tolerance band on an exact measurement — but neither renders as an actual **dimension**: `measurementOverlay.ts`'s overlay is a plain line and text label, with no extension lines, no arrowheads/witness marks, no toleranced-value styling. item 22 (2D technical drawings) explicitly flags "dimensions" as an unscoped follow-on needing its own design discussion rather than assumed to fall out of its Phase 1 automatically — this item is that discussion.

    **Scoped deliberately narrow: this renders an already-pinned measurement as a dimension, it does not add dimensioning as an interactive placement tool.** Full GD&T authoring — picking entities and dragging a leader to place a dimension, extension-line offset control, stacked/chained dimensions — is drafting-application territory this file's Non-goals section already rejects for the identical reason interactive sketching is rejected. What's in scope is purely presentational: turn data CAD-Preview already persists into a recognizable dimension glyph wherever that data is already shown or exported.

    **Phase 1 (S) — 3D-view rendering.** `measurementOverlay.ts`'s label/marker builders already compute a world-space line and label position from `Annotation`/`MeasurementState`'s `anchorPoint`/`linePoints`; extension lines (short perpendicular offsets from each measured point to the dimension line) and arrowhead/witness-mark geometry are the same class of pure `THREE.Line`/`THREE.Sprite` construction already used there, not a new rendering technique. A toleranced pin (once the tolerance-band item's optional Phase 2 `Annotation.tolerance` field ships) renders its label as `nominal ±tol`, with an out-of-tolerance pin distinguished by colour — the annotation still stores the measured fact; only the label's colour, a presentation choice, reflects the derived pass/fail, matching `checkInterference`'s `hasOverlap`-as-fact convention.

    **Phase 2 (S), sequenced after item 7's DXF export and item 22's hidden-line work** — bake the same extension-line/arrowhead geometry into `svgSilhouette.ts`'s output and item 7's DXF writer, for every currently-pinned `Annotation` on the exported view. No new MCP tool — this rides the same `export_svg_silhouette` tool item 7 already extends, emitting extra geometry when annotations exist rather than adding a new response shape.

    **No live-WASM probe needed** — pure geometry math (offset/arrowhead construction from already-known points) plus rendering/serialization, no new kernel surface in either phase.

    **Verification**: the extension-line/arrowhead math is a natural candidate for its own small pure module (mirroring `clipping.ts`'s "pure math extracted from the THREE-touching class" precedent), unit-testable headless. The actual 3D rendering and export-baking carry the standing F5-only webview verification caveat.

9. **Live operation preview — show the result before Apply, coloured by intent** (**M**). Comparing against [FluidCAD](https://fluidcad.io), whose feature dialogs render the geometry the pending operation *would* produce as a translucent overlay, rebuilt on a debounce as parameters change, and — the part worth copying most — **coloured by what the operation does to the material**: green where it adds, red where a cut removes, blue for wire-only results. A fillet reports colour *per band*, because one selection can add material on a concave edge and remove it on a convex one simultaneously.

    **CAD-Preview already has this shape twice, for two ops only.** The explode slider (`explodePreview.ts`) and the Transform Gizmo both preview live before commit, and both already solved the hard discipline questions: never compound onto the previous frame's result (re-derive from a cached base every time), and cancel the preview before the real op is pushed so a stale transform is never left stacked under the authoritative replay. Every *other* op — every boolean, fillet, chamfer, hole, shell, split, and all of feature modeling — is typed blind into a form and only becomes visible after Apply, which is precisely where a wrong parameter is most expensive to discover.

    **No new kernel surface, which is what keeps this in Tier 2.** The B-rep preview is `loadBRepCached(…, [...currentOps, draftOp])` — the existing call, with the not-yet-committed op appended, on the existing debounce — discarded rather than persisted. That is the same "speculative replay" the op stack already performs on every real edit; nothing new is asked of OCCT. The intent colouring is the one piece needing thought: the cheap version is per-op-kind (a `cut`/`shell`/`split` result renders red, an additive one green), and the honest version — per-band, as the comparison project does — needs the boolean's own `Modified`/`Generated` history to attribute each new face, which is a real design question this item should flag rather than assume.

    **Two traps this codebase has already hit once each, worth restating here so they aren't re-hit**: a preview must never enter the op stack (the webview owns that stack, and an uncommitted preview in it would be undoable, persistable, and wrong), and it must be cancelled on *selection* change as well as form change — the Transform Gizmo shipped with exactly that bug, where switching selection left an orphaned preview stranded with nothing to reset it.

    **Verification**: standing F5-only caveat for the rendering. The genuinely testable piece is the debounce/cancel state machine, which should follow `explodePreview.ts`'s precedent of keeping the cache-and-restore logic in a pure module with its own unit test (its own regression test — "two consecutive calls with different factors must not compound" — is the exact shape needed here).

10. **Render on demand, not every frame** (**S**). Comparing against [FluidCAD](https://fluidcad.io), whose render loop draws only when something actually changed — a `requestRender()` call, or the camera controller reporting movement — rather than unconditionally every frame.

    **CAD-Preview renders continuously.** `viewer.ts`'s `animate` ends in an unconditional `requestAnimationFrame(this.animate)`, so an idle CAD Preview tab with a static model redraws ~60 times a second forever, in a webview inside an editor the user may have open all day. Nothing about this codebase requires it: the animation loop's only genuinely per-frame work is `OrbitControls`' damping (which reports whether it actually moved) and the measurement label's distance-based rescale (which only matters while the camera is moving).

    **Adopt the containment test alongside it**, from the same source: skip re-framing when the new bounds' sphere already fits inside the last padded fit sphere, so the camera stops twitching on every rebuild — a small, visible quality improvement in a codebase where every edit triggers a re-tessellation and re-frame.

    **The one real hazard to call out**: several features drive continuous visual updates (the explode slider, gizmo drags, the clip-plane offset slider, item 9's preview above) and each must call `requestRender()` explicitly or they will silently stop updating mid-drag. That is the whole risk, and it is a search-and-audit job across the known interaction sites rather than a design question. Standing F5-only verification caveat.

11. **Theme-reactive scene colours, not just a theme-reactive background** (**S**). Comparing against [FluidCAD](https://fluidcad.io), which reads every scene colour — faces, edges, grid, highlight, selection — from CSS custom properties and re-reads them from a `MutationObserver` on the theme attribute, so the 3D view re-tints live when the editor theme changes.

    **CAD-Preview handles exactly one of those colours this way.** `cadPreview.background` is a setting with a session-only override in the Appearance group; the geometry, edge, highlight and selection colours are constants in `geometryBuilder.ts`/`viewer.ts`. The result is a viewer whose model does not respond to the editor theme at all — and this is more visible here than in a standalone app, because a VS Code webview sits directly beside themed editor chrome. Note the toolbar/panel icons already solved this problem correctly (the generated SVG set is `currentColor`-based specifically so it tracks the theme), so the convention exists in this codebase; the 3D scene simply predates it.

    **The mechanism is already half-present**: `viewer.ts` caches a `baseColor` in `userData` per object and `highlightGroup()` already multiplies against a stored `baseOpacity` rather than overwriting — the same "one source of truth, composed at apply time" discipline a theme swap needs. The work is moving the constants into CSS variables, reading them once into `THREE.Color`s, and re-applying on theme change.

    **One thing to preserve deliberately**: the per-Part colour swatches are user data, not theme data, and must not be re-tinted. Standing F5-only verification caveat, and this is one where checking both a light and a dark theme is the whole test.

12. **Explain the geometry under the cursor** (**S–M**; three independently shippable pieces). Comparing against [FluidCAD](https://fluidcad.io), which has three distinct affordances for the same underlying question — *what is this thing I am pointing at, and what will happen if I click it?* — none of which CAD-Preview has interactively.

    - **A geometry-type inspector card.** Hovering or selecting a face or edge shows a small corner card classifying it (face: plane / cylinder / cone / sphere / torus; edge: line / circle / arc / ellipse) with **only the fields that apply to that classification** — area for a plane, radius for a cylinder, major and minor radius for a torus, half-angle for a cone. CAD-Preview computes exactly this already, but only headlessly: `inspect` returns `surfaceType` plus bbox, centre, area/length, and for a planar face its normal. There is no interactive equivalent — a user clicking a face in the viewer is told nothing about it. Needs a host round trip (analytic surface type is not derivable from the tessellation — a fine-faceted prism and a cylinder are indistinguishable in triangles), so this is a new protocol pair over the existing `getEntityFacts` pipeline, not new geometry work.
    - **A teach tooltip.** Hovering geometry while an op form is open shows, in monospace, *how that entity would be addressed* — its `face-N`/`edge-N` id, and which already-applied ops reference it. This is the single best "explain the system" idea in the comparison project, and it maps unusually well here because CAD-Preview's whole persistence model is an op list of stable-until-they-aren't entity ids: showing the id under the cursor makes the sidecar legible, and showing which ops already reference an entity is genuinely new information available from data the webview already holds.
    - **A selection-groups context menu with hover preview.** Right-clicking an entity offers computed groups with member counts — "tangent chain (12)", "same surface type (30)", "same producing op (4)" — and **hovering a menu item previews exactly what clicking it would select**. This is item 3's query filters given a discoverable entry point: the same predicates, reachable by right-click instead of by composing a query. Ship it *after* item 3 and reuse its predicate vocabulary rather than duplicating it.

    **Verification**: standing F5-only caveat for all three. The inspector card's host round trip is the one piece with automated coverage available — it reuses `getEntityFacts`, already exercised through `inspect` in `npm run mcp:smoke`.

### Tier 3 — MCP agent-workflow ergonomics

*Admission: closes a friction point documented in real-world agentic CAD usage elsewhere, using capabilities the MCP pipeline already exposes — persistence or tooling additions on top of `mcpTools.ts`/the sidecar-store pattern, not a new kernel capability. None of these needs a live-WASM probe; each composes existing, already-verified primitives (`parametricScript.ts`'s compiler, `measureExact`, `fileRouter.ts`'s `routeFile`, `mcpSidecars.ts`'s store convention).*

Prompted by a MakeUseOf write-up of a FreeCAD-via-Claude-Code workflow ([source](https://www.makeuseof.com/claude-code-replaced-cad-software-printing-parts-half-time/)). FreeCAD's own MCP integration is architecturally different from this one — a persistent, session-scoped document inside a running FreeCAD process, driven over its Python API, versus this codebase's stateless-per-call design where every tool call is explicit-path-in/sidecar-as-state — so most of the piece's specifics (its CAM-toolpath forks, its `--only-text-feedback` screenshot-budget flag) don't transfer directly; the latter in particular is already this codebase's own default posture (`inspect`/`measure`/`measure_exact` are fact-only with no image cost at all, and `render_snapshot`'s images are opt-in and explicitly framed as "diagnostic, not authoritative" per `describeCapabilities()`'s `verdictConventions` — see `CLAUDE.md`'s "Agent feedback tools" section). Three gaps the piece named do transfer, reframed for this codebase's own architecture rather than copied verbatim.

13. **Saved, named, parameterized scripts — a persistent macro library** (*issue #14*) (**M** headless; **+S–M** for the interactive half). The article's sharpest complaint: FreeCAD-MCP agents have "no persistent skill library across sessions" and must "re-derive the same bolt pattern logic every time" — a real cost for exactly the repetitive-but-parametric jobs (mounting plates with bolt patterns, brackets with fixed hole spacings) it also calls out as the workflow's strongest fit. Issue #14 asks for the same capability from the other side of the tool: macros to automate repeated work interactively. Both land on one mechanism, which is why they are one item.

   **`src/parametricScript.ts` already compiles a declarative `{variables?, steps}` document with a `repeat` loop and a full expression evaluator (`paramExpr.ts`) — it is missing only a name and a place to persist it across calls.** That is the whole gap: there is no macro *language* to design, and deliberately so. Recording a macro is likewise not a new capture mechanism — `<model>.edits.json` is *already* an ordered, replayable op list, so "record" is a selection over ops the user has already applied, and "play" is the compile-and-append path that already exists.

   - **A script's own `variables` block is already its parameter list — no new schema needed.** `ScriptLibraryEntry {name, description, script: ParametricScript}` is the whole shape; calling a saved script with overrides is just merging caller-supplied `{name: value}` pairs onto the saved `variables` array by name before compiling (an unknown override name degrades to a `warnings` entry, never a hard failure — this codebase's standing per-field-tolerant convention, not a new one).
   - **Storage is one explicit JSON file, not a hidden per-workspace convention.** This codebase has no notion of a workspace root inside `mcpTools.ts` today (every path is caller-supplied), and a script isn't tied to one CAD document the way `.edits.json` is tied to one source file — so the natural fit is a single `libraryPath` JSON file the caller names explicitly (e.g. checked into a project alongside its models), holding `{version, scripts: {name: entry}}`, parsed with the same tolerant-drop-malformed-entries discipline every other sidecar in this codebase uses. A new `src/scriptLibrary.ts` (pure, vscode-free, unit-tested) owns parse/serialize; `mcpSidecars.ts` gains the Node-fs read/write, mirroring the established pure-module/impure-store split.
   - **Three new tools, all thin wrappers over existing machinery**: `save_parametric_script(libraryPath, name, description, script)` compiles the script against its own declared variable defaults first (a dry run, no `modelPath`/geometry needed) and refuses to save one that doesn't compile — a broken macro should never make it into the library silently. `list_parametric_scripts(libraryPath)` returns each entry's name/description/parameter names+defaults, so an agent can discover what's available without reading the raw JSON. `run_saved_script(libraryPath, name, modelPath, parameterOverrides?, ops-and-dryRun params identical to run_parametric_script)` loads the entry, resolves overrides, and hands the merged script straight to the exact same compile-and-apply path `run_parametric_script` already uses — no second B-rep-only gate, no second entity-rebinding call site, just a different source for the script document.
   - **The interactive half (issue #14's own framing) is a panel over the same library file, not a second mechanism.** A "Macros" sidebar section listing each saved entry with its parameters, a value field per parameter, and a Run button that pushes the compiled ops onto the existing `EditsModel` stack — so a macro is undoable, inspectable in the history, and removable op-by-op exactly like any hand-applied edit, with no special "macro" state for undo/redo to reason about. **Record** is a selection over the current op list (check the ops to keep, name it, save) rather than a live capture session, which avoids inventing a recording mode and makes "record" work retroactively on edits already applied. The one genuine design decision: whether recording should offer to *promote a literal to a parameter* (turn a hard-coded `20` into a `L` variable). Recommendation — yes, but as an explicit per-field opt-in in the save dialog, never inferred, since guessing which numbers are meant to be parametric is exactly the kind of silent wrong assumption this codebase avoids elsewhere.
   - **Deliberately NOT a new interactive persistence convention**: the panel reads and writes the same caller-named library JSON the MCP tools use, so a macro recorded by a human is directly runnable by an agent and vice versa — the same interoperability property the parts/edits/mesh sidecars already give the two surfaces.
   - **Verification**: unit tests for `scriptLibrary.ts`'s parse/serialize/merge-overrides (pure, no WASM), plus an `mcp:smoke` addition mirroring the existing bolt-circle script check — save a parameterized bolt-circle macro, list it back, run it twice with different `radius`/`count` overrides against a fresh copy of `bull.stp` each time, and confirm the two results differ by exactly the parameter change (same `(R·cos, R·sin)` position check the existing `run_parametric_script` smoke coverage already does, run through the saved-script path instead of an inline script).

14. **Tolerance-band fact checks on exact measurements** (**S–M**). The article separately names "close tolerance relationships and GD&T annotations" as still hard to specify. Full GD&T (datums, flatness/position/profile callouts, ASME Y14.5 semantics) is modeling-application scope this project has already rejected elsewhere (see Non-goals' "Interactive sketching with geometric constraints") — but a much narrower slice, a nominal value plus a tolerance band checked against an already-exact measurement, is pure arithmetic on top of the closed `measure_exact` tool and needs no new kernel surface at all.

   - **`check_tolerance(kind, entityIdA, entityIdB?, nominal, tolerancePlus, toleranceMinus?)`** (`toleranceMinus` defaults to `tolerancePlus`, i.e. symmetric ± when only one is given) calls the existing `measureExact` pipeline function unchanged, then computes `deviation = measured − nominal` and `withinTolerance = deviation ≤ tolerancePlus && deviation ≥ −toleranceMinus` as an additional **fact** field alongside the raw measured value — never phrased as a pass/fail verdict in the tool description, matching `checkInterference`'s `hasOverlap`-as-fact precedent and this codebase's `verdictConventions` (tools report facts; the agent — or, transitively, the person it's answering to — renders the judgment).
   - **Phase 2, optional and webview-only**: extend the already-persisted `Annotation` shape (the closed "Persisted, topology-anchored annotations" feature) with an optional `tolerance?: {nominal, plus, minus}`, surfaced as a small inline field next to the Measure panel's existing **📌 Pin** button — so a human reviewing the model can record the same nominal-plus-band intent interactively, with the annotation's existing detached/struck-through handling covering a tolerance-carrying pin whose anchor entity is later lost exactly the same way it already covers a plain one. This half needs the standing F5-only verification every `provider.ts`/webview change in this codebase needs; the MCP tool alone (phase 1) is fully headless-testable via `mcp:smoke`.

15. **Hole Wizard: standard tapped/threaded hole presets** (**S–M**). The same comparison project's "Hole Genie" layers metric coarse/fine and imperial UNC/UNF standard pitch tables, depth quick-sets, and tap-drill-size hints on top of its own hole feature — a convenience CAD-Preview's hole ops have no equivalent for today.

    **No new op kind, no new kernel surface at all.** `AddHoleOp`/`AddCounterboreHoleOp`/`AddCountersinkHoleOp` (`src/editOps.ts`) already take plain numeric `radius`/`depth` (plus counterbore/countersink params) with zero standard-size awareness — a caller has to already know, e.g., that an M6×1.0 tapped hole wants a 5.0 mm tap drill. The fix is a pure data table, not a kernel change: a new `src/holeStandards.ts` (vscode/OCCT-free, unit-tested) holding the ISO metric coarse/fine pitch table and the UNC/UNF table, each designation mapping to a clearance-hole and a tap-drill diameter, feeding the *existing* hole ops' `radius` field unchanged.

    **Two thin surfaces on top of the same table**, mirroring items 5/7's own MCP-tool-plus-interactive-half split: a new MCP tool `list_standard_hole_sizes(standard, designation?)` for agent discovery (so an agent doesn't have to hardcode a pitch table itself), and — interactively — a designation dropdown in the hole op's param form that fills the existing `radius`/`depth` fields rather than introducing a new field type. Depth "quick-sets" (common preset depths, e.g. "through") are a similarly small, additive convenience on the same form.

16. **A distributable agent skill, plus the two zero-cost MCP surfaces this server doesn't use** (**S–M**). Comparing against [FluidCAD](https://fluidcad.io), which ships an installable Claude Skill (`mcp/skills/FluidCAD/SKILL.md`) alongside its MCP server, and additionally populates two MCP surfaces CAD-Preview leaves empty. There is **no `skills/` directory in this repo**, and `CLAUDE.md` is not a substitute — it is contributor memory for people working *on* the extension, not instructions for an agent working *with* the MCP server, and it is not installed anywhere an end user's agent would find it.

    **Three separable pieces, cheapest first:**

    - **The server's `instructions` string (S, minutes).** The MCP SDK lets a server ship a short instruction block that conforming clients inject into context before any tool is called. `mcpServer.ts` sets none today. This is free real estate for the invariants an agent otherwise has to discover by trial: every `path` is absolute; state lives in sidecars next to the CAD file and the source file is never written; **tools report facts, never verdicts** (already stated in `describeCapabilities()`' `verdictConventions`, but only visible to an agent that calls that tool first); a `supported: false` result is need-more-info, never a silent pass or fail.
    - **An MCP resources surface (S).** Register the same capability/op-catalog content `describe_capabilities` returns as read-only resources (e.g. `cad-preview://capabilities`, one per op kind). Clients that auto-attach resources get it without spending a tool call; clients that ignore resources keep using the tool. Deliberately the *same* content from the *same* source — a second hand-maintained copy would be exactly the drift item 30's coverage gate exists to prevent.
    - **The skill itself (S–M).** A `skills/CAD-Preview/SKILL.md` with the standard YAML frontmatter, triggering on **tool availability** (`mcp__cad-preview__*`) rather than on the product name — the pattern that makes it fire when an agent is doing CAD work without saying "CAD-Preview". The transferable content, retargeted onto this codebase's own tools: plan in **generic CAD vocabulary, never op-kind names**, so a human can review the approach before any JSON exists; a **snapshot-cost calculus** (spend a `render_snapshot` before *depending* on anything selection-driven or kernel-heavy; op replay now reports applied/not-applied outcomes, so a quiet no-op already surfaces as a warning rather than silence); **sub-agents read, they never build** (a sub-agent that applies an op mutates the sidecar the main agent is reasoning about); and **volume is a regression check, not verification** — it can tell you something changed, never that the model is right.

    **Verification**: the `instructions` string and the resources surface are both covered by extending `npm run mcp:smoke` (assert the initialize response carries instructions; assert `resources/list` returns the expected set). The skill is prose and has no automated verification beyond the coverage gate in item 30 if its examples are written in the executable fenced language.

17. **Camera-aware snapshots and `hit_test` — close the pixel → entity loop** (**S–M**). Comparing against [FluidCAD](https://fluidcad.io)'s visual tool set, which is materially richer than a fixed view packet in three ways CAD-Preview could adopt without touching its (already headless, already Playwright-driven — and in this respect *better*) rendering path.

    - **A `view` discriminated union** instead of a fixed packet: `current` / one of 14 named views (6 cardinal plus all 8 isometric octants, each self-describing — "iso-ftr = front-top-right") / `orbit-from-current{azimuthDeg, elevationDeg}` / `look-from{eye, target}`. `render_snapshot` today always renders `DEFAULT_VIEWS` (two opposed isometrics plus top and front), which is a good default and a poor only-option — an agent that has spotted something in one view has no way to nudge the camera slightly and look again. Their schema also carries an explicit contract worth copying verbatim: *a snapshot view never moves the user's interactive camera.*
    - **`screenshot_shape(entityId)`** — auto-frame one entity from its own bounding box (which `inspect` already computes) rather than the whole model. The single most common thing an agent wants after `inspect` returns something surprising.
    - **A single 2×2 composite** as an option alongside the current four separate images, so the result can be laid next to an orthographic drawing sheet and compared 1:1 — and, incidentally, costs one image's worth of attention instead of four.
    - **`hit_test(rayOrigin, rayDirection)` → face/edge id.** The missing inverse: an agent can currently go from an entity id to a picture, but never from something it sees in a picture back to an entity id. `renderService.ts` already stands up a real webview with the shipped `viewer.js` and the full picking pipeline in it, so the raycast machinery is present — this is a new message on an existing harness, not new geometry code.

    **Verification**: `npm run mcp:smoke`, with the same Chromium-absent tolerance `render_snapshot`'s existing coverage already has (assert the `supported: false` path when Playwright is unavailable, the real path when it is). `hit_test` is the one piece with a sharp assertion available — fire a ray down a known axis at a fixture with known geometry and assert it returns the specific face id `inspect` reports at that location.

18. **Refuse to clobber unsaved editor buffers, and ship a fix with every refusal** (**S**). Comparing against [FluidCAD](https://fluidcad.io), whose file-writing MCP tools query the editor for its unsaved-buffer set and **refuse** rather than overwrite, listing the conflicting paths and offering an explicit `force` override — its own skill calls overwriting a user's in-progress work "a serious failure mode."

    **CAD-Preview's exposure is narrower than that project's but real, and it is cheaper to close here.** The MCP server never writes the CAD source (every output path goes through `assertNotSourcePath`), but it *does* write the `.edits.json` / `.parts.json` / `.annotations.json` / `.mesh.json` sidecars — which are ordinary JSON files a user may well have open and hand-edited in the editor, and which the extension itself reconciles from disk via the five per-document file watchers. An agent writing a sidecar while the user has unsaved changes to that same file in a VS Code tab silently wins. And unlike the comparison project, **CAD-Preview *is* the editor** — `vscode.workspace.textDocuments.filter(d => d.isDirty)` answers this with no IPC and no protocol at all, for the interactive half.

    **The headless half needs a decision this item should make explicitly**: `dist/mcp-server.js` runs as its own process with no VS Code API, so it cannot see dirty buffers directly. The honest options are to expose the dirty set through the same mechanism a future instance registry would use, or to scope the guard to the interactive path only and say so. **Recommendation: scope it to the interactive path in v1** and record the headless gap, rather than inventing a cross-process channel for it.

    **Generalize the second half of the pattern, which is the more broadly useful one**: their equivalent guard refuses a write that would break the file and returns a **paste-ready fix** in the error's `details.suggestion`, not just a diagnosis. This codebase already returns structured `warnings` everywhere; extending the convention so that a *rejection* carries the corrected value (a clamped parameter, the nearest valid op kind, the resolved id an unresolvable one most likely meant) is a small, uniform improvement to `validateEditOp`'s reason strings and to every tool that rejects input. Note their **guards fail open, never closed** rule alongside it: when the check itself cannot run, the write proceeds rather than failing.

### Tier 4 — New model-layer concepts

*Admission: adds a genuinely new concept to the document model — a new persisted entity, a new class of derived information, or a new kernel capability behind a new op kind — rather than closing a gap in an existing one. Most items here are phased so that the cheap, independently-useful phase can ship alone, and several have a phase that needs a live-WASM probe before it can be estimated.*

19. **Arbitrary and reusable construction planes** (*issue #36*) (**L** overall; **S** for Phase 1 alone).

   **First, the correction that changes the shape of this item: arbitrary planes already exist throughout the kernel and the op model.** Every plane-bearing edit op takes an explicit `Vec3` pair, not an axis enum — `mirror`, `splitByPlane` and `section` all take `{planePoint, planeNormal}`, and every 2D profile (`addCircleProfile`, `addRectangleProfile`, `addPolygonProfile`, `addEllipseProfile`, `addRoundedRectangleProfile`, `addSlotProfile`, `addTrapezoidProfile`, `addArc`, `addEllipseArc`) takes `normal` plus, where phase matters, `up`. `align` is the *only* op with an axis enum. So "add arbitrary planes to the edit ops" would be wrong work. The three real gaps are elsewhere:

   - **(a) The display clip plane is axis-locked** — and only there. `planeForAxis(axis, offsetFrac, box)` derives the normal from an `"x" | "y" | "z"` literal, `ViewState.clip` persists `{axis, offsetFrac}`, `viewStateSidecar.ts` validates against the three literals, and the UI is three `data-axis` buttons.
   - **(b) There is no way to derive a plane from picked geometry.** `facePlane` exists but is host-side only; no protocol message carries a plane to the webview, and the webview constructs exactly one `THREE.Plane` in the whole codebase (in `planeForAxis`). Three-point plane construction exists nowhere, host or webview.
   - **(c) There is no named, reusable, persisted plane.** No sidecar stores one; every op carries its own inline, independently-typed copy. Sketching six profiles on one plane means typing the same `normal`+`up` six times. The only available indirection is per-scalar parametric variables, which have no plane semantics and no coherence check.

   **Phase 1 (S) — arbitrary clip normals.** By far the best cost/benefit, and almost entirely a type-widening exercise: **everything below `Viewer.setClippingPlane(plane: THREE.Plane | null)` is already orientation-agnostic**, including `capCenterAndSize(plane, box)` (which already takes a generic `THREE.Plane`, not a `ClipAxis`) and the entire stencil clip-cap. Widen `ViewState.clip` to carry an optional explicit normal beside the existing `axis`, keeping the axis form as the legacy shape so an older `.view.json` still loads — purely additive optional fields need no version bump under this codebase's tolerant-parse convention. **The one thing to probe rather than assume is the stencil clip cap under a non-axis-aligned normal**: `clipCap.ts` is not unit-tested (verified F5 + throwaway-Playwright only), and its documented failure mode is *silent* — get the stencil state wrong and the model simply renders uncapped, with no error anywhere. Same class of risk as the split-view item's own stencil note, and worth probing once for both.

   **Phase 2 (S–M) — derive a plane from picked geometry**, the piece that makes Phase 1 usable rather than merely more general (typing a normal vector by hand is not what "clip along this face" means). Two sources, and they differ sharply in cost:

   - **From a picked planar face** — nearly free now that `inspect` reports `planeOrigin` (the OCCT-computed plane origin it used to discard; see `CLAUDE.md`'s "Agent feedback tools" section). `facePlane` already returns exactly `{pt, nl}`.
   - **From three picked vertices** — needs something that genuinely does not exist: *point selection currently feeds nothing but Parts and Annotations.* Every op-draft consumer filters for `volume`/`surface`/`line` only, and no op resolves a `point-N` id to a coordinate on either side of the boundary. The mechanism is closer than that sounds, though — `main.ts`'s `collectSnapPoints()` already harvests live world-space positions from `point-N` sprites for the snapping feature; it collects *every* point rather than the selected ones. Filtering that by the current selection plus `THREE.Plane.setFromCoplanarPoints` is the whole implementation.

   **Phase 3 (M) — a named, persisted plane entity**, which is what makes this a Tier 4 item rather than a Tier 2 one. A `plane-N` id namespace and a sixth sidecar (`<model>.planes.json`, following the five existing ones' tolerant-parse shape), with plane-bearing ops able to reference a plane id instead of inline vectors. **The design question to settle first, because it determines whether this interacts with entity-id rebinding at all: store the resolved vectors, or a live reference to the face the plane came from?** Recommendation: **store resolved vectors**, with the provenance (which face it was derived from) recorded as optional metadata only — matching the convention `align`'s `to` coordinate already established deliberately ("store resolved values, not live references"), and keeping planes entirely out of `entityRebind.ts`'s id-drift machinery. A live face reference would need rebinding on every topology-changing op, for a feature whose whole value is stability.

   **This does not reopen the sketching non-goal.** A construction plane is a *placement* for the parametric profile ops that already exist — it removes retyping and enables "clip along this face", and every op it feeds still takes numeric, expression-capable fields. It adds no click-to-draw geometry and no constraint solver, which is what Non-goals rejects and why that rejection stands.

   **Two smaller findings worth recording here so they aren't rediscovered:** what AutoCAD calls a UCS is a plane *plus an in-plane frame*, and this codebase already has both conventions — `inPlaneBasis(normal, up)` (deterministic, user-anchored) and `planeBasis(axis)` (arbitrary perpendicular). `sectionSolids` currently uses the arbitrary-phase one, which is fine for a trimmed boolean result but would need `inPlaneBasis` semantics for any work plane meant to carry a stable 2D coordinate frame. And **`gp_Pln` is used nowhere in this codebase** — every face is built via the `BRepBuilderAPI_MakeFace_15(wire, true)` wire overload, so the plane overload is unprobed should a true infinite-plane primitive ever be wanted.

20. **Decompose imported geometry into parametric primitives** (*issue #34*) (**L** overall; **S–M** for Phase 1 alone). Feature recognition — take an imported STEP whose geometry is opaque, identify that a solid *is* a box or a cylinder, and re-express it as a primitive whose side length or radius is a named variable the user can then edit.

   **The parametric half is already complete end to end** — variables, per-op `exprs`, `resolveEditOps`, and `set_variables` (which already writes ops and variables together) all exist and would need no change. Emitting `{op: "addBox", size: [20,10,5], exprs: {"size[0]": "L"}}` alongside a `ParamVariable{name: "L", …}` is already a supported shape. **What is missing is (a) deriving primitive parameters from a B-rep at all, and (b) any way for ops to replace the source geometry rather than add to it.**

   **Phase 1 (S–M, independently valuable) — return the surface parameters `inspect` already computes and discards.** `entityFacts.ts` reads `BRepAdaptor_Surface_2(face, true).GetType()`, maps it to a `SurfaceType` label, and deletes the handle — so `surfaceType: "cylinder"` tells a caller a face is cylindrical and *nothing else*: no radius, no axis direction, no axis location, no cone half-angle, no torus major/minor. Adding them is one accessor call per face on a handle that is already in scope. **This needs a live-WASM probe before it can be estimated, per this file's own rule**: `.Cylinder()`, `.Sphere()`, `.Cone()` and `.Torus()` are called *nowhere* in this codebase, so their overload names, return-handle shapes, and sub-accessor names are entirely unrecorded. `BRepAdaptor_Surface`, `gp_Cylinder`, `gp_Cone`, `gp_Sphere`, `gp_Torus` and `gp_Pln` are all green in the manifest, which — as ever — is necessary but not sufficient. **The probe and its verification bar both already have a precedent to copy**: `facePlane`'s `.Plane()` → `Location()`/`Axis().Direction()` is the shape (note every sub-accessor returns its own handle needing `.delete()`), and `measure_exact`'s radius path sets the bar — not "the calls don't throw" but a round trip against known parameters: `addCylinder(radius: 3, axis: A)` → `inspect` its lateral face → assert the radius is exactly `3` and the axis matches `A`. Worth probing `BRepAlgoAPI_Defeaturing` in the same pass — green, completely unused here, and exactly the "remove a recognized feature" primitive a later phase would want.

   **Phase 2 (M) — a read-only recognition report, facts only, emitting no ops.** Per solid: the face inventory by surface type, a candidate primitive fit, and **the fit residual** (maximum deviation between the fitted primitive and the real faces). The residual is what keeps this a fact rather than a verdict, per `describeCapabilities()`'s `verdictConventions` — a caller decides whether 0.002 mm of deviation means "this is a cylinder". **This phasing is not a general preference, it is the same rule the closed "Mesh → B-rep promotion" item was held to, for the same reason**: a mis-recognized primitive that silently replaced real geometry would feed `get_mass_properties`/`measure_exact` confidently-wrong numbers — the same misleading-false-result failure mode that gated mesh promotion behind a report, and that `compare_models` avoids by publishing its match residuals instead of a verdict. Natural home: extend `collectAllEntitySignatures`, which already performs exactly the right deterministic per-entity walk in the right id order but records only `{id, kind, centre, measure}`.

   **Phase 3 (L) — actually emit ops and variables.** Two structural blockers, neither of them a matter of effort:

   - **`AddBoxOp` has no orientation at all** — it is `{center, size}`, full stop. A recognized box that is not axis-aligned cannot be expressed as one op; it needs `addBox` + a follow-on `rotate`, or a new oriented-box op. Related trap: **`center` does not mean the same thing across primitives** — box/sphere/torus take the geometric centre, while cylinder/cone/prism/wedge take the **base** centre, so a fitted cylinder's axis location must be converted rather than passed through.
   - **Nothing in the op model can replace the base shape.** `applyEditsBRep` folds ops over `readShape(sourceFile)`; all 44 op kinds either append or operate on solids already present; there is no "empty base" concept, since `routeFile()` is a pure function of file extension computed once per document-open. Two viable shapes, both new: a new `TOPOLOGY_CHANGING` op kind that suppresses base solids (which then has to interact with `entityRebind.ts`), or **the `promote_mesh_to_brep` model — analyze, and write a brand-new file** whose content is the recognized primitives. **The export model is the recommended v1**, and for exactly the reason recorded when mesh promotion made the same call: it sidesteps in-place reclassification entirely, and the written file is an ordinary document from the moment it exists.
   - Worth noting: **no code path anywhere in this repo currently produces an expression string from geometry.** `exprs` is only ever authored by a human typing in the panel, by an agent's raw JSON, or by a hand-edited sidecar — and `parametricScript.ts` deliberately does the *opposite*, baking and stripping `exprs` after compiling. The plumbing needs no change, but this would be its first programmatic producer.

21. **Fit construction planes/primitives to a mesh/scan region** (**S–M**, no live-WASM probe needed). A local sibling project, HCAD, region-grows across smooth triangles (a dihedral-angle gate, capped at a fraction of the mesh size) from a clicked seed triangle, then fits the simplest of plane / cylinder / sphere to the region — point-PCA for a plane, a normal-covariance axis plus a Kasa least-squares circle fit for a cylinder, a 4×4 Kasa fit for a sphere, all on top of a small hand-rolled 3×3 Jacobi eigensolver — with documented tie-breaking so a flat face doesn't win as a huge, technically-also-fitting sphere.

    **Fills a real, specific gap between two existing items rather than duplicating either.** item 19 ("Arbitrary and reusable construction planes")'s Phase 2 derives a plane only from an *exact* B-rep face or from 3 picked `point-N` vertices — nothing fits a plane to noisy, unstructured mesh triangles the way an imported scan needs. item 20 ("Decompose imported geometry into parametric primitives") is scoped entirely to exact B-rep `BRepAdaptor_Surface` accessors, which don't exist for a mesh source at all — a raw STL/OBJ/PLY/glTF triangle soup has no analytic surface to query, only points.

    **Pure TypeScript math, operating on data this codebase already has parsed** — the region-growing walk and the plane/cylinder/sphere least-squares fits need no OCCT/Gmsh/meshio++ call at all, only the mesh triangle/adjacency scaffolding `meshComponents.ts` already builds for `meshHeal.ts`/`silhouetteEdges.ts`. That is what lets this item, unusually for Tier 4, honestly skip a live-WASM probe — there is no WASM binding involved anywhere in it.

    **Phase 1 (S) — facts only, emitting no ops**, mirroring item 20 Phase 2's own "facts, not a verdict" framing to avoid the identical misleading-false-result risk a wrongly-accepted fit would create: given a seed triangle (or a selected mesh region), return the fitted primitive's kind, parameters, and the fit residual (max deviation between the fit and the real triangles) — a caller decides whether the residual is small enough to trust. **Phase 2 (S), gated on item 19 Phase 3's `plane-N` sidecar existing** — turn an accepted plane fit into a genuine stored construction plane, or an accepted cylinder/sphere fit into parameters for the existing `addCylinder`/sphere-primitive ops (as a *new* body at that location, matching every other primitive-creation op's append-only convention — never a silent reclassification of the source mesh, the same restraint the closed "Mesh → B-rep promotion" item and item 20 both already apply).

22. **2D technical drawings via triangle-based hidden-line removal** (**M**, un-blocks a stated Non-goal — see the edited bullet below). A local sibling project, HCAD, solves the identical problem this project's own Non-goals section calls kernel-blocked — an orthographic hidden-line drawing, visible edges solid and occluded edges dashed — with **no B-rep HLR API at all**. Its projection engine projects every triangle into 2D through a view basis once, buckets them into a uniform 2D grid, then tests each feature edge's visibility at a fixed number of sample points along its length against just the triangles in its own grid cell — turning an O(edges × triangles) hidden-line test into something fast enough to project a real part in milliseconds, by its own account. Each edge comes out split into visible and hidden runs, rendered solid and dashed respectively into an SVG sheet.

    **Why this genuinely un-blocks the stated Non-goal, rather than resembling a workaround already ruled out**: the Non-goals bullet is explicit that the blocker is OCCT's `HLRBRep_*` family being unbound in this WASM build, and that the one surviving API, `HLRAppli_ReflectLines`, was probed and rejected on the *quality* of its drawing, not on availability. The comparison project's technique calls no B-rep HLR API whatsoever — it operates purely on tessellated triangles, which is exactly the representation this codebase already has for every source (B-rep via `tessellateByGroup`, native for mesh formats). The blocker it sidesteps is the same blocker this project has recorded; the workaround is kernel-agnostic, so it applies here unchanged.

    **Materially cheaper than a from-scratch implementation, because most of the surrounding machinery already shipped for SVG silhouette export.** `src/svgSilhouette.ts` already has a `ViewBasis` type, the `SVG_VIEWS` view-direction packet, and a correct-unit/-scale SVG serializer; `src/silhouetteEdges.ts` already classifies front/back-facing triangles per direction via triangle adjacency — the silhouette-only special case of the same visibility problem this item generalizes. What's missing is specifically the grid-bucketed, per-edge visible/hidden run-splitting step.

    **Phase 1 (M)** — a new pure module (e.g. `src/hiddenLineRemoval.ts`, vscode/OCCT/THREE-free, unit-testable against hand-built triangle fixtures the same way `meshTopology.test.ts`/`svgImport.test.ts` are) implementing the grid-bucketed edge-visibility test, feeding `svgSilhouette.ts`'s existing SVG writer extended with a dashed stroke for hidden runs — the one genuinely new SVG-writer capability needed. Single view, no dimensions, mirroring `export_svg_silhouette`'s exact scope, gate, and dual B-rep/mesh-source path — the natural shape for a sibling MCP tool, `export_technical_drawing`. **Phase 2 (L, explicitly not committed to in this pass)** — multi-view sheet layout and dimensions, the kind of machinery a snap-target/dimension-resolution system would need. This starts to resemble "drafting application" territory the way full interactive sketching does (an explicit, deliberate Non-goal already), so it needs its own scoping discussion — e.g. auto-generated fixed-view sheets with no interactive dimension placement — rather than being assumed to follow automatically from Phase 1.

    **No live-WASM probe needed, for the same reason item 21 doesn't need one**: the whole point of this technique is that it touches no OCCT call at all.

23. **Selector synthesis — persist a re-executable query instead of a positional entity id** (**L** overall; **M** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io), which faces the same topological-naming problem every history-based CAD faces and answers it in a way this codebase has not considered: **it never persists an entity reference at all.** A pick in its viewport is converted into a *source-code query expression* that re-derives the selection from scratch on every rebuild. There is no id to go stale, because there is no id.

    **This is a genuinely different answer from the one already shipped here, and it complements rather than replaces it.** CAD-Preview persists positional `face-N`/`edge-N`/`solid-N` ids and repairs them after the fact with `entityRebind.ts`'s best-effort geometric match (bbox-centre nearest-neighbour with an area/length tie-break) — a *recovery* mechanism that runs after topology changed and, by its own documented admission, "can't distinguish 'this face moved' from 'this face was deleted and a new coincidental one appeared nearby.'" A stored query is a *prevention* mechanism: it never needed to survive renumbering because it re-resolves against whatever the model currently is. The two compose — a query that resolves to exactly one entity is authoritative, and the existing rebinding stays as the fallback for a stored raw id, so nothing already persisted has to be migrated.

    **Four pieces of portable machinery, in the order they'd be built:**

    - **Build-time classification buckets.** Every op already knows, at the moment it runs, which faces it produced and what role each plays — an extrude's start cap, end cap, and side walls; a fillet's generated bands. FluidCAD records these into named buckets (`endFaces`, `sideFaces`, `capEdges`, …) and an accessor resolves against the live array. **This phase is independently valuable even if nothing else here ships**, because it is a strictly better namespace than global geometric matching for exactly the ids that drift most, and it is additive to `occtOperations.ts`'s existing per-op functions.
    - **A synthesis ladder**, tried in order and stopping at the first candidate that resolves: whole bucket → bucket plus an induced predicate → a scene-wide predicate → bucket indices. The ladder matters because the top rungs are the stable ones and the bottom rung is what today's positional ids already are, so the fallback is never worse than the status quo.
    - **Constant-free-first induction.** A greedy set-cover over candidate predicates, with restarts to escape a myopic opener, that **prefers predicates carrying no baked-in numeric constant** — `edge().line().below("xz")` beats `edge().onPlane("xz", -34.641…)` even when the latter needs fewer terms, because a qualitative/datum predicate survives the dimension edits that silently break a literal. This is the single most transferable idea in the whole approach and the one that makes stored queries meaningfully better than stored coordinates.
    - **Oracle verification.** Every candidate is *executed* before being accepted, and kept only if it resolves to exactly the picked set. This is what makes a synthesized selector trustworthy rather than plausible, and it is the same discipline this codebase already applies when it re-`inspect`s a rebound id and compares geometry rather than trusting the match.

    **One correctness gate worth carrying over verbatim: bindability.** A pick whose producing op was a pattern instance or a replayed op cannot be safely named, because the name would be ambiguous across instances — FluidCAD detects this and routes those picks to a scene-wide predicate instead. CAD-Preview has exactly this shape today (`patternLinear`/`patternCircular` append `count - 1` copies; the mesh engine tags them `pattern-{K}`), so the same check applies directly, and getting it wrong would produce a selector that silently resolves to the wrong instance — the misleading-false-result failure mode this file gates other items behind a report for.

    **Scope discipline this item must state, because it is the obvious way to get this wrong:** the query language should stay a small predicate AST persisted as JSON in the existing `.edits.json` sidecar, resolved by the same tolerant gate `validateEditOp` already is — **not** a new expression language and **not** executable code. This codebase already rejected `eval()` on CSP grounds for `paramExpr.ts` and hand-wrote a recursive-descent evaluator instead; a selector AST is the same call. It also shares a predicate vocabulary with item 3's selection filters, which is why that item should ship first and this one should reuse its vocabulary rather than inventing a second.

    **Verification**: the induction, the ladder, and the AST resolver are all pure and unit-testable headless against hand-built entity-fact fixtures (no WASM) — the oracle-verification step is what needs the live kernel, and its bar is the one `measure_exact`'s own radius path set: not "the selector resolved" but "the selector resolved to the *same* entity, confirmed by comparing `inspect`-reported geometry against the pre-edit baseline with zero delta," exactly as the closed entity-rebinding work already verifies itself in `npm run mcp:smoke`.

24. **Cheap thin-wrapper ops mined from FluidCAD** (**S–M** for the set; each independently **S**). *Every one of these **needs live-WASM verification** of its overload suffix before it can be estimated*, per this file's own rule — they are listed together because each is a handful of lines over an OCCT class this build already exposes, not because they should ship as one change.

    - **Distance-angle chamfer.** `chamfer` currently takes one `distance`. FluidCAD gets the asymmetric and distance-angle variants from the *same* `BRepFilletAPI_MakeChamfer` instance this codebase already constructs, via `.Add(d1, d2, edge, face)` and `.AddDA(d, angleRad, edge, face)` beside the `.Add_2(amount, edge)` already in use. Roughly three lines plus two new optional `EditOp` fields.
    - **`shell().join(...)` styles.** `BRepOffsetAPI_MakeThickSolid`'s join mode is already passed as `GeomAbs_JoinType.GeomAbs_Arc` in the verified 9-argument call recorded in `CLAUDE.md`; exposing intersection/tangent as an option is a parameter, not a new API.
    - **`draft(angle, faces)`** via `BRepOffsetAPI_DraftAngle`. Note explicitly that FluidCAD's implementation auto-derives the neutral plane from the bounding box's min-Z face with a hardcoded +Z direction — a real limitation to *improve on rather than copy*, since this codebase already has `facePlane` and, pending item 19's Phase 2, a way to derive a plane from a picked face.
    - **Construction geometry (`.guide()`).** A boolean flag on any 2D profile/curve op marking it reference-only: rendered, pickable, excluded from profile resolution. Trivial, and it pairs with the wireframe build ops already shipped.
    - **Inscribed-vs-circumscribed polygons**, **a slot built around an existing edge** rather than from length+radius, and **midplane/midaxis references** (a plane halfway between two planes, an axis halfway between two axes) — each a small addition to an existing op family.

    **Verification**: each op follows the established pattern — a probe against the live WASM to pin the overload suffix (this file's standing requirement, and `CLAUDE.md` records dozens of precedents), then round-trip coverage in `npm run mcp:smoke` asserting the produced geometry matches an analytically-known value, the bar `addCylinder`/`measure_exact` already set.

25. **Substantial new feature ops mined from FluidCAD** (**L**, phased; not estimable per-op until probed). The genuinely large capabilities, listed so the opportunity is on record with an honest size attached rather than mistaken for the cheap set above. Each is ~400–1200 lines of real geometry work in the source project, **not** a wrapper: **`wrap()`** (true surface *development* of a flat sketch onto a cylinder or cone — length-preserving, not projection — then thickening along the surface normal, with emboss/engrave/standalone variants; the most original capability in that codebase); **`rib()`** (build a rib from an *open* spine sketch, extruded until it meets surrounding solids, with end-blending into adjacent walls); **`.thin(offset)` across the whole sweep family** (thin-walled solids directly from an open or closed profile, with dual offsets); **loft `.guides()` plus `.startCondition`/`.endCondition`** (guide rails the surface must ride, and normal/tangent takeoff with a signed magnitude — a real quality jump over plain `ThruSections`, which is what this codebase currently uses); **extrude/cut up-to-a-face terminators** (`extrude(face)`, or first/last intersecting face found by filter — the "up to next" every mainstream CAD has); and **`.pick(regions)` + `.drill()`** for choosing which enclosed regions of a multi-region sketch a feature consumes.

    **Where CAD-Preview is already ahead, recorded so this item is read as a gap list and not a scoreboard**: FluidCAD has **no** assemblies, mates, or joints (its `part()` is a fusion-isolation namespace with a name, nothing more), no box/cone/torus primitives, no variable-radius or face fillet, no pattern-along-path, no interference detection, no model comparison, no mesh health or mesh→B-rep promotion, no format breadth beyond STEP/STL/BRep, and essentially no validation or manufacturability analysis. Several of those are shipped capabilities here. The transfer is one-directional for this item only.

    **Sequencing**: nothing here blocks anything else in this file, and each op is independently shippable. If any single one is picked up first, `.thin()` is the recommendation — it applies to five existing ops at once rather than adding a sixth.

### Tier 5 — Externally gated

*Admission: the work is understood and scoped, but is blocked on a decision or an event outside this repository — a license choice, an upstream merge, or a dependency that does not yet exist. Listed so the blocker is on record and re-scoping is unnecessary when it clears; **not** estimable until it does.*

26. **Open OpenSCAD (`.scad` / `.csg`) files** (*issue #35*) (**M** for the recommended path; **L** and license-affecting for the maximal one).

   Three genuinely distinct approaches, in ascending cost. **The recommendation is (a) plus (b); (c) should not be chosen by default.**

   - **(a) Parse `.csg` only — no new dependency, no license change.** OpenSCAD's `.csg` export is *the fully evaluated model*: loops unrolled, modules inlined, variables literalised, `if` branches collapsed, every transform emitted as an explicit 4×4 `multmatrix`. **There is therefore no language to implement** — FreeCAD's own `.csg` lexer has 33 reserved words and no arithmetic, no `if`/`for`, no variables, because none survive into the format. Most nodes (`cube`, `sphere`, `cylinder`, `polyhedron`, `union`, `difference`, `intersection`, `group`, `multmatrix`) map directly onto primitives and booleans this codebase already has, with graceful degradation on the rest — the same convention every unresolvable operand in this codebase already follows.
   - **(b) Shell out to a user-installed `openscad` binary** for `.scad` → `.csg`, then (a). Still zero bundled megabytes and **no license propagation — a separate process is mere aggregation, not linking**. Degrades to a clear `supported: false` when the binary is absent, structurally identical to how `render_snapshot` already handles a missing Playwright. This is precisely FreeCAD's own architecture.
   - **(c) Bundle `openscad-wasm`.** Technically attractive: it is under the official `openscad` GitHub org, actively committed to, ships a dedicated **Node** build, needs no `SharedArrayBuffer`, and drives through an Emscripten MEMFS plus a literal `callMain(argv)` — structurally identical to how this codebase already drives Gmsh. **But it costs roughly 8–14 MB uncompressed (plus ~8 MB more if `text()` is ever to work), and it permanently upgrades the shipped `.vsix` to GPL-3.0-or-later.** CGAL is GPLv3+/LGPLv3+ with no GPLv2 option, and Manifold is Apache-2.0, which the FSF holds GPLv2-incompatible; OpenSCAD's own playground documents shipping its build as GPLv3 for exactly these reasons. **This is not a conflict for a GPL-2.0-*or-later* project** — the "or later" grant is precisely the escape hatch — **but it is a one-way door, and it would be the first bundled dependency to force it** (gmsh-wasm is GPL-2.0-or-later and OCCT is LGPL-2.1-with-exception; both are GPLv2-compatible today). See item 27, which converges on the same decision from a different direction.

   **One correctness decision must be settled before any option, and getting it wrong reproduces the same misleading-false-result failure mode item 20 describes.** **OpenSCAD's `cylinder` is a faceted prism, not an analytic cylinder.** `$fn`/`$fa`/`$fs` survive into `.csg`, and the common default `$fn = 0` means *unresolved* — the consumer must reimplement OpenSCAD's own segment-count rule from `$fa`/`$fs`. Mapping a `$fn = 10` cylinder onto an exact `BRepPrimAPI_MakeCylinder` yields a solid that silently disagrees with OpenSCAD's own STL by the chord error, and `get_mass_properties`/`measure_exact` would then report confidently-wrong numbers. FreeCAD's answer is an explicit dial — a `useMaxFN` preference (default 16: below it build the real polygon, above it treat as circular) — worth copying, though note its default silently favours exactness over fidelity.

   **Other limits to record now rather than discover later:** `.csg` prints at default stream precision (~6 significant figures), a hard accuracy ceiling on anything reconstructed from it, and rigid transforms come back with float noise (`rotate([90,0,0])` → `2.22045e-16`), so exact axis alignment must be recovered with a tolerance. A `multmatrix` is **not** guaranteed rigid, since `scale`/`mirror` collapse into it. Module names are destroyed — every user module becomes an anonymous `group()`. `hull` and `minkowski` have no OCCT equivalent at all (FreeCAD round-trips them through the binary and accepts triangles). `text()` carries a font *name*, not outlines — and the official WASM build ships with "no support for fonts". `import`/`surface` reference external files, so `.csg` is evaluated but not self-contained. And the format is documented poorly, versioned inconsistently, and framed by its own man page as "mainly used for debugging and testing" — treat it as a de-facto format with no stability guarantee.

   **Ruled out, with evidence: writing a JavaScript OpenSCAD evaluator.** Every prior attempt is dead — the JSCAD translator is deprecated and *its own designated successor is also deprecated* — the one live from-scratch effort is Rust with acknowledged silent divergences from the reference implementation, and OpenSCAD's `$`-variable **dynamic** scoping alongside ordinary lexical scoping is a documented design landmine that upstream contributors themselves call one of the language's worst mistakes. Upstream also closed its own bytecode-interpreter rewrite as not planned. This is the same "shipping the weak two-thirds of the feature" reasoning that rejected a constraint solver in Non-goals.

27. **Robust volumetric meshing from a skin mesh** (*issue #6*) (**S** for Phase 0; **M** for Phase 1; **L** and blocked for Phase 2).

    **The framing correction that matters most: this already works today for clean input.** `generate_mesh` on an STL/OBJ/PLY/glTF source already produces a tetrahedral volume mesh — `gmshService.ts` runs `classifySurfaces(stlAngle)` → `createGeometry()` → `addSurfaceLoop` → `addVolume` and meshes it in 3D. **The gap is robustness, not capability**: that pipeline needs a watertight, manifold, reasonably clean boundary, and it fails or produces garbage on the meshes people actually have — scans, sculpts and print-ready STLs with holes, self-intersections, non-manifold edges and duplicated geometry. The *diagnostic* half is already done too: `check_mesh_health` reports free edges, non-manifold edges, degenerate faces, and whether an OCCT sewing ladder closes. **What is missing is the repair path between the diagnosis and the mesher.**

    **Status of the route named in the issue, verified against the checkout at `/home/vicente/src/meshioplusplus`:**

    - **SDF is complete and JS-reachable — but on an unmerged branch.** `computeSdf`, `sampleDistance`, `distanceToSurface`, `surfaceWatertightCheck`, `grid` and `voxelize` are all in `src/wasm/index.d.ts` with full options (voxel *and* octree structure, unsigned / pseudonormal / winding-number signing, narrow band), and v9.25.0's changelog calls it "Signed distance fields, completed." It lives on local branch `sdf`, **38 commits ahead of master and not merged**. So this item is gated only on that merge (the former "item 1" dependency-bump half closed on 2026-08-24 — @meshioplusplus/wasm is now 10.9.0) — which is why it is last, not because the work is unclear.
    - **MMG is entirely absent from meshio++.** No dependency, no WASM target, no build-system reference, no TODO, no roadmap entry. The only two occurrences in the whole repository are an unrelated analogy in the changelog and a 2021 comment inherited from Python meshio about medit keywords. **There is no WASM MMG to call.** Cross-compiling it would follow meshio++'s own pinned-dependency pattern (HDF5, netcdf-c, cgnslib) but is upstream work in a different repository, not work here.
    - **meshio++ has no surface → volume operation of any kind**, and says so plainly in its own roadmap: "Every operation transforms a mesh you already have; nothing creates one." `simplexify` never raises topological dimension; `extractSurface` goes the other way.
    - **Licence check needed before anything is bundled**: MMG is (to be confirmed) LGPL-3.0-family, which — exactly like item 26's option (c) — would be GPLv3-compatible but not GPLv2, forcing the same one-way `.vsix` license upgrade. **Two independent roadmap items converge on the same decision; it should be made once, deliberately, rather than twice by accident.**

    **Phase 0 (S, ungated — no dependency on the meshio++ merge, and independently validated by a working reference implementation) — a purely topological repair pass, no SDF and no voxelization at all.** A local sibling project, HCAD, ships exactly this as its own first, cheap repair pass: weld near-duplicate vertices at a bbox-relative tolerance, drop degenerate and duplicate triangles, and ear-clip-fill only *small* boundary loops (its own cutoff is 64 edges) — conservative by design, reporting a still-open larger hole rather than papering over it. This closes the gap between `check_mesh_health`'s existing diagnostic (from the closed "Mesh → B-rep promotion" item, already reporting free/non-manifold edge counts) and the meshing pipeline: extend `meshHeal.ts`/`meshComponents.ts` with an analogous conservative repair function, reported the same "facts, plus exactly what was fixed, never silently applied" way `checkMeshHealth` already reports facts, feeding the *existing*, already-working `classifySurfaces`/`addSurfaceLoop`/`addVolume` mesh-to-volume pipeline unchanged. Ships independently of, and much sooner than, the SDF-gated phases below — it needs neither the meshio++ `sdf` branch merge nor a dependency bump (the former "item 1" closed — meshio++ is current). A second sibling project's mesh-import path independently validates the same shape of fix: [SindriCAD](https://github.com/MakerViking/sindricad)'s own cleanup pipeline for imported STL/OBJ meshes (`sidecar/builder.py`'s `_refacet_clean`/`_drop_debris`/`_unify_body`/`_sew_mesh_file`) runs the identical weld-then-sew sequence before treating an imported mesh as editable — a second, independently-built confirmation that this conservative repair shape, not a full SDF remesh, is the right first phase.

    **Phase 1 (M, gated only on the SDF merge) — repair, then reuse the existing mesher. No MMG required, and this is the part worth doing first among the SDF-gated phases.** An SDF is watertight and manifold **by construction**, regardless of how broken the input was: holes close, self-intersections resolve, and the winding-number signing mode handles the genuinely ugly cases. So `computeSdf` → `isosurface` at level 0 already yields a clean closed triangle surface — which is exactly what the *existing* `classifySurfaces`/`addSurfaceLoop`/`addVolume` path needs. The whole feature is: `check_mesh_health` says the boundary is not closed → offer an opt-in repair pass → hand the repaired surface to the pipeline that already works. **Opt-in and clearly reported, never automatic**, because the cost is real: an SDF resamples at a grid resolution, so sharp edges round off and the result is an approximation of the input, not the input — which must be stated in the output rather than silently applied.

    **Phase 2 (L, blocked on MMG existing as WASM at all)** — true level-set / anisotropic remeshing for genuine control over element quality and grading, rather than accepting whatever the isosurface resolution produced.

    **Independent validation of the SDF approach in Phase 1/2, and concrete pitfalls worth keeping on hand before implementing against the meshio++ `sdf` branch once merged.** The same local sibling project, HCAD, independently built and shipped the identical rasterize → signed-distance-field → isosurface technique (its own voxel "Solidify" path) for the identical problem — a real, measured validation that the design above is sound, not merely plausible. Its own documented pitfall trail: a sign-convention bug (its level-set surfacer treats the *positive* region as solid — inverted once, silently producing a near-bounding-box block instead of the real shape, until a regression test specifically checking "the output fills a small fraction of its bbox, not most of it" caught it); voxel stair-stepping on the resulting surface, fixed only by combining an exact near-surface point-to-triangle distance band, center-anchored (not corner-anchored) trilinear sampling, and a post-simplify pass to collapse the sliver edges the marching step introduces; and a hard limit — an opening wider than roughly 2 voxels leaks the flood fill and leaves the interior hollow rather than filled. For scale, its own numbers: a real 149k-triangle scan solidifies in ~1.4 s at a 96³ voxel resolution and ~3.8 s at 160³, with the 96³ result needing a decimation pass afterward (~275k output triangles) before it's a reasonable meshing input.

    **A cheaper alternative already reachable at merge time, worth recording:** `voxelize(fill="inside")`, or `computeSdf` + `crop`, yields a **hexahedral voxel occupancy mesh** directly — a staircase approximation rather than a conforming mesh, but a legitimate answer for some FEM workflows, and it needs nothing beyond the merge.

28. **Native 6-DOF (SpaceMouse-class) input for the viewport** (**M–L**, externally gated on a native-module packaging decision). Comparing against [SindriCAD](https://github.com/MakerViking/sindricad): its Rust layer (`src-tauri/src/spacemouse.rs`) reads a 3Dconnexion SpaceMouse via raw HID (its webview has no WebHID access under WebKitGTK on Linux), ranking candidate devices by **HID usage page/usage** (Generic Desktop / Multi-axis Controller, `0x01`/`0x08`) rather than vendor-ID allowlisting — fixed this way after a vendor-only match once misidentified an ordinary Logitech mouse as a SpaceMouse and fed its motion into the 3D camera.

    **The constraint that forced SindriCAD's Rust-side workaround doesn't apply to CAD-Preview's own layer split, which changes where this would live.** A VS Code webview has no WebHID either (the same browser-sandbox gap), but CAD-Preview's **extension host** is a plain Node.js process, not a browser sandbox — the same process that already runs OCCT/Gmsh/meshio++ WASM. A native HID addon could in principle read the device there and pipe motion deltas to the webview over the existing `postMessage` channel (`Viewer.orbit`/`pan`/`dolly`, already exposed and unit-tested in `cameraControls.ts`), mirroring the OCCT-in-host/Three.js-in-webview split this codebase already has, with no Tauri-style native shell needed.

    **What actually gates this, and why it's Tier 5 rather than Tier 2**: every WASM dependency this codebase bundles today (OCCT, Gmsh, meshio++) is architecture-independent by construction — one `.wasm` file runs on any host CPU/OS. A native HID addon is not: it needs a prebuilt binary per OS/CPU-arch combination the `.vsix` targets, a real packaging model change (platform-specific `.vsix` publishing, which this extension doesn't use today) versus the current single universal package. That's a decision to make deliberately, not a probe to run — hence Tier 5, alongside the OpenSCAD and MMG items' own license-gated packaging decisions, rather than a straightforward Tier 2 estimate.

    **If ever built, the one concrete technical lesson worth carrying over verbatim**: device discovery by HID usage-page/usage, not vendor ID — the exact bug SindriCAD's own comment records hitting once.

### Tier 6 — Documentation and onboarding

29. **Narrative, screenshot-illustrated tutorials — a FluidCAD-style gallery** (**M** overall; **S** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io)'s `docs/tutorials/` (13 pages, each building one real part through numbered `Step N` sections — Setup → Steps → Full code → "What you practiced" — with a screenshot after nearly every step): `doc/getting-started.md` is already a large, thorough **reference** (one section per UI panel, with tables and screenshots) but has nothing **narrative** — no single page walks a reader through building one real part end to end. `doc/mcp-server.md`'s one bolt-circle example is the closest thing to a worked example this repo has today, and it's a single JSON snippet, not a tutorial.

    **The one real structural mismatch, and how to design around it rather than fight it.** FluidCAD tutorials start from an empty code file; CAD-Preview has no such thing — `CustomReadonlyEditorProvider` only ever opens an *existing* CAD file, every creation op **appends** to whatever solids are already present, and there is no "delete body" op. The fix is not a new capability, just a naming convention: start every tutorial from `examples/STP/block.stp`, a real, tiny (3×4×5 mm) seed solid already shipped in the repo, and make the tutorial's first added primitive fully enclose the seed's bounding box — two separate, non-unioned solids in the same compound still z-buffer-occlude correctly, so the seed is genuinely invisible in every subsequent shaded render with no extra op needed (confirmed against the live WASM: the seed always stays its own separate `solid-0` group in the compound — creation ops append, they never fuse). Worth stating once, briefly, in the tutorials themselves as a real, useful CAD-Preview technique for working around the append-only model, not hidden as a trick.

    **Phase 1 (S) — the pages and cross-linking, using only existing screenshots plus text/JSON.** A new `doc/tutorials/` section (an index/gallery page + one page per tutorial, wired into `doc/.vitepress/config.mts`'s `nav`/`sidebar` alongside the existing `User Guide` group), each page following FluidCAD's proven shape adapted to this tool: H1 + intro ("covers X, Y, Z"), a **Starting point** section naming the seed file, numbered `## Step N` sections (concrete UI actions in the same "1. … 2. … 3." mini-procedure style `getting-started.md` already uses throughout), a closing **Full operation list** section (the cumulative op-JSON array — doubles as a literal `apply_edit_ops`/`run_parametric_script` payload, reinforcing that the interactive UI and MCP are two views of the same op model), and a **What you practiced** recap. Five concrete candidates, chosen to cover the feature breadth with minimal overlap: a **Bracket** (primitives + fillet + counterbore holes — the closest analog to a FluidCAD "first tutorial"); a **Parametric bolt-circle flange** (variables + circular pattern, plus a pattern-the-tool-then-subtract technique for "patterning a hole" — there is no direct op support for patterning a cut feature, only for solids, so this is worth a doc callout on its own); a **Sketch/extrude/shell enclosure** (2D profile sketch → extrude → shell, the one whole workflow family with zero narrative coverage today); **Prepare and mesh a part for FEA** (Parts + FE Mesh + Kratos MDPA export — this extension's actual raison d'être, not just a features tour); and **Model with an AI agent via MCP** (a narrated `mcp-server.md`-style conversation that builds the *same* bracket as the first tutorial, reusing its screenshots with a "built by an agent instead of by hand, identical result" framing — needs no new fixtures at all). This phase alone — reusing existing `doc/public/screenshots/*.png` wherever a step already matches a shot panel, text/JSON elsewhere — already closes the narrative gap with zero pipeline risk.

    **Phase 2 (S–M) — real per-step screenshots through the existing pipeline, not hand-drawn**, per `CLAUDE.md`'s standing "screenshots are generated, never hand-captured" rule. Investigated in detail, not just assumed: `scripts/screenshots/fixtures-entry.ts` currently produces one *global* fixture set from `bull.stp` with no per-shot parametrization, and `capture.mjs`'s `SHOTS` array is a hand-written `{file, setup(page), target}` list — both additive-friendly (no rewrite needed) but genuinely new work. `fixtures-entry.ts` needs extending to call the already-4-parameter `loadBRep(extensionPath, bytes, "step", ops)` with real, cumulative `EditOp[]` arrays per tutorial step; every op's `targets`/`edges`/`profile` ids must be resolved against the *actual* group/edge/face ids `loadBRep` returns for that step, not guessed — a throwaway probe script following this codebase's own established "brute-force probe against the live WASM" convention is the way to get them, exactly as `CLAUDE.md` records doing dozens of times elsewhere for OCCT overload discovery. `capture.mjs` then needs roughly 10 new, purely-additive `SHOTS` entries (flat filenames, matching the existing 100%-flat `doc/public/screenshots/` convention — no subfolder, since only that one directory is ever `mkdirSync`'d today), reusing `populate()`'s exact `geometry → {type:"viewState", view:null} → sleep → tree → sleep` ordering (`CLAUDE.md`'s own documented load-bearing sequence for correct camera framing on first load — skipping the `viewState` post is the exact regression it records happening once already). Playwright 1.62.1 with a matching cached Chromium (revision 1234) are already installed in this dev environment, so the pipeline is runnable here, not just in theory.

    **Verification, stated per this file's own standard**: `npm run build` (the fixture-generator additions type-check) → `npm run docs:screenshots` → **visually inspect every new PNG via the `Read` tool**, not just check the exit code (`CLAUDE.md` records a real, exit-0-but-silently-broken screenshot regression from skipping exactly this once already) → `npm run docs:build` (VitePress's dead-link checker covers the new nav/sidebar/cross-links) → `npm test` as a cheap sanity check that nothing under `src/` was touched. Phase 1 needs none of the WASM/Playwright verification above — it is markdown and nav-config only.

    **Sequencing note**: the op-JSON in each tutorial's "Full operation list" is exactly the kind of block item 30's executable-examples test would run, so writing these pages in the fenced language that item defines costs nothing now and makes every tutorial self-verifying later.

30. **Executable doc examples, and a coverage gate for agent-facing docs** (**M** overall; **S** for Phase 1 alone). Comparing against [FluidCAD](https://fluidcad.io), which maintains a parallel `llm-docs/` tree — one terse markdown file per API symbol plus a handful of concept notes — that its MCP server serves at runtime, and which is held to the real API by two CI gates. CAD-Preview's agent-facing documentation is `describe_capabilities()`' generated output plus hand-written prose in `doc/mcp-server.md`, and **nothing checks either against the code**: `OP_PARAM_DOCS` (`mcpTools.ts`) is already locked to the live op catalog by `mcpTools.test.ts`, but the prose, the parameter examples, and every JSON snippet in `doc/**` are unverified — a renamed field or a dropped op kind would leave a confidently-wrong example in place with every test still green.

    **Phase 1 (S) — execute the examples. This is the cheap half, and it is cheaper here than in the project it comes from.** FluidCAD runs every fenced example block through `new Function` against its real runtime, which works but means the docs execute arbitrary JavaScript. CAD-Preview's `run_parametric_script` format is **declarative with no code execution at all** — a `{variables?, steps}` document compiled by `parametricScript.ts`, which is already pure, already unit-tested, and already needs no WASM to compile. So a vitest case that walks `doc/**/*.md`, extracts every ```` ```parametric ```` fenced block, and asserts each one **compiles with zero rejected steps** is a small, fully-headless test with no sandboxing question to answer. Adopt FluidCAD's **fenced-language-as-opt-in marker** convention exactly: ```` ```json ```` blocks stay illustrative and are ignored, only the dedicated language tag is executed, so an author opts a block in per-block rather than having every code block in the docs become a test. Catches the three documented rot classes — a syntax error in an example, an example naming an op kind or field that no longer exists, and a block that compiles but produces nothing.

    **Phase 2 (S–M) — a coverage gate with three failure modes, not one.** The authoritative symbol list already exists and needs no new registry: `describeCapabilities()`' op catalog is exactly the set of things that must be documented. The gate fails on **missing** (a documented-nowhere op kind), on **stale** (a doc claiming an op kind that no longer exists — *this* is the one that catches renames, and it is the half most such gates omit), and on **unused-allowlist** (an opt-out entry that is now documented or no longer exported, so the escape hatch garbage-collects itself rather than rotting). Keep the allowlist a committed file with a `# reason` comment per entry, so every opt-out shows up in review — this codebase already applies the same "no silent skips" discipline to `validateEditOp`'s rejections and to every `warnings` array in the MCP surface.

    **Deliberately NOT proposing a separate `llm-docs/` tree.** FluidCAD needs one because its MCP server is a *thin proxy with no other doc channel*; CAD-Preview already ships `describe_capabilities` as a first-class tool that returns the op catalog, parameter docs, entity-id scheme, export matrix, and `verdictConventions` in one call. Duplicating that into a second hand-maintained tree would create exactly the drift this item exists to prevent. The gap is verification of what already exists, not a new surface — which is why this is Tier 6 and **S–M**, not a new-capability item.

    **Verification**: the extractor and the gate are both pure Node/TypeScript, unit-testable with a temp fixture tree (a doc with a good block, one with a bad block, one claiming a nonexistent op kind), plus the gate itself running green over the real `doc/` tree. No WASM, no webview, no F5 caveat — the first item in this file with no verification gap at all.

## Non-goals / known constraints

- **Writing the CAD source file** — never. The read-only invariant (sidecar persistence, export-only baking) is architectural, not a missing feature.
- **OCCT in the webview** — the kernel stays in the extension host; the webview runs only Three.js (architecture invariant).
- **G-code preview** — considered (text-to-cad ships a strong implementation: layer scrubbing, feature-type coloring, adaptive decimation) and rejected: 3D-printing-oriented, outside this extension's CAD/FEM domain.
- **URDF/SDF robotics rendering** — considered (joint articulation, FK, MoveIt2 integration in text-to-cad) and rejected for the same reason.
- **Interactive sketching with geometric constraints** — considered and rejected, not deferred. It is the single clearest "this is a modeling application now" feature, and CAD-Preview is a preview/inspect/prepare tool. More concretely: the numeric profile and curve forms are **not** a degraded mouse — they accept parametric variable expressions (`L*2`, `R*cos(i*360/N)`) that a click-to-place tool cannot express, so replacing them with drawing would trade away a distinguishing capability for a familiar one. Worth noting that SketchForge, a dedicated sketch application, still has no constraint solver either — building this would mean shipping the weak two-thirds of the feature.
- **Reference-image tracing underlay** — rejected. Its value is almost entirely to sketching, which is a non-goal above; and it would punch a hole in a real design property: every texture in the webview is a procedurally-drawn `CanvasTexture` (`geometryBuilder.ts`'s `dotTexture()`, `labelOverlay.ts`, the generated-SVG icon pipeline), a deliberately asset-free design driven by the webview's CSP. Injecting a user-supplied data-URL image trades that away for a workflow the tool doesn't have.
- **2D vector technical drawings via hidden-line removal** — **kernel-blocked, not deprioritized.** Every `HLRBRep_*` class is red in this OCCT WASM build: `HLRBRep_Algo`, `HLRBRep_PolyAlgo`, `HLRBRep_HLRToShape`, `HLRBRep_PolyHLRToShape`. `HLRAlgo_Projector` is green but is a low-level internal only reachable through them. Same class of finding as `Message_ProgressRange_1` and `Interface_Static.CVal` — recorded here so it isn't re-proposed.

  **The narrow survivor, `HLRAppli_ReflectLines`, has now been probed against the live WASM, and it is not the way in either.** The binding genuinely works — the unsuffixed constructor takes a `TopoDS_Shape`, and `SetAxes`/`Perform`/`GetResult` are all bound and functional (249 ms on `bull.stp`, returning a non-null compound this codebase's own `enumerateEdges` reads as 25 edges). It was rejected on the drawing itself, which is only visible by looking at it: rendered side by side against a tessellation-derived silhouette of the same view, `GetResult()` produced the outer boundary and a few fragments while missing the part's circular holes and interior cutout entirely. `GetResult()` returns reflect lines only; sharp feature edges live behind `GetCompoundOf3dEdges(type, …)`, whose `type` argument is an `HLRBRep_TypeOfResultingEdge` — from the entirely-red family above — so calling it throws. The one filter that would make the kernel path competitive is unreachable. **SVG silhouette export shipped anyway**, built on triangle adjacency instead (`silhouetteEdges.ts`), which additionally works for STL/OBJ/PLY/glTF sources that `HLRAppli_ReflectLines` could never have handled — see `CLAUDE.md`'s "SVG silhouette export" section. Hidden-line *drawings* remain out of reach through the B-rep kernel; an *outline* no longer is.

  **A kernel-agnostic path was found after this note was last updated — see item 22, now queued in Tier 4.** The blocker above is specific to OCCT's own `HLRBRep_*` family; it says nothing about a hidden-line test built directly on the tessellated triangles this codebase already has for every source, B-rep or mesh. A local sibling project, HCAD, independently ships exactly that: a grid-bucketed per-edge visibility test with no B-rep HLR call anywhere in it. This doesn't change anything above — the B-rep kernel path is still dead, for the reasons already recorded — but it means hidden-line *drawings*, not just an outline, are no longer permanently out of reach either; they're queued, not ruled out.
- **3D text, engraving, and embossing** — **kernel-blocked.** `Font_BRepFont` and `Font_BRepTextBuilder` are both red in this build, so there is no path from a glyph to a `TopoDS_Shape`.
- **Parametric part generators (gears, threads, springs)** — rejected. Standard parts are something this tool should *source*, not *author*: `search_standard_parts`/`download_standard_part` already fetch real, verified geometry from step.parts as ordinary STEP files the existing pipeline opens (and, since the closed "Standard-parts browse and insert panel" item, so does the interactive sidebar). Authoring involute gear profiles is modeling-application scope.
