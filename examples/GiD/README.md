# GiD postprocess fixtures

`two-tets.post.msh` + `two-tets.post.res` — two tetrahedra sharing a face,
written by meshio++'s own GiD writer (v10.18.0+) so the committed files are
exactly what the library itself produces. Generated by converting
`../MED/two-material-tets.med`, the same geometry the MED fixture carries.

```
two-tets.post.msh   ← geometry (nodes + elements)
two-tets.post.res   ← results sibling, found by stem convention
```

## Why both files, and why only one of them opens

GiD's ascii flavour splits a model across a **sibling pair**: geometry in
`<stem>.post.msh`, results in `<stem>.post.res`. The reader discovers the
`.post.res` purely by swapping that final segment — nothing inside the
`.post.msh` names it — so the two must travel together.

CAD-Preview routes only the `.post.msh`; `.post.res` is deliberately **not**
independently openable (it is not a mesh). `meshioCompanions.ts` stages the
sibling into meshio++'s MEMFS alongside the primary, the same way it already
stages XDMF's `.h5`.

## `.post.msh` is a compound extension — and that matters

It ends in `.msh`, which CAD-Preview registers to a **different** format
(Gmsh). `routeFile` therefore matches the **longest** registered suffix first;
a last-dot-only lookup would silently resolve every GiD file to a Gmsh parse
that then fails. This is the same bug meshio++ itself had to fix in its own
`resolve_format` in 10.18.0. See `src/fileRouter.ts`.

## Flavours

Only the **ascii** flavour is registered. meshio++ also reads GiD's
`binary` (`.post.bin`) and `hdf5` (`.post.h5`) flavours, but this codebase has
no fixture verifying either, and its standing discipline is to claim only what
has actually been checked — so neither extension is routed.
